# Additional Pre-Play Locality With One Source Foundation

> **OOC DEVELOPMENT / SCENARIO INSTRUMENTATION.** This is an out-of-character local console path that lets an operator author, confirm and commit **ONE additional distinct World-State locus and ONE EXACT_FINITE Source Condition at that new locus** to an ORIGINAL locality that `establish-locality` already committed, **before any player character is bound**. It is **mechanism only**: two physical setting facts. It is not a world builder, not a route or map, not movement, not travel, not source discovery, not perception, not knowledge, not extraction, not collection, not an availability verdict and not autonomous NPC behaviour. It creates no world, game actor, cohort, relationship or character, no corridor, route, edge, distance or traversal duration, grants no permission to extract anything, and advances no time.

Bounded implementation slice (`@immortalis/operator`: `establish-additional-locality`), composed from the **already implemented** World-State owner operations `CanonicalCampaign.establishLocus` and then `CanonicalCampaign.establishSourceCondition`. No `packages/contracts`, `packages/engine`, `packages/protocol` or `packages/testkit` module changed; there is no new World-State operation, owner, facet, schema, source key class, persistent receipt format, status gate or universal locality or multiple-source initializer. The shipped binary registers no owner extension.

Authority: the BLUE v5.2-A1 bounded implementation brief "Additional Pre-Play Locality and Finite Source" (native pin `2026-10-22T01:26:01.691Z`) on official `main` `a10421dd2f433bc5bdd90d03ff39ebccfc96448b` (after merged #75 and #76), under F-027 v1.0 (`spec/f027/spec-lock.json`, blob `ba46a5d19985bd360ba0cc47217d0947dc3fc4f3`, unchanged) and the frozen WG / WS-003 §§4, 4A, 4B authority that `establish-locality` already uses. **No source pin, Runtime Contract snapshot, open gate, acceptance row or status changed. F-028/OB-030 remains Blocked, PF-6 inactive, IA/V unpromoted.** Local success is not provider or recovery acceptance. ## The command

```
immortalis-operator establish-additional-locality --campaign <dir> --campaign-id <id> --locality-file <file> [--operator-dir <dir>] [--reclaim-stale-lock]
```

The locality file is one strict JSON document:

```
{
  "format": "immortalis-additional-locality",
  "format_version": 1,
  "locus":  { "world_id", "locus_id", "designation", "constraints": [ { "aspect", "statement" } ] },
  "source": { "source_key", "world_id", "locus_id", "dimension", "material_class",
              "quantity": { "amount", "unit" }, "access_facts": [ { "aspect", "statement" } ], "statement" }
}
```

The `locus` section carries exactly the authored fields of the existing `WorldLocusSchema` (`locus_id`, `designation`, `constraints`) plus the `world_id` it belongs to; the service derives the fact reference to the world, which is never authored or copied. The `source` section is **exactly one `EstablishSourceConditionInput`** (`packages/contracts/src/source-drawdown.ts`, unchanged), the same shape as the `source` section of the `establish-locality` setup file. Every object is strict and every field required: the file can carry no owner, facet, version, depth, recoverable, delivered, establishment, exhaustion, route, edge, distance, travel duration, publication label or "confirmed" claim (each is an unknown field and is refused). The two sections must agree on the world, and the source must be **at the new locus**. `quantity.amount` is a positive safe integer; a zero, negative, fractional, string, ranged or estimated quantity has no representation.

The file is read once, from one open descriptor: a regular file (not a link) owned by the invoking OS user and writable by nobody else, of bounded size. What was read is what is shown, confirmed and committed; a file changed afterwards cannot change it.

**Operator eligibility, not a source-validity rule.** This path additionally requires at least one authored physical access fact, so that the source can later be the target of the existing source-qualified observation (`observe-surroundings --source`), which uses only `source.access.N` premises. That is this command's own condition, as it was for `establish-additional-source`; the Source Condition schema is unchanged.

## Sequence

1. **Read and check the file** (above). Nothing is asked of the console if it is refused.
2. **Open the existing package** for the local operator (the usual OS-user verification, the package lock, journal replay and canonical integrity). This command **never creates, adopts, repairs or clears** a package: a missing or foreign directory, or another campaign identity, is `SESSION_UNAVAILABLE`.
3. **Read the established locality from canon** (`establishedLocality`, read-only, shared with `establish-additional-source`): the ORIGINAL world, the first locus and the first source that one `establish-locality` setup identity committed, each still the version-1 fact that setup wrote. None held, or the confirmed locus or source uncommitted → `LOCALITY_NOT_ESTABLISHED`; held but since advanced → `PRE_PLAY_CLOSED`.
4. **If this identity already committed** (a repeat, a lost reply, a restart): judge it on the immutable committed records. When **both** the locus and the source committed with the content of this file, they are verified and reported **without asking again and without a write**. A different proposal under a held locus or source key (the identity is derived from the exact content, so it cannot be the committed one) is `LOCALITY_CONFLICT` / `SOURCE_CONFLICT`, and an identity whose committed record disagrees with this file is the same refusal.
5. **Pre-play and consistency refusals**, all before the console is asked and with no write: a bound player character (`role.player_character` binding present) → `PRE_PLAY_CLOSED`; a locus or source for another world → `WORLD_MISMATCH`; the locus key already held (including the first locus's, or another proposal's) → `LOCALITY_CONFLICT`; the source key already held (including the first source's or an earlier additional source's) → `SOURCE_CONFLICT`; a **different** additional locus of this command that holds its locus without its source → `LOCALITY_CONFLICT` (an incomplete locality is finished from its own file or not at all, never built over or abandoned).
6. **Prove the owner path admits it**: the committed world is republished on a scratch package that is then removed, and the locus and then the source are run through the genuine `establishLocus` and `establishSourceCondition` (the owner also rejects, for example, duplicate access aspects). A refusal is `INVALID_LOCALITY` with nothing written. The scratch package is never reused.
7. **Confirm, once.** The whole proposal is shown (authored text JSON-quoted so a control sequence cannot rewrite the console) with what it does **not** do and the stages still to commit. The operator types `establish-additional-locality <fresh challenge>` on the very next line; anything else, a stale or pre-typed line, another verb's phrase or end of input declines and nothing has been written. The confirmation is a one-time token bound to the verb and the exact subject (campaign, established locality, additional identity, pending stages and the full locus and source).
8. **Commit in dependency order**, each a separate durable World-State publication: the locus through `CanonicalCampaign.establishLocus` (`PROGRESS locus COMMITTED …`) and **only once that fact is committed** the source through `CanonicalCampaign.establishSourceCondition` (`PROGRESS source COMMITTED …`). The owner derives `depth: EXACT_FINITE`, `establishment.kind: INITIAL_SETTING_FACT`, `recoverable = quantity`, `delivered: []`, `exhaustion: null`, the locality references, and reads and depends on the world and locus facts. The operator never writes either fact directly, and the store's own dependency rule refuses a source whose locus is not committed. An unknown outcome of the locus publication is never followed by an attempt at the source.
9. **Verify on a fresh reopen.** The package is closed and reopened through the engine's owner-verified open; both new facts' keys, owner/facets, version 1, typed values and committed provenance are compared with the confirmed proposal, **every fact the campaign held before is compared with its pre-commit self** (key, owner, facet, value, version, provenance), and the fact count and revision are exactly the expected number greater. Only then is `ADDITIONAL_LOCALITY_READY` reported.

Statuses: `ADDITIONAL_LOCALITY_READY`, `ADDITIONAL_LOCALITY_INCOMPLETE`, `ADDITIONAL_LOCALITY_OUTCOME_UNKNOWN`, `ADDITIONAL_LOCALITY_REFUSED`, `ADDITIONAL_LOCALITY_VERIFICATION_FAILED`, `LOCALITY_NOT_ESTABLISHED`, `PRE_PLAY_CLOSED`, `WORLD_MISMATCH`, `LOCALITY_CONFLICT`, `SOURCE_CONFLICT`, `SESSION_UNAVAILABLE`, `DECLINED`, `INVALID_LOCALITY`, `LOCALITY_FILE_UNTRUSTED`, `LOCALITY_FILE_UNREADABLE`. `ADDITIONAL_LOCALITY_READY` means exactly: this locus and this source are both committed under this identity, verify, and nothing earlier changed. A locus committed without its source is `ADDITIONAL_LOCALITY_INCOMPLETE` (a known refusal of the source) or `ADDITIONAL_LOCALITY_OUTCOME_UNKNOWN`, and is **never** called an established additional locality. It is not perception, knowledge, availability, reachability or permission.

## Identity, convergence and fail-closed

The service authors only the technical publication identities and derives them from the exact authored content, never from a clock or a random value: `<id>` is a hash of the campaign identity, the locus section and the source section, giving, per stage `locus` / `source`, group `operator-additional-locality:<id>:<stage>`, intent `operator-additional-locality-intent:<id>:<stage>` and cause `operator-additional-locality-cause:<id>`.

- **The same confirmed proposal always reaches the same identities.** A retry after a crash or a lost reply replays what committed (RC-16, by the store's own identity check) and finishes what did not; it never writes a second, rerolled or altered locus or source.
- **Any different content, even under the same keys, meets the committed identities and is refused**; committed facts are never replaced, and a proposal for a held key is never treated as a new locality. After a crash between the two publications only the exact original proposal can finish the pair.
- **No retained state is added.** There is no new pin, receipt or ledger format: the committed record in the package is the only memory of what committed. An uncertain outcome is resolved only by reopening and reading canon.
- **No arbitrary global restriction on lawful distinct keys.** One invocation admits one pair; a further distinct locus and source (and an earlier `establish-additional-source` source) coexist with it, so long as no other additional locus of this command is left without its source.

## Recovery

The package's own file lock and durable-write order are used unchanged. A kill leaves the lock; it is refused until the operator explicitly passes `--reclaim-stale-lock`, which the engine honours only for a provably dead holder. Tests interrupt before the locus, after the locus and before the source, after the source and before the reply, after the close and before the readback (a failed reopen), by a commit that never reached the store, by an uncertain store outcome, by an incompatible replay, by a real `SIGKILL` of the shipped binary at the console and after each commit, and by a failure before **and** after every mutating filesystem operation of the whole command; each converges on the uninterrupted campaign (equal head, state and journal hashes), and at no cut is a source present without its locus.

## Security

The full proposal (locus, quantity, material class, keys, access facts and statements) is shown only on the operator's own console and held only in the owner-verified package. It is not written to the retained-state directory, and no host-facing surface (referee, player-view, observe-request or advance-request MCP servers) imports or names this command. **No MCP, phone or client locus or source list, search or creation tool is added**, and the fixed-shape withholding of the existing source-qualified observation is untouched. The module has no network, child-process, environment or global-state access.

## Downstream boundary

Nothing here makes a host discover a locus or source, creates a way to reach one, or permits collection. Two World-State loci do not imply a route, distance, edge or traversal between them: route, time and commit authority for movement remain explicitly missing, and the existing original-PC movement derivation is unchanged. **A character at the first locus is not co-located with the new source.** The existing `observe-surroundings --source <key>` requires the source to be local to the character's own physical custody; a test builds the pair before the character is authored and placed at the first locus and shows that naming the new source is refused identically to an absent source, with the host never asked and nothing written. Any future presence, observation or movement at the new locus needs its own lawful cause and authority and is **not** included in or accepted by this slice. No test in this slice asserts a route, travel, movement, perception, availability, extraction or collection verdict.

## Mechanical pin adjustments

Seven predecessor conformance tests pin the bytes of the operator files this command must touch to exist at all (`cli.ts`: the new command; `confirmation.ts`: its own confirmation verb, so its confirmation cannot be presented as the locality's or the source's; `index.ts`: three named exports), the operator package's module inventory and its exported surface. Their hashes, inventories and lists were adjusted openly, as the previous slices did, and nothing else in those tests changed.

Two predecessor security scans were taught about the new module: the scan that names the operator modules mentioning a source key now lists `additional-locality.ts` (it is a trusted-side module that establishes a locus and source, like `locality.ts` and `additional-source.ts`), and the scan for canon-writing calls exempts it as it exempts them, because its scratch dry run republishes the committed world on a throwaway package. It is bound instead by `tests/security/additional-locality-security.test.ts`, which requires that, outside that dry run, the module's only writes are the existing `establishLocus` and `establishSourceCondition`.

`additional-source.ts` changed only by exporting two read-only helpers it already had (`establishedLocality`, with its result type, and `sourceProblems`) so that both commands judge the established locality and a source against its confirmed content identically; no behaviour of `establish-additional-source` changed. `locality.ts`, the confirmation semantics, `commands.ts`, `session.ts`, the contracts, the engine owner API, the spec lock, gates and register remain byte-identical to `main` (pinned in `tests/conformance/additional-locality-conformance.test.ts`).
