# Local Trusted PC Command & Reopen Continuation Foundation

Bounded implementation slice (`@immortalis/operator`), built on the Trusted Confirmed Active-PC Single-Leg Movement Gateway (`docs/protocol-pc-relocation-foundation.md`), the Trusted Stop-at-Delivery Temporal Advance Gateway (`docs/protocol-pc-transfer-advance-foundation.md`), the Active-PC Post-Handover Physical Locus Custody (`docs/pc-locus-custody-foundation.md`), the Canonical Campaign file package (`docs/campaign-package.md`) and the Temporal kernel (`docs/temporal-foundation.md`). **A local operator can open one saved campaign, make the two distinct player choices of one post-handover active-PC single-leg relocation — each with its own explicit console confirmation — through the unchanged host-protocol gateways, close, and reopen the same campaign to reconcile an ambiguous outcome or to make the next separately confirmed choice, by the original identities.** It is a mechanism, not a game feature: it creates no campaign, PC, binding, custody, destination, event, observation or knowledge, and it claims no arrival.

## The trust boundary, and what it is not

1. **The verified operator** is the OS user (uid) that runs the process and **owns** the chosen campaign directory, which must not be writable by group or other. Whoever can write the package can already forge canon, so the operator who may command it is the user who owns it. The retained-intent directory is stricter: owned by the same user and closed to everyone else (mode `0700`); an existing looser directory is refused, never silently changed.
2. **The chosen campaign** is named by the operator (`--campaign-id` is required for every command that changes anything). A different identity in that directory is refused (`CAMPAIGN_MISMATCH`); a ledger belonging to another campaign or operator is refused and never adopted.
3. **Confirmation** is the operator typing, on the very next console line, `relocate <challenge>` or `advance <challenge>`, where the challenge is fresh, unpredictable and printed only after the service has stated the exact choice. A recorded "yes", a line typed before the prompt, free text, an LLM sentence, a stale challenge, the other verb, an empty line or the end of input all decline. The two choices use different verbs and different fresh challenges, so the first confirmation is not, and cannot be presented as, the second.
4. **Authority is stated by this trusted side and never read from input.** The service passes the contracts' own `PLAYER_CHOICE_AUTHORITY` (`role.player` + `permission.player_choice.commit`) to the existing binders. There is no `confirmed` flag, role, permission, identity, status or owner-result field on the command line or in any command input; the input schemas are strict.
5. **Not claimed:** that a human, rather than a script, is typing; any login, credential, tenant, session cookie or remote identity — **no remote authentication provider is implemented or claimed**; confidentiality against a user who owns the package (they can already read and forge it); or a production authorization. A deployment that needs more must add it separately; nothing here is a hosted service, HTTP/MCP surface, multiuser deployment or LLM interpreter.

## The sequence

1. **`relocate --world W --locus L --delivery-unit U --delivery-value N`** (confirmation 1 of 2). The PC is **not** an input: it is the active PC of the operative binding, read from canon, with its stationary custody. The destination must already be an established locus. The service shows the campaign, operator, character, origin, destination and the declared delivery boundary, and asks. On confirmation it retains the intent, binds `bindTrustedConfirmedPcRelocationContext` and invokes `commitConfirmedPcRelocation`: the PC-owned voluntary commitment → PC-owned Movement Service Request → Logistics commitment → Logistics dispatch → Temporal registration, each under its own owner and unchanged. It advances **no** time and delivers nothing.
2. **Close, then reopen** (a new process or session; every handle is rebuilt from the verified current campaign).
3. **`advance`** (confirmation 2 of 2, a distinct choice). No operator input at all: the stop, object and any held remainder are read by the gateway from the Temporal kernel's own registered state. The service mints a new immutable `transaction_id` (and cause, trigger, publication labels), retains it, binds `bindTrustedConfirmedPcTransferAdvanceContext` and invokes `advanceConfirmedPcTransferToDelivery`. The kernel alone selects what is due (any independently registered work, e.g. a GIP sunset, resolves in its own order) and the stage owners alone commit Logistics delivery → World-State destination → Logistics retirement.
4. **Held remainder.** A truthful `DEPENDENCY_UNRESOLVED` stop leaves one held remainder. Nothing retries it — not a reconcile, a status, a reopen or the passage of the session. Only a **newly confirmed** `advance`, with its own transaction identity, consumes it (`continues` = the held transaction, the prior request verbatim, as the gateway already does).

Statuses: the gateways' three minimum ones (`RELOCATION_COMMITTED`/`ADVANCE_COMMITTED` mean a **transaction committed**, never arrival, perception or knowledge; `*_OUTCOME_UNKNOWN` is neither failure nor success) plus the service's own neutral ones (`DECLINED`, `UNAVAILABLE`, `INVALID_INPUT`, `SESSION_CLOSED`, `RECONCILIATION_REQUIRED`, `CHANGED_CHOICE`, `STALE_INTENT`, `NOTHING_TO_RECONCILE`). Every refusal derived from canonical state is the one `UNAVAILABLE`, with no cause, owner, key, revision, hash, stop reason or held-remainder detail. The console never prints a fact key, identity, hash or stop reason.

## The delivery boundary is a declared input

No source defines a travel time, route or duration (CAL-01 stays UNCALIBRATED), and canonical state holds no pre-existing delivery boundary for a journey that has not yet been committed: the existing relocation gateway already takes it from its trusted side as an explicit, declared `delivery_at`. This mechanism does not derive, default, validate against distance or invent one. The operator states it explicitly on the command line, it is shown in confirmation 1, and the Logistics owner re-judges it. **Where the operator's declaration comes from (the independent journey premise) is outside this mechanism;** if a deployment needs the boundary to originate in an authoritative source, that source does not exist yet and must be supplied by Blue, not by this package.

## Retained intents and recovery (RC-16)

Each confirmed choice is written durably to `<campaign>.operator/intents-<hash>.json` (or `--operator-dir`) **before** the gateway is invoked, then marked `COMMITTED` after the gateway reports it. A crash, lost reply or ambiguous outcome therefore leaves a `CONFIRMED` intent that **`reconcile`** presents again, by its original identity, to the unchanged gateways — which replay what committed and finish what did not — without asking again (the choice was already confirmed; nothing here can create a new one). Before replay the intent is compared with canon: a different destination or boundary in canon is `CHANGED_CHOICE`, and a retained `COMMITTED` that canon no longer holds (an older save restored under it) is `STALE_INTENT`; neither replays.

- A session becomes **ambiguous** the moment any write has an unknown outcome and refuses everything but close; only reopen reconciles.
- While any confirmed intent is unreconciled, **no new choice** can be made (`RECONCILIATION_REQUIRED`), including from a fresh session.
- A refusal that left no canonical footprint forgets the intent (it had no effect); one that left a footprint keeps it. A retained relocation is replaced by a different one only if it never took effect, or took effect only as the PC-side willingness toward the same destination (so only the declared boundary is open); that needs a fresh confirmation. After Logistics commits, nothing replaces it.
- A crash that leaves the package `LOCK` behind is refused (`LOCKED`) until the operator explicitly passes `--reclaim-stale-lock`, which the engine honours only for a provably dead holder.
- Tests prove convergence on the uninterrupted canon (equal `state_sha256`) for a lost reply or unwritten group at each of the five relocation commits and each progression group, and for a failure before or after **every** mutating filesystem operation of both commands and of each command's two retained-intent writes.

## Refusals (fail closed; no write, no duplicate, no leak)

Cancel or decline either confirmation; malformed, extra, missing or over-claiming input (unknown flag, duplicated flag, `--role`, `--pc`, `--confirmed`, a transaction identity); an absent or stale session; a different campaign; a missing active PC, custody or destination; a destination that is the origin (owner refusal); a changed destination or boundary after a choice is retained; an unauthorized role/permission (never an input); an old session or an old trusted handle after close/reopen; two operators on one campaign (lock conflict); a corrupted journal; a foreign-owned or group/other-writable package; a ledger of another campaign/operator or a malformed one; a progression before any relocation or after delivery; and an unsupported action. The injected store/disk faults above exercise the unknown-outcome and crash cases.

## Not claimed

First-playable certification; any physical perception producer or route; autonomous NPC choice; a generic action interpreter or natural-language game host; multi-journey routes or durations; a second journey, reverse handover or Economy holding; remote or hosted deployment, HTTP/MCP, paid APIs, an LLM, multiplayer, tenants or accounts; production authorization; provider or recovery acceptance (IA-07 BLOCKED); any IA/V row, gate, source-lock or F-027 spec change; PF-6/F-028 activation. A committed relocation or advance is a **transaction status**: arrival, perception, narration and knowledge require separate lawful I-001/F-014D access, which this slice does not implement.

## Residuals

- The saved campaign must be opened with the owner registrations it was written with. The shipped binary registers none (the canonical registry only); the test campaign's history source behind the actor is a testkit stand-in registered by the test process entry (`tests/support/operator-process-entry.ts`), because no production producer of that history exists. It grants no role, permission or authority.
- The publication labels `basis` (`local-operator-confirmed-choice`) and `secrecy` (`local-operator-session`) and the identities the service mints are technical encodings authored by this trusted side (F-027 defines no vocabulary for them); the PC, Logistics and Temporal owners do not interpret them.
- A lost retained-intent file strands an unfinished journey from reconciliation (the same choice can be restated and re-confirmed, since the gateways' identities derive from the PC); it cannot be mistaken for a new journey, because canon holds the footprint.
- Lock contention is refused, not queued. The ledger and canon are two files, not one atomic unit; the ordering (retain, then present, then settle) and reconciliation are what make that safe.
- Node `>=22.22.2` is required by the repository; the command line runs TypeScript with `--experimental-strip-types`.
