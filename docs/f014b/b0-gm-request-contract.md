### 2.4 SI_SUBDAY_V1 conversion and safe arithmetic

`siSubdayV1Target(basis: CanonicalTime, value: number, unit: "second"|"minute"|"hour"): Result<CanonicalTime, "INPUT_INVALID">` (pure, CANDIDATE):

```text
converted = value * SI_SUBDAY_V1_SECONDS[unit]
targetVal = basis.value + converted
refuse unless Number.isSafeInteger(converted) && Number.isSafeInteger(targetVal) && converted >= 1
return { unit: basis.unit, value: targetVal }        // unit carried verbatim, never mapped (A5 "no arbitrary unit mapping")
```

- **Source of the factors.** A5 and A9 supply them, and the P1a/P1b fixtures confirm them: "T0 second:100 ... 3 seconds → Derived target 103" and "10 minutes → SI_SUBDAY_V1 target 700" (v0.6 §7).
- **Bounds come from existing code only.**
  - `basis.value ∈ [0, 2^53−1]`, because `CanonicalTimeSchema` enforces `int().nonnegative().max(Number.MAX_SAFE_INTEGER)` (`temporal.ts:51`).
  - `value ∈ [1, 2^53−1]`.
  - The target must satisfy the same `CanonicalTimeSchema` bound.
  - Exactness: the guard is `Number.isSafeInteger` on both the product and the sum. This is the existing pattern at `engine/src/pc-collection/derive.ts:446–452` ("the derived completion is not representable"). IEEE rounding is monotonic, so any exact result above 2^53−1 rounds to a value of at least 2^53 and fails the guard, and any result at or below 2^53−1 is exact.
  - The resulting maximum `value` at basis 0 is 9 007 199 254 740 991 seconds, 150 119 987 579 016 minutes and 2 501 999 792 983 hours. In general it is `floor((2^53−1 − basis.value) / factor)`.
- **No other cap.** A9 says "No arbitrary numeric wait cap is adopted", and the static public horizon limit of v0.6 §5.1 belongs to the B1 catalogue. Whether "SUBDAY" implies a cap below one day is OSQ-9.
- **What the unit means.** The result is in canonical coordinate units. Reading those units as seconds is valid only after B1's category-8 check that the clock origin is one SI second per unit (A17 §5). B0 never reads or infers this, and it never branches on the spelling of `basis.unit` (A17 §2).

### 2.5 Cross-field rules and the composed parser

## 6. What B0 does not do, and test labelling

B0 does none of the following:

- It opens no transaction and writes nothing: no store, coordinator, journal or ledger, no durable writer, and no `TransactionAuthority` or `ResolutionTransaction` value (A12 §1, §3).
- It performs no read of any kind. That includes no T0 category 1–8 read. In particular it does not read `temporal/origin`, does not call A0's preparatory `siOriginWitnessViolation` (PR #116, §3.8), and does not compare `observed_basis` with the live clock (A7 category 2 is B1).
- It makes no positive catalogue eligibility decision. Only the `catalogue_sha256` shape is checked, with no digest equality and no LC-05 disposition (A12 §3).
- It infers nothing from the spelling of `observed_basis.unit` (A17 §2).
- It performs no authentication, session binding, `transaction_id` derivation, or GM tool-argument schema (v0.6 §6.1 belongs to the B1 ingress).
- It defines no PAUSED, INTERRUPTED, RESUME, knowledge-verdict or supersedes form (A10; A15 §2 → B2).
- It changes no legacy schema, gateway, guard or history policy (P1–P4; A12 §5: zero transitions).
- It supplies no GM-facing output and no normalized-class mapping.

Labelling (A12 §1, §5; A13 §4):

- Every B0 test title begins `B0 refusal-only:` or `B0 shape control (not admission):`.
- No title or assertion message may contain `PASS`, `ELIGIBLE`, `ADMITTED`, `T0` or `B1`, or any claim of a source-qualified engine transaction.
- Each suite's header comment states: "T1 mechanism component (BLUE v0.3 §4): strict request/refusal contract only; no B1 positive, no T0 PASS, no production capability; F-014B LC closures unchanged."
- Shape-control positives (B0-01..03) exist only so that the negative tests are not tautological, in the sense of A12 §5. P1a/P1b are "hypothetical arithmetic/owner-resolution witnesses" (v0.6 §10).

## 8. Open source questions

These are genuine gaps where neither the sources nor the code determine one answer.

- **OSQ-1, trigger wire spelling.** The sources give `GM_INTERPRETED_PC_WAIT`. Every existing kind in code is lowercase-hyphenated (`direct-observation`, `operator-…-choice`). A9 §3 leaves "exact wire naming" pending. This draft uses the source spelling verbatim.
- **OSQ-2, `trigger.ref` content.** The sources are silent on what `trigger.ref` names for a GM wait (a JSON-RPC request, an action namespace, or something else). v0.6 §6.1 defines only the transaction-ID derivation. B0 checks `Id` only.
- **OSQ-3, `cause` and `publication` values.** The sources give no GM-wait values for `cause` or `publication {basis, secrecy}`. B0 checks `Id` only.
- **OSQ-4, evaluator-policy identity.**
  - A10 §7.1(5) and §8.1(5) require a "§10 evaluator-policy version" to equal "the sealed INITIAL identities", and evaluator-policy identity to be "represented across strict request/authority/seal variants".
  - But the v0.6 §4.1 INITIAL field list (A4) has no such member, and A11 says "No extra strict INITIAL member ... is approved".
  - B0 follows A4 and A11, so the member is absent and refused (R31). Whether it is a `gm_wait` member, an authority field or a catalogue component is undetermined.
- **OSQ-5, the literal site of "ResolutionRequestSchema validation" (A1).** Because of P1–P3, the exported `ResolutionRequestSchema` cannot host the exclusivity rule without changing the protected legacy binders' accepted inputs or crashing their module load. Two readings remain open for BLUE, and B0's separate GM shape fits either:
  - (a) "request validation" means the request stage: a dispatch at `coordinator.ts:429` over an unchanged player schema plus the new GM schema;
  - (b) the shared context is widened (v0.3 §8 "even when shared context parser expanded"), and the legacy binders' refusal-before-read promise (P3) is given up to kernel-side refusal.
- **OSQ-6, D-3 suite pins for kernel files.**
  - `temporal.ts` and `temporal/integrity.ts` are each pinned inside all three D-3 conformance suites (P7; integrity at `protocol-pc-target-advance-conformance:70–71`, `protocol-null-pc-ooc-advance-conformance:55–56`, `protocol-null-pc-ooc-held-continuation-conformance:63–64`).
  - v0.4 §2 item 3 requires N-1 inside `integrity.ts`, which is B1. v0.3 §7 puts the D-3 gateways and their conformance pins out of scope (W3).
  - The freight slice's precedent replaced kernel-file pins in those suites with scoped-delta comments (e.g. `protocol-pc-target-advance-conformance:65`, `:76`). Whether that counts as W3 is not decided by v0.5 §4 ("W3 is invoked only if ... not by ordinary exact hash retesting of the shared Temporal source").
  - The question binds B1, and it also binds B0 if Option E2 is chosen.
- **OSQ-7, the form of post-PAUSED and post-INTERRUPTED re-entries.** These are `GM_RESUME_ADJUDICATED_WAIT` and continuation after INTERRUPTED (A10 §7.1(5), §7.2(2)). Whether each is a third `gm_wait` phase, a separate request, or the existing CONTINUATION is undetermined. B0 refuses them as unlowered (R03, R13).
- **OSQ-8, the scope of "declaration shapes" (A12 §1).** It is unstated whether this includes:
  - the Role Registry §5 row (v0.6 §3 interface bullets) as a typed record;
  - the catalogue disposition vocabulary (`INERT` / `PASSIVE_PROVEN` / `ACTIONABLE_OR_UNSAFE` / `UNDECLARED`, v0.6 §5.1, plus the prospective `INTERRUPTION_GUARDED`, A10 §8.1(2)).
    This draft limits B0 to the request and `gm_wait` shapes, because A12 §3 assigns the LC-05 catalogue to B1.
- **OSQ-9, the "SUBDAY" bound.** It is unclear whether `SI_SUBDAY_V1` caps the converted duration below one day (86 400 s). The sources fix only the units, and A9 says "No arbitrary numeric wait cap is adopted". B0 applies representability only.
- **OSQ-10, the GM tool-argument shape.** Which fields the model supplies is not enumerated. The transaction ID and target are adapter-derived (v0.6 §1, §6.1), and `observed_basis` is "seen by the GM". This is a B1 ingress question.
- **OSQ-11, refusal vocabulary.** There is no source or code code for pairing-denied, arithmetic or origin-mismatch reasons. B0 maps every refusal to an existing `TemporalErrorCode` and leaves the reason labels open. Whether B0 request-shape refusals must share the GM-facing normalized "unavailability" class (A10 §7.1(3)) is B1's to fix.
- **OSQ-12, catalogue digest semantics.** A11 leaves "the proposed versioned catalogue-manifest resolution" unreconciled: the hash input, canonicalization, and the "version and source equality" of A4. B0 checks the 64-lowercase-hex shape only.

### Source/code contradictions found (for BLUE)

- **K1, pin census.** v0.5 §4 P-3 and RED v0.4 P-3 say `temporal.ts` is byte-pinned in `operator-conformance` (L61–62) and that "No hash pin on integrity.ts was located". At `0c9e74b`, `temporal.ts` is pinned at **11** sites and `temporal/integrity.ts` at **6** sites (the three D-3 suites, `ms-setup-regression-pins:29–30`, `observation-conformance:81–82` and `protocol-pc-transfer-advance-conformance:57–58`). Three of each set are inside the D-3 protected suites. So the B1 N-1 integrity change (v0.4 §2 item 3) cannot avoid touching D-3 pin sets (OSQ-6).
- **K2, the shared-context assumption.** v0.3 §8, v0.4 §1 and RED v0.3 N-1 assume G2 widens the shared `TransactionContextSchema`. In code, the four D-3/legacy binders and the operator ledger `.pick` that context. Widening it makes them bind GM-pair transactions, contrary to their "refuses without a read" docstrings. A refinement on `ResolutionRequestSchema` would make their `.pick` throw at import under zod 4.6.5 (P1–P3), and v0.6 §3 item (2) names "any picked request schemas" as a consumer.
- **K3, evaluator-policy identity.** A10 requires it in the sealed INITIAL identities and in the strict variants. A4 and A11 exclude any extra INITIAL member (OSQ-4).
- **K4, historical reach (code gap, not a source conflict).** v0.6 §3 requires exclusivity on "retrospective integrity and replay". Replay skips `check` (`campaign-core.ts:440`, `:605–610`), and `verifyHistorical` has no Temporal transaction hook (`owners/admission.ts:537–553`). Today the player-only context is defended historically only by the open-time value-schema re-parse (`world/integrity.ts:218–222`). B1 must add a historical hook, and that changes `historyVerificationId`.
- **K5, line anchors.** These are minor. `TransactionContextSchema` is at `temporal.ts:483–487` (not L482). `continuationRequestViolation` is defined at `admission.ts:608–622`, with its doc at `:594–607`. The active-PC "new ≠ held" guard is at `:192–193`.
- **K6, no conflict on SI_SUBDAY_V1.** v0.6 §4.1's "requiring ratification" is resolved by A9 §2(3). The code's "no calibration constant" scan (`temporal-conformance:298–311`) agrees with A9's "not ... amendments to F-027": the factor table cannot sit in `TEMPORAL_SOURCES` without amending that test.
