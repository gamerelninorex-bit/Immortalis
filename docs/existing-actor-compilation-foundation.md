# Existing-Actor I-002 Pre-Binding Compilation & Ownership Boundary Foundation

Twenty-ninth bounded slice, built on the Canonical World Identity & Owner Foundation (`docs/canonical-world-foundation.md`: the I-002 Existence Contract, the one PC owner `pc_existence`, the Role Registry binding), the Named-Actor capability backbone (`docs/actor-capability-foundation.md`) and the I-002 PC capability receiving foundation (`docs/pc-capability-foundation.md`). An **already-existing, lawfully non-PC actor can now be compiled into the minimum I-002 Existence Contract before any operative `role.player_character` binding**, without that compilation being the player-control handover.

Governing lock: `spec/f027/spec-lock.json` (F-027 v1.0). No source pin, Runtime Contract snapshot, open gate or acceptance status changed.

## The controlling invariant

> Before the Role Registry binding commit, the existing actor's current lawful non-PC owner remains writable; the binding commit is the control/ownership cutover; compiling an existing actor into minimum I-002 form is not a blank-slate player-authorship pass. (Handover Contract, "Single Commit Point"; "Existing Actor → PC" 1, 3, 4; F-014A v3.3 interface note: "F-014A remains writable only while the entity is under lawful non-PC actor ownership.")

## Behavior, end to end

1. The Named-Actor owner establishes (and later closes) the actor's capability facts as before.
2. `releasePlayerCharacter` with a contract carrying `existing_actor_compilation` pins those facts and commits **one** fact at `pc/<id>/existence-contract`. The pinned facts are untouched.
3. The prior owner **stays writable**: further Named-Actor establishments and capability closes for that identity are admitted exactly as before (and the same holds for the Epistemic/KTI recipient checks that share `actorBoundaryViolation`).
4. `bindPlayerCharacter` for that identity, and a raw first-`ACTIVATION` binding, are rejected; so is every `ACCEPTED_GENERATION_HISTORY` PC capability basis. The binding slot stays NULL and no PC capability exists.
5. Everything above survives save → close → load, with the identical ownership result and, from any durable cut, convergence on the uninterrupted run.

The ordinary fresh PC is unchanged: no field, the Named-Actor owner is closed for its identity (also for an identity that had actor state before an unclassified contract), it binds on the explicit native basis, and its PC capability path is the twenty-eighth slice's. A fresh/arbitrary PC cannot gain the exception: the classification needs pins to its own committed Named-Actor state, a committed contract can neither gain nor lose it (sealed canon), and every claim must be `SAFELY-INHERITED`.

## Construction decisions that are technical encodings, not new semantics

- **Presence of one optional field is the classification.** The `classification` literal exists so a tampered or third value fails strict parsing; it is not a new rule. Optionality keeps every existing contract's serialization unchanged.
- **`source_state` kinds.** The only authoritative already-existing non-PC actor state this repository holds is the Named-Actor owner's capability facts, so those two kinds are the accepted sources (an actor therefore needs at least one committed fact to be compiled). Widening it to another owner is a later, source-backed step.
- **All claims `SAFELY-INHERITED`.** This encodes "not a blank-slate player-authorship pass" / "compiler-owned inference" (Handover Contract, Existing Actor → PC 4 and the Confirmation Surface). It does not decide what the player may later author after the binding commit.
- **Version pins are exact.** The sources are sealed (create-only), so an exact pin loses nothing; a pin to another version fails closed.
- **No `DEFERRED` / `ACTIVE-LIMITED` field.** I-002 v2.4 makes I-002 the owner of the binding-mode classification, emitted in the Generation Hand-Off: **`DEFERRED` only when an accepted or already-established activation, readiness or awakening condition exists; otherwise `ACTIVE-LIMITED`**; no score, timer, scheduler or third classification. None of this slice's ownership semantics depends on a mode (the cutover is the binding commit under every mode), the repository has no representation of a readiness condition, and a field with that rule would have to invent one. So the rule is **preserved by not being re-stated or weakened**: no mode field exists, the compilation schema is strict (a `binding_mode`, condition, score or timer is rejected), and nothing here classifies, defaults or emits a mode. Emitting it with the Generation Hand-Off remains for the slice that implements that Hand-Off. If Blue reads this seam as _material_ to the compilation, that is an alternative to decide, not a gap this slice papered over.
- **Rejection codes.** `REFERENCE_INVALID` for a binding/receipt over a compilation and for a bad source or claim (the existing reference/ownership vocabulary); strict-shape failures remain `VALUE_INVALID`.

## Not implemented (fail closed; none resolves an open gate)

The Existing-Actor → PC Role Registry handover transition itself (the binding schema still represents only the first `ACTIVATION`); actor-capability → PC-capability carry-forward; unresolved inherited capability (`UNRESOLVED` stays unrepresented); world-prior or Causal Draw PC capability; PC → non-PC handover; replacement/deactivation/fork/succession; Intrinsic Amendment Events; broad PC generation, cognition, personality or lifecycle; `BROADCAST_EXPOSURE`; generic IM-01; PF-6/F-028; provider, database or deployment work; a new simulation owner, generic handover ledger, scheduler or second persistence path. The existing-actor Confirmation Surface (displaying the handover packet and requiring its acceptance before the binding commit) belongs to the binding slice: this slice records the Generation Hand-Off release verbatim, exactly as for a generated PC, and the compilation cannot be bound.

## Residuals

- The compilation is verified for identity, ownership and provenance only. Whether it _sufficiently_ preserves the existing entity is the compiler's authored judgment (no source supplies a sufficiency rule).
- `actorBoundaryViolation` is shared, so an existing-actor compilation also leaves the identity a lawful Epistemic/KTI recipient until binding, consistently with the invariant.
- `verifyCanonicalIntegrity` still lists all facts once per open (diagnostic path, CAL-06).
