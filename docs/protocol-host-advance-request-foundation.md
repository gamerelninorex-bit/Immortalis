# Host-Requested, Independently Confirmed Active-PC Target-Only OOC Time Advance Foundation

One bounded, **mechanism-only**, host-neutral interface by which a compatible, locally configured chat/agent host can **request** that the operator consider an out-of-character advance of canonical time for the active PC — and by which that request becomes a time advance **only** through the already-shipped, separate, fresh confirmation on the trusted local operator console and the existing `pc-target-advance` command, with the operator supplying the **exact target** themselves. The request is an administrative precursor, **not** an in-world wait, a natural duration, an automatic world clock or player knowledge.

## The one loop

```text
host (AI chat client)                operator's console (a different process, a different channel)
─────────────────────                ───────────────────────────────────────────────────────────
request_active_pc_target_advance ──► (a non-canonical ASK is left in the owner-only retained state)
   "A request was left. No time has
    advanced; no target is named."
                                     immortalis-advance-request-answer --target-unit <u> --target-value <n>
                                       re-proves the ask against canon (bound host, character, CURRENT basis, ask identity),
                                       then runs the EXISTING pcTargetAdvance with the target THE OPERATOR typed:
                                       states the exact choice, draws a FRESH nonce, reads the very next line;
                                       only "pc-target-advance <nonce>" typed THEN confirms (subject-bound, one use);
                                       the retained intent and a fresh transaction identity come first, then
                                       advanceActivePcToTarget → TemporalCoordinator.advance (F-014B (T0,T1] boundaries);
                                       a registered GIP sunset provider alone writes `active` → `expired` at its own sunset
read_current_observation_glance ──►  (the EXISTING, separately authenticated, read-only player-view server)
   only what an independent Epistemic observation already earned, or the one opaque refusal
```

## The host's request (the host supplies no identity, time, target, basis, source or authority)

1. **Admission and lifecycle** are exactly the read and observation-request servers' (JSON-RPC 2.0 only; request identities strings or integers; `initialize` then `notifications/initialized` before any tool is listed or called; a closed one-tool surface). A message that fails admission never reaches the trusted request: the package and the retained state are not opened.
2. The tool takes **no arguments**. **Any** argument at all — a target, a duration, a condition, a "confirmed", a copied "yes", a challenge, a role, a permission, a character, a basis, a transaction identity, an actor order or an outcome — is an over-claim: the call is refused **before the package or the retained state is touched** and nothing the host named is ever carried.
3. The invoking operating-system user must own the campaign package (closed to everyone else) and the owner-only retained-state directory (`verifyLocalOperator`). This distinguishes **OS-user verification** from broad real-human authentication: it identifies **no person and no remote login**.
4. The host must be the one the operator bound _to ask for a time advance_, holding the secret of that binding. A matching secret **confers no role and no permission and is not authorization to act**: it entitles the host to leave a request for the operator to consider. It is **independent** of the Glance-reader credential, the AI-referee credential and the observation-request credential: none of them opens anything here, and this one opens nothing there.
5. The campaign opens through the engine's owner-verified re-open under its single-writer lock; a writer already active, an uncommitted journal tail, a stray file, a stale lock (never reclaimed here), an Epistemic integrity violation or an I/O error fails closed; nothing is repaired or altered.
6. The **authorized player view and the canonical active-PC binding must agree** (the same `releaseProblems` / `bindingProblems` proofs the observation command and the read make). The character is the one **canon** proves; the host names none.
7. Only the committed canonical time is read; an unestablished basis is refused. **No Instrument, Temporal object, boundary, custody, scene, observation or packet is consulted to decide anything**, so the request cannot depend on, or reveal, any hidden world state, and it states no expectation of what the advance would do.
8. The non-canonical ask is left **while the campaign's single-writer lock is held**: `{campaign, operator uid, host identity, proved character, canonical basis, random identity}`, created exclusively as its own file `request-<id>.json`. It states no target, choice, confirmation, verdict, world fact or time. **Custody** is the identity-bound custody PR #70's H-1 repair established, applied from the start: because every ask is its own file named by its own random 128-bit identity, removing `request-X.json` can remove ask X and **nothing else**, however a cleanup is interleaved with a replacement in any process; a re-asked ask is a new identity, so a late or duplicate cleanup of the first cannot reach the second. A repeated request for the same character at the same basis is the same ask, returned and not multiplied; asks for another basis or character are stale and are each removed **by their own identity**. Should duplicates of one ask ever coexist, the operator serves the lowest identity once and settles them together, each by its own name. A crash can leave only an inert `.tmp` name, never a half-written ask.
9. The host is told only that a request was left, in fixed words (no time has advanced, nothing is decided, no target is named, the player may decline). Every failure — an unbound host, a wrong, foreign or reused (or read-, observation-request- or referee-credential) secret, another campaign or operating-system user, a mismatched character, a writer that is active, an unreconciled package, an unestablished basis and every over-claiming argument — is the same one opaque `TARGET_ADVANCE_REQUEST_UNAVAILABLE` refusal, byte for byte and with the same error flag.

## The operator's answer (the player's choice and the target are made here, if at all)

- Run on the operator's own console by the operator: `immortalis-advance-request-answer --campaign <dir> --campaign-id <id> --target-unit <unit> --target-value <n> [--operator-dir <dir>] [--request-wait <s>] [--reclaim-stale-lock]`. The target is an **exact `CanonicalTimeSchema` value the operator types** (not a duration or a date), validated by the existing command, exactly as for `immortalis-operator pc-target-advance`. The command names no character, role, permission, confirmation or transaction; the character is the one the request carries and canon re-proves.
- It re-proves the ask: the file is a valid ask of this campaign and operator; the host is still bound _for that character_; the player view still proves; and the current canonical basis **equals the basis the ask was made at** — checked once through the read proof and **again inside the very session that will be shown the choice**. A stale or no-longer-bound ask is **discarded, by its own identity,** and the operator is asked nothing; a campaign that cannot be proved right now (a writer, an unreconciled package) **keeps** the ask and reports it.
- It then says plainly _"A HOST HAS ASKED THAT YOU CONSIDER ADVANCING THE WORLD'S TIME. That is only a request: it names no target, it is not your choice, it confirms nothing, and no time has advanced."_ and runs the existing `pcTargetAdvance`, which states the exact choice, draws a **fresh** challenge **after** the request exists, and accepts only the verb and challenge typed back on the **very next line**. A recorded or pre-typed "yes", a free-text line, an empty line, end of input or a stale phrase declines. The confirmation is a module-private, subject-bound, one-time token. **This slice never builds, passes or receives one.**
- What follows is the existing, unchanged owner chain. The command retains the confirmed intent **before** the gateway is invoked, with its own newly minted, immutable transaction identity; the gateway admits only a character whose World-State custody is currently valid and stationary (an original `ACTIVATION` or a separately lawful handover basis) with no held continuation; the Temporal kernel enforces F-014B (T0,T1] registered boundaries, stop/hold/interrupt and result provenance; a registered GIP expiry provider alone writes an Instrument's `active` → `expired` at its own sunset, and only if the confirmed target reaches it. Nothing here authors a stage, a GIP status or a verdict.
- Result meanings are the existing ones: `PC_TARGET_ADVANCE_COMMITTED` is a **transaction status only** (not target attainment, expiry or PC knowledge); `UNAVAILABLE` refuses opaquely; `PC_TARGET_ADVANCE_OUTCOME_UNKNOWN` demands reconciliation by the original identity (`immortalis-operator reconcile`), and the ask is **kept** until then — it is never reported as "no effect".
- The ask is consumed (the identities the operator classified, and no newer ask) once the choice is settled (committed, declined, or a definite refusal). It is **kept** where the choice was not settled — an unknown outcome, an unreconciled or stale retained choice, a target the command refused as invalid, or a session that could not open — so the operator runs the same command again. A crash after the commit but before the ask is cleared converges on the next answer **without a new choice**: the committed advance moved the basis, so the leftover ask is stale and discarded, and the operator is asked nothing.

## Boundaries

1. **Zero canonical mutations by a request.** A request writes no canonical byte: not an intent, a target, a transaction, a GIP write or a Temporal time. The package is byte-identical before and after any number of valid or over-claiming requests; the only file written is the ask in the operator's retained state.
2. **No host or model confirmation, and no host target.** The ask carries and accepts no confirmation and no target. `advance-request.ts` and its siblings on the host's side cannot import, name or call the confirmation, command, session, Temporal, GIP, gateway or terminal surfaces (a static check); `advance-request-answer.ts` only `say`s to the terminal, reaches the choice only through the unchanged `pcTargetAdvance`, and passes it only the operator's own target parameter.
3. **Transport separation.** `read_current_observation_glance` is neither converted into a command nor given a request authority; the read server and the observation-request server list their own tools and a call to this tool there is `unknown tool`, and conversely. The four credentials (read, observation-request, time-advance-request, referee) are four separate spaces. `role.player` / `permission.player_choice.commit` and the protocol operation names are named nowhere in the slice: only the independently confirmed operator-side choice attests them, inside the unchanged command.
4. **One refusal; no hidden-reason leak.** The request acknowledgement is the same whatever the world holds; a time advance reveals no GIP, custody or world word to the host, and the existing read is the existing opaque refusal. A time change never creates an Epistemic observation, a packet or player knowledge.
5. **No long-lived secret in a prompt or log.** The host's secret travels only as a file _path_ (an owner-only regular file; a symbolic link, another owner's file or one anyone else can touch is refused), is never an argument, an environment value or an output, and the binding keeps only its SHA-256 digest.
6. **Isolation.** Two campaigns with equal-looking identities share no ask, binding, secret or context.

## Using it

```text
# the operator, once the character is authored, placed, and canonical time is established (existing commands):
immortalis-operator author-character … ; immortalis-operator establish-character-locus …

# separate trusted bind actions (none names a character, role or permission; each proves the view against canon and writes an owner-only secret file):
immortalis-advance-request-bind --campaign <dir> --campaign-id <id> --host-id <host> [--operator-dir <dir>]    # may ASK for a time advance
immortalis-player-view-bind     --campaign <dir> --campaign-id <id> --host-id <host> [--operator-dir <dir>]    # may READ (PR #69)

# in the host's MCP configuration (the bind action prints the line; the secret itself is never printed):
immortalis-advance-request --campaign <dir> --campaign-id <id> --operator-dir <dir> --host-id <host> --secret-file <path>

# on the operator's own console, when the host has asked (--request-wait waits for one to arrive); the operator names the exact target:
immortalis-advance-request-answer --campaign <dir> --campaign-id <id> --target-unit <unit> --target-value <n> [--request-wait <seconds>]
```

## Not implemented (fail closed, not guessed)

In-world waiting or action cost; a free-text or conversational intent classifier for "let time pass"; automatic or recurring time advance; a duration, condition or calendar target; GIP authoring or policy changes; any NPC cognition or actor order; original-PC movement or relocation; remote human login or any claim that OS-owner verification identifies a person on the Internet; a non-model-controlled confirmation channel other than the operator's console (an anything-able-to-write-to-the-console is-the-operator limit, unchanged); an always-on host or request notification (the operator runs the answer command, optionally waiting for a request); host-visible request status or progress; revocation or rotation of a host binding other than the operator removing it from the retained-state directory; any model, provider, network, paid API or credential; any new owner, facet, canonical field, migration, IA/V promotion or F-028/PF-6 change. This slice alone does not satisfy First Playable: it closes the host-request → separate operator target and authorization → committed Temporal transaction → GIP's own owner result chain for one OOC target-only advance, and nothing more.

Each request and each answer briefly takes and releases the package's single-writer lock (the engine has no read-only open, and none is added). A package whose lock is held by another process reads as the opaque refusal for that moment (the host may simply ask again) or, on the operator's side, as an unavailable-but-kept ask; a request killed mid-flight can leave a lock that only the operator's explicit `--reclaim-stale-lock` takes over.
