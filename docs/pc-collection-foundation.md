## The chain (the minimum proof)

player confirms one exact attempt → PC-side commitment-of-record + PC-owned Production request → `role.gm` physical-reach judgment → Population individual occupancy → Production's derived work record + extraction (cycles, causal duration and the earned boundary DERIVED) → the PC's own, separately confirmed time passage through the existing Temporal → Production Source Delta → World-State delivery → Production Reserve inflow chain → the source drops once, the Reserve rises once → a separately confirmed second attempt meets the real remaining source.

`tests/integration/pc-collection-foundation.test.ts` is the witness: collect 3 from a source of 5 → source 2, Reserve 3; a separately confirmed second attempt for 3 is refused by Production's admission against the real remaining 2 (the registration is released by lawful denial; nothing moves).

## What the caller can and cannot say

A trusted server-side context (`bindTrustedConfirmedPcCollectionContext`) carries the exact confirmed choice (PC, per-act identity, source, Reserve, amount, `role.player` authored authority), the PC's established mechanism, Production's Capability / Access basis and the publication material. A value a host fabricated is not a context. Four host operations (`commit_confirmed_pc_collection`, `get_pc_collection_reach_task`, `submit_pc_collection_reach`, `start_confirmed_pc_collection`) accept a strict body of the operation name (plus, for the one judgment, the untrusted reading). There is no field for a campaign, PC, act, source, amount, destination, mechanism, confirmation, role, permission, boundary, duration, identity, rule, provenance, verdict or result. Every refusal is the same refusal; the only things returned are three minimum statuses and, for the one read, the bounded task. Time passes only through the existing separately confirmed active-PC target advance, whose fresh advance now asks the engine's single rule (`pcCollectionCrossingClear`) whether the PC's own in-flight collection is positively recognised and the crossing positively free of any other due boundary.

## Derivations, never declarations

- **Cycles** = the amount (serial, one unit per cycle). **Causal duration** = cycles × τ. **Earned completion** = start + causal duration. No caller supplies a requested horizon, a rate, a duration or a boundary; the extraction's declared start and boundary must equal the derived ones or admission refuses.
- **τ is stated by the PC's own authored content, or there is no exact completion.** The mechanism's actuator words, traversal words and cycle words are each a verbatim quotation of a cited accepted claim of the PC's released Existence Contract, and the cycle words contain τ's exact numeral (as a whole number) and its canonical time unit. A caller can name no number the content does not state. This is a **textual** grounding: it proves the authored words say exactly this number in this unit, not that the words mean "one handling cycle" (no installed rule can judge that), and the canonical unit must literally appear in the authored claim.
- **The F-014B §11 determination is derived, never authored.** §11's context-banded floor governs a consequential _interaction_ (actor presence, a co-present scene, conversation). The closed class has no counterpart actor, so the engine records `NOT_APPLICABLE_SOLITARY_DIRECT_HANDLING` in the work record; no source supplies a numeric band, so a caller could only invent a minimum, and none is representable. **This reading of §11 is PROVISIONAL and needs ratification.**
- **Reach verdict** = REACHABLE iff the path is open, or closed and the mechanism is able to pass. A closed path requires a decided, mechanism-anchored reading. Every ground must be a verbatim quotation of wording the task delivered (`MIN_GROUND_LENGTH`).
- **Occupancy interval** = exactly the interval the commitment and the mechanism determine.
- **Source/Reserve outcomes** are never written by the collection path: the existing chain computes them.
- Admission (IM-11) re-derives every fact from committed state; load verification (`verifyPcCollectionIntegrity`, code `PC_COLLECTION_STATE`) applies the SAME rule to the facts as they stood before each write, so a history built outside admission cannot say what the premises did not.

## The player's decision: the operator bridge (P0)

The only non-fixture ingress to `bindTrustedConfirmedPcCollectionContext` is the **operator's own fresh console confirmation** — the same existing player-confirmation authority the relocation and the time-advance choices use (`requestOperatorConfirmation` / `consumeConfirmation`: a one-time token bound to the verb and to the exact subject shown, accepted only if the operator types back the challenge printed after the subject). `collect(ctx, input)` (`packages/operator/src/commands.ts`):

1. takes intent only — the source, the Reserve, the exact amount, and which established mechanism and Production basis the attempt rests on; a strict body with no field for an identity, authority, boundary, duration, verdict or result;
2. reads current canon and refuses, **before the console is asked**, an attempt naming a source, Reserve or mechanism canon does not hold (an invented action is never offered);
3. states the exact attempt and obtains the operator's own confirmation of exactly it (`collect <challenge>`);
4. mints the immutable act identity (`operator-act-<uid>`) **before the first canonical write** and retains the confirmed intent durably in the operator ledger (`COLLECTION` intents, one per act identity);
5. only then binds a fresh trusted context and commits the PC-side commitment-of-record and the PC-owned request. It reads no reach, starts no work and advances no time.

`collectContinue(ctx)` takes no input and asks nothing: it acts only on a retained, operator-confirmed attempt, takes the `role.gm` reading from the injected `reachHost`, and starts Production's work; the PC's time passes only through the operator's separate, second `pc-target-advance` choice. `reconcile` re-presents a retained attempt by its original act identity (a crash after retention, before canon, is reconciled — never replaced). What is **not** claimed: that a human typed the line (anything able to write to the console is the operator, as for every operator command), authentication of any remote client, or a CLI/MCP subcommand for these two commands.

## Where the exact cycle comes from (B-1 / B-2) and the §11 floor (C) — BLUE disposition

- **B-1 (the governed route).** The exact-timed class needs a genuinely authored, accepted PC claim that supports the one-unit handling cycle in the canonical time basis, obtained **before** the act is confirmed. The mechanism carrier follows such a claim by locator; without it the exact positive is **WITHHELD** (a mechanism that quotes no cycle cannot be established, and no default such as τ=7 exists). The numeral-plus-unit check is a **lexical guard, not a semantic adjudication**: it does not prove the quoted words causally mean the mechanical per-unit cycle. An I-002 §22 Invocation Branch can close an actually-unresolved operative detail only BEFORE its consequence; none exists in this class's path, so none is invented or used here (no branch is created and no retroactive optimisation is possible). Ordinary PCs are not required to specify numeric rates.
- **B-2 (separately deferred; NOT a substitute).** A PC with only qualitative or banded handling capability cannot be consumed by this exact serial-unit boundary, Temporal registration and all-at-boundary settlement. A different bounded completion/scheduling design would be needed; nothing here invents a numeric rate or assumes a completion at a chosen advance horizon, and no broader action class is marked implemented.
- **C (proposed, not adopted).** The `NOT_APPLICABLE_SOLITARY_DIRECT_HANDLING` determination is an explicitly PROVISIONAL reading; the absence of a counterpart actor is not an adopted exemption of F-014B §11. Whether solitary same-form gathering is a "materially consequential interaction" must be adopted explicitly, with any applicable floor derived from authorised scene/context evidence. Until that determination is authoritative, **exact completion is not promoted to accepted design**; no numeric band, zero-duration exception or caller-declared floor is representable.

## D-1 — PC Collection Voluntary Cessation (PROVISIONAL, proposed, NOT adopted)

A separately confirmed PC choice may **request cessation of the SAME in-flight collection identity**. It is a new action cause, not a claim that earlier work never occurred, not a new source status and not an arbitrary Production cancellation. The chain, each step an owner's own admission-re-derived write:

1. **PC-side request** (`pc_collection_cessation`, `PcCollectionAdapter.cease`): admitted only for a started, uncredited, unterminated collection of the active PC, under `role.player` + `permission.player_choice.commit`, pinned to the exact committed commitment and work versions and to the current binding, custody and occupancy versions, at the canonical time read at the request, **strictly before the earned boundary**, with **no unresolved earlier boundary** (an index entry at or before the canonical time, or a held unresolved dependent, refuses) and with the work's pending boundary engaged.
2. **Production's terminal disposition** (`production_pc_collection_termination`, `PcCollectionAdapter.terminate`): derived from the committed request, the work record and the canonical time (the stop time is the canonical time at which Production resolves it, never earlier than the request, so a request is never retroactive and work that continued after it is elapsed progress). One atomic group records it and releases the key's claim on the source; the source, the Reserve and every Source Delta are not written (no write of them is representable, and the integrity verifier requires a terminated collection to have no delta, delivery or credit).
3. **Temporal's retirement** (`TemporalCoordinator.retireTerminatedObject`, admitted by `pcCollectionRetirementGroupCheck`): only after Production's termination, the work's pending earned boundary is retired (superseded, never resolved) and removed from the boundary index; canonical time, every other object and every other index entry are untouched. The kernel knows no owner's state: it is given an object and the one fact that terminated its work, and admission re-derives that this pair is lawful.
4. **Population's release** (`population_pc_occupancy` → `RELEASED_TERMINATED`, `releaseOccupancyTerminated`): the SAME PC's individual interval, exactly once, only after steps 2 and 3. **A second lawful action becomes possible only after this complete release**; between the steps the PC stays occupied and the hold names the stage (`CESSATION_REQUESTED`, `TERMINATED_AWAITING_RELEASE`), time cannot pass over a PC that has asked to stop until Production has resolved it, and re-presenting the same stop finishes the remaining steps by identity (RC-16).

Distinct outcomes stay distinct: a **stopped process** (`RELEASED_TERMINATED`, a termination record) is not **already-closed output** (a closed collection is never stoppable and the one refusal is returned) and not a **pre-start denial** (`RELEASED_DENIED`, work never admitted). The earlier completed source/Reserve deltas stay canonical. The operator bridge is `cease(ctx)` (no operator input at all): it offers the stop only for the active PC's retained, positively in-flight collection (the console is not asked otherwise), obtains the operator's own fresh, SEPARATE confirmation (`cease <challenge>`; a confirmation of the start is not one), retains a `COLLECTION_CESSATION` intent under the retained act's identity, and `reconcile` finishes an unfinished stop by that identity.

**What D-1 deliberately is NOT.** It is not F-014B §10 and not clause D-2: it never evaluates, infers or waives actionable knowledge, an Event/Observation/Report/Knowledge time or a standing policy. It is lawful only at a canonical time that already includes resolved history and holds no unresolved earlier boundary, so it never forces its way across one; when a foreign boundary still lies ahead of the stop, the stop is the PC's own safe act at the present instant. A **D-2** stop/continue composition — stopping at an actionable-knowledge boundary with a durable continuation identity — needs real Epistemic receipt and standing-contingency carriers the repository does not have, and is **DEPENDENCY-BLOCKED, not permission for a pretend event**. D-1 invents no cancellation result, partial credit, source status or rate, and adopts no exemption.

### Response to the BLUE review of `afda22a` (R-1 … R-5)

The mechanisms above stand as reviewed. The points below pin what each rule does and does not claim. They are the builder's statements about newly authorized, unreviewed rules, not ratified text.

**The delegated author rule (R-3).** Under the delegation the builder takes the minimum rule needed and no more: _for a world whose every committed profile is strictly `ORIGINAL`, the operator-owner who runs the campaign is the author of that domain, and may state, once and by an explicit typed confirmation, its starting chronology, its closed-domain declaration, the per-source "unencumbered" grounds, an EMPTY Reserve and a physical extraction basis._ Operating-system file ownership is **only** the ingress filter (it keeps a non-author process from writing the file); it is **not** the authority. The authority is the delegation, and it is scoped by canon: `initialize-time`, `declare-closed-setting` and `prepare-collection` refuse (UNAVAILABLE, nothing asked, nothing written) unless the campaign holds at least one world and every committed world's `reference_causal_basis.mode` is `ORIGINAL` (`onlyOriginalWorlds`), and the engine refuses a closure over a non-original world independently of the operator (`sceneClosureViolation`). A reference-setting domain has no such author; its rights, chronology and closure would need an authority this delegation does not give.

- **Conflicting owner or source claims.** The author's "unencumbered" ground is a statement, not a lock: it never overwrites or hides a contrary fact. A claim open on the source's account, or any other Temporal boundary due at or before the earned completion, defeats enrollment at every start (`foreignEngagementViolation`; an incomparable unit fails closed); a source right over a source that is not at the declared locus is refused at admission. Tests: `tests/unit/pc-collection-engagement.test.ts`, the enrollment-defeated and foreign-process cases in the enforcement/cessation suites.
- **Why the chronology words need not be a canonical owner fact.** The coordinate (unit and value) is the canonical fact (the Temporal state); the author's words are the author's gloss and are bound to it by a digest in the publication identity (`initialize-time` identity = hash of campaign, time and statement), so a different statement or time is a different act, an identical one replays, and none can overwrite. Nothing downstream reads the words; only the coordinate is consumed. The smallest correction, if BLUE wants the words themselves canonical, is one provenance fact carrying the statement beside the Temporal origin; **it is not built** and none is silently assumed.
- **No Economy rights owner** is created, and no source ownership beyond the author's stated per-source ground is modelled (blocker 18).

**Closed-scenario semantics (R-1).** A closure is credible only inside the author's original domain and only against what the owners record. The covered set (Population ledgers attached to the locus, actors coupled to it, PCs whose stationary locus it is, excluding the acting PC's own handover coupling) is derived by World-State, re-derived at every use, and the declaration is STALE the moment any of it differs. No universal completeness is claimed: an actor, process or engagement that **no owner has recorded** is invisible to it (blocker 15). The independently falsifying contrary fact is a lawful canonical actor coupled to the locus after the declaration: it stales the closure, an act not yet started is withheld, an act already running is INVALIDATED and is never silently completed or credited (`tests/integration/pc-collection-closure-falsifiers.test.ts`).

**Workforce carriers (R-2).** Population's primary carrier of who labours where is the **ledger**; a unit's residence, presence and burden live only in the ledger's unit schema, and `deriveWorkforceAccounting` scans exactly that carrier by residence-at-locality, presence **or** burden (`tests/conformance/workforce-carriers-conformance.test.ts` enumerates Population's kinds and fails if another carrier appears unclassified). Cohorts, closes and barriers are derived over ledgers or belong to the unimplemented §28 aggregate and are neither consulted nor claimed. A unit that counts the PC makes the representation INCLUDED; UNKNOWN follows a stale or missing scope; both keep withholding the act. A unit resident and present elsewhere but burdened at the locality is accounted. No §28 arithmetic.

**Standing and time (R-4).** Source-backed exclusion is the enrollment engagement check above plus the live closure/scope currency check; adversarial tests: a coupled actor mid-work (INVALIDATED), a late ledger carrier (scope STALE, representation UNKNOWN), a foreign claim or process (enrollment defeated), each leaving the independent cause intact. The **exact deficiency** is this: no ratified owner or terminal rule says what becomes of an in-flight collection whose standing, binding or custody is lost in the middle of work. Nothing here terminates or releases it automatically, and nothing suppresses a competing cause. The PC's own separately confirmed `cease` is the only release and is lawful **before** an unresolved boundary; once the clock reaches the work's boundary while it is INVALIDATED, the kernel's `CONTINUATION_HELD` holds the **whole campaign** clock and `cease` is refused (`tests/integration/pc-collection-v03.test.ts`, "mid-work loss of a premise"). That state is a genuine deadlock that only a ratified terminal rule can resolve. No global write fence is added.

**Authentic play (R-5).** No real player, real GM or real next decision has occurred. Every referee reading and every console line in the repository's tests is scripted: mechanism evidence only. The cloud host has no phone or remote terminal ingress. **What it never does.** It never resumes, advances, consumes or cancels the held continuation: only the player's later, separately confirmed held resume (the existing active-PC or NULL-PC gateway, which carries the sealed original request verbatim) consumes it. No condition is removed, superseded, retargeted or invented. It creates no Event, Observation, Report or notice and no player-facing return differs by reason class, cause, earlier time or horizon. It is never evaluated before B, never in response to a horizon and never by player or operator choice: the settlement takes no input; an operator or host may only _present_ it (`settle-collection-lapse`, and quietly first inside `pc-target-resume`), and every owner path re-proves it. While a lapse is sealed and its release is incomplete the active-PC crossing gate refuses uniformly. Re-presenting it after a lost reply or a crash at any step finishes it, under identities derived from the PC and act, without a duplicate write.

**RED construction constraints, as built.**

- **C-1 (crossing-transaction causality), cause-specific.** The decisive premise is judged against the crossing transaction's admissible basis. The engine identifies the owner facts that _changed_ relative to what the act pinned or was judged against (`changedPremiseKeys`: a version-equality that no longer holds — binding, custody, mechanism, reach, the scene's pinned world/locus/closure/ledgers — a path-facts digest, the source's locus, a ledger/actor/PC the closure did not cover, Population's determination), each of which is by itself a sufficient cause. A lapse is derivable (and a loaded lapse verifies) only if at least one changed key is an _admissible cause_: committed **before** the crossing transaction opened, or declared as a dependency by the extraction's own temporal object (v1.2(c)). A cause committed at or after the opening and not so declared (a post-stop write, an undeclared same-instant sibling) is not admissible; and an **unrelated later owner write never erases an admissible cause** (it is not a changed premise key at all). Load verification bounds the window at the lapse itself and never refuses a campaign for what moved afterwards. Residual, stated plainly: the engine has no point-in-time read of an ADVANCING fact, so a fact whose _current_ version post-dates the opening hides its earlier versions and cannot be admitted by itself; another admissible cause still suffices. In this class the extraction declares only its own chain (extraction, delta, delivery), so no premise-owner write can be a declared dependency; the declared-dependency branch is built, tested pure, and vacuous in practice.
- **C-2 (lineage enforced in the owners).** Production's derivation and Temporal's retirement each re-prove the lineage by `acceptableHeldLineage`, the rule both held-resume gateways share (a target-only, condition-free request, back to its initial transaction, stopped `DEPENDENCY_UNRESOLVED` with unfinished dependents). A presenter-only guard would not suffice and is not what is built.
- **C-3 (replay).** Load verification re-judges the sealed record against its immutable pins (commitment, work, extraction, the sealed held transaction and its first stage), its plan data, its released claim, the absence of any Source Delta/delivery/credit and the order of its release. It does **not** re-derive the premise judgment from facts that moved afterwards.

**Binding independence, and its exact deficit.** The affected PC and act are identified **mechanically from the sealed held lineage and the Production work record it names** (`heldPcCollections`), never from the currently active binding, an operator-provided identity or a newly bound unrelated PC; the presenter takes no identity and reads no binding (a source conformance test pins this), and `pc-target-resume` and `null-resume` both present the settlement first. A canonical _end-to-end_ lost-binding witness cannot be produced in this build: the player-character binding is a SEALED single-slot fact (its transition is only ACTIVATION or the one EXISTING_ACTOR_HANDOVER, `prior_binding` and `replacement_binding` are null), so no owner transition exists that nulls or replaces an active binding after a collection started; a test commits a replacement at both expected versions and both are refused. The binding-independent derivation is therefore proved at the engine level against a fact view whose binding names another PC or none (the lapse derives for the held PC, reason `INCOMPATIBLE`; a stranger's lapse does not derive). Should a later owner rule add a binding transition, no change to the settlement is needed.

**Not claimed.** The operator's own `collect-finish` offers a finish only for work positively in flight, so a normal operator-driven collection whose premise is lost before the finish is refused (and may be stopped by `cease`); the held-at-B state arises when the premise is lost inside the crossing itself or when time is carried over the boundary by another lawful route. The operator's `pc-target-resume` can resume only a lineage that its own ledger holds. Raw conditional continuations, D-2, partial credit, a re-pin or restoration route, any cancellation or failure status, a general condition-supersession law and §28 remain absent. Exercised only by synthetic fixtures and scripted consoles; no real player or GM has run it.

## Mutual exclusion, re-entry and interruption (C5, C8)

- A PC with a movement that is **pending or in flight** (commitment-of-record, request, Logistics commitment, transfer, or a destination commit awaiting retirement) cannot register or start a collection; a PC with an OPEN occupancy cannot commit to a movement. One occupancy at a time. Once the PC's single leg has **settled** (World-State's destination commit exists and the transfer is retired) the PC is stationary at that destination — World-State's destination is the one authority for it, the origin custody record is immutable predecessor provenance, and a collection there is judged by the same rules; it cannot collect at the origin it left. - Time passage over the PC's own OPEN collection is refused unless the collection's object is engaged and is the only boundary due by the target. The F-014B §10 actionable-knowledge evaluator is **not implemented**, so the absence of an interruption cannot be established when other work is due: the crossing is refused (a declared `creates_epistemic_interruption: false` is not proof).
