# Initial Local Demand and Independently Authored Production Start Admission Foundation

> **OOC DEVELOPMENT / SCENARIO INSTRUMENTATION.** This is an out-of-character local console path that lets an operator author, confirm and commit, in a fresh, operator-confirmed, **pre-play** scenario that already holds a canonical time and **before any player character is bound**, **TWO separately authored opening acts**: (1) **ONE material demand** attributable to ONE already-committed Population Unit or Population-owned Cohort, and (2) **ONE bounded Production start** against ONE already-committed same-locality Reserve, with an explicit input/output transformation and an exact future completion boundary. It is **mechanism only**. It advances **no time**, registers no Temporal object, and says neither that the output exists nor that the demand is satisfied. It is not live Population need formation, not valuation, not a market or exchange, not a player or actor decision, not labour, not a rate or yield, not a stock, title, reservation or priority, and not true-world productivity.

Bounded implementation slice (`@immortalis/operator`: `establish-local-demand`), composed from the **already implemented** Economy owner operation `EconomyAdapter.issueDemand` and then the already implemented Production owner operation `ProductionAdapter.startOperation`. No `packages/contracts`, `packages/engine`, `packages/protocol` or `packages/testkit` module changed; there is no new Economy or Production operation, owner, facet, schema, key class, stage, status, lifecycle, persistent receipt format, status gate or general scheduler. The shipped binary registers no owner extension.

## The command

```
immortalis-operator establish-local-demand --campaign <dir> --campaign-id <id> --demand-file <file> [--operator-dir <dir>] [--reclaim-stale-lock]
```

The demand file is one strict JSON document with two distinct sections:

```
{ "format": "immortalis-initial-local-demand", "format_version": 1,
  "demand":     { "demand_envelope_id", "carrier", "demand_entry": { "output_class", "quantity" } },
  "production": { "request_key", "reserve_id", "transformation": { "input_quantity", "output_quantity", "output_class", "output_condition" }, "completion_at" } }
```

`demand` is exactly the unchanged `IssueDemandInput` and `production` exactly the unchanged `StartOperationInput` (`packages/contracts/src/economy.ts`, `production.ts`). Every object is strict and every field required, with nothing defaulted: the file can carry no owner, facet, version, pin, carrier basis, availability, allocation, claim, priority, stock, title, price, labour, rate, yield, duration, completion, output, access, satisfaction, publication label or "confirmed" claim (each is an unknown field and is refused). The one cross-section agreement is this path's own: the production act's `request_key` must be the Economy request the demand allocates to (`economy/request/request:<demand_envelope_id>`, derived by the Economy owner from the demand identity alone).

**The demand never grants the second act.** The `production` section is required, shown, and confirmed expressly. The demand is an economic claim only; Production alone verifies the request, the time, the Reserve and its claim availability. The stipulated input, output, condition and boundary are the operator's premises: nothing is inferred, estimated or derived, and the duration is not a field — only an exact future canonical-time boundary is.

The file is read once, from one open descriptor: a regular file (not a link) owned by the invoking OS user and writable by nobody else, of bounded size. What was read is what is shown, confirmed and committed; a file changed afterwards cannot change it.

## Sequence

1. **Read and check the file** (above). Nothing is asked of the console if it is refused.
2. **Open the existing package** for the local operator (the usual OS-user verification, the package lock, journal replay and canonical integrity). This command **never creates, adopts, repairs or clears** a package: a missing or foreign directory, or another campaign identity, is `SESSION_UNAVAILABLE`.
3. **Read the established locality from canon** (`establishedLocality`, shared with the earlier commands). None held → `LOCALITY_NOT_ESTABLISHED`; held but since advanced → `PRE_PLAY_CLOSED`.
4. **If both acts of this identity already committed** (a repeat, a lost reply, a restart): judge them on the immutable committed record. When each record is exactly the one write of this proposal, with the exact derived value and reads of — and dependencies on — exactly what it was made against, the canonical time still the sealed AS-OF-NOW basis, and every pinned fact still the one pinned, they are verified and reported **without asking again and without a write**. A record committed with other content, or whose fact is not held, or an operation committed without its demand, is `DEMAND_CONFLICT` / `OPERATION_CONFLICT`. A canonical time that has moved, a pinned Population, world or locus fact that has changed, a bound player character, or an operation, claim or Reserve that an owner has since resolved is `PRE_PLAY_CLOSED`, never "established". Replay is pre-play only.
5. **Pre-play and consistency refusals**, all before the console is asked and with no write: a bound player character → `PRE_PLAY_CLOSED`; **any other demand, request, realization, Production operation, claim or completion held in the campaign** → `DEMAND_CONFLICT` / `OPERATION_CONFLICT` (this path's own fail-closed condition, one initial local process per campaign; the sources fix no inter-process law and none is invented here); the demand key or the operation key already held by another identity → the same conflicts.
6. **Require the Population carrier**: the named ledger (and, for a Cohort carrier, the Cohort) committed at the established world and a locus of it, naming a Unit it holds or a Cohort of it. Otherwise `CARRIER_NOT_COMMITTED`. A **Cohort carries a demand only once Population has composed it with exact, non-empty membership** — the Economy owner's own rule, restated here only so the refusal is clear; composing it is Population's own ordinary close at a later canonical time. Economy copies none of Population's count, membership or identity.
7. **Require the existing canonical time** (`TIME_NOT_ESTABLISHED` otherwise — a missing prerequisite, never a success) and a declared completion boundary **strictly after it, in the same unit** (`HORIZON_NOT_AHEAD` otherwise). This command creates, chooses and advances no time; the demand is made AS-OF-NOW at the time the campaign holds.
8. **Require the Reserve**: committed by Production at its first version, **fresh** (nothing claimed, consumed or credited), and attached to exactly the carrier's world and locus (`RESERVE_NOT_COMMITTED` / `RESERVE_NOT_AT_LOCALITY`). Production's admission judges the claim against it again.
9. **Prove the owner path admits it** (dry run). The package's committed state (manifest, current state and journal — never its lock) is copied to a scratch directory, opened there through the engine's own owner-verified open, and the demand and then the start are run through the genuine owner operations on the copy; the copy is then removed and the campaign itself is read, never written. Anything the owners refuse (an output other than the one the request asked for, another unit, an input the Reserve cannot support, a boundary not after the start) is `INVALID_PROCESS` with the owner's code, and nothing is written.
10. **Confirm, once.** Both acts are shown, labelled apart (ACT 1 — MATERIAL DEMAND; ACT 2 — PRODUCTION START, "a SEPARATE act: the demand above does not grant it"), with the canonical time read and what the command does **not** do, authored text JSON-quoted so a control sequence cannot rewrite the console. The operator types `establish-local-demand <fresh challenge>` on the very next line; anything else, a stale or pre-typed line, another verb's phrase or end of input declines and nothing has been written. The confirmation is a one-time token bound to the verb and the exact subject (campaign, locality, process identity, pending acts, canonical time and both authored sections).
11. **Commit in dependency order** (`PROGRESS demand COMMITTED …`, then `PROGRESS start COMMITTED …`): the demand through `EconomyAdapter.issueDemand`, which creates the Demand Envelope **and its one Production Request atomically**; and only after that fact is committed the start through `ProductionAdapter.startOperation`, which creates the **IN_PROGRESS Production operation, its RC-06 claim and the Reserve's open-claim entry atomically**. The owners derive everything; the operator never writes through any raw `store.commit`.
12. **Verify on a fresh reopen.** The package is closed and reopened through the engine's owner-verified open; each new fact's key, owner/facet, version, typed value and committed provenance are compared with values **derived independently of the owner adapters** (the sealed `AS-OF-NOW` availability with "no supply for the request", the fixed one-demand-one-request allocation, the Tier A support basis, the claim, the Reserve holding exactly that claim), **every fact the campaign held before is compared with its pre-commit self** — the Reserve alone excepted, which may differ only by this operation's open claim, compared against its own before-value — and the fact count and revision are exactly the expected number greater. Only then is `LOCAL_DEMAND_READY` reported.

Statuses: `LOCAL_DEMAND_READY`, `LOCAL_DEMAND_INCOMPLETE`, `LOCAL_DEMAND_OUTCOME_UNKNOWN`, `LOCAL_DEMAND_REFUSED`, `LOCAL_DEMAND_VERIFICATION_FAILED`, `LOCALITY_NOT_ESTABLISHED`, `PRE_PLAY_CLOSED`, `TIME_NOT_ESTABLISHED`, `HORIZON_NOT_AHEAD`, `CARRIER_NOT_COMMITTED`, `RESERVE_NOT_COMMITTED`, `RESERVE_NOT_AT_LOCALITY`, `DEMAND_CONFLICT`, `OPERATION_CONFLICT`, `SESSION_UNAVAILABLE`, `DECLINED`, `INVALID_PROCESS`, `PROCESS_FILE_UNTRUSTED`, `PROCESS_FILE_UNREADABLE`. `LOCAL_DEMAND_READY` means exactly: both acts are committed under this identity, verify, and nothing earlier changed except the Reserve's open claim. A demand committed without its start is `LOCAL_DEMAND_INCOMPLETE` (a known refusal of the second act) or `LOCAL_DEMAND_OUTCOME_UNKNOWN` — **never** a success — until the same command is rerun to finish it. **An earlier, already-canonical demand is never silently rolled back or misreported.**

## Identity, convergence and fail-closed

The service authors only the technical publication identities and derives them from the exact authored content, never from a clock or a random value: `<id>` is a hash of the campaign identity, the demand and the production act, giving for each act `<name>` ∈ {`demand`, `start`} group `operator-initial-local-demand:<id>:<name>`, intent `operator-initial-local-demand-intent:<id>:<name>` and cause `operator-initial-local-demand-cause:<id>`. The demand and the start are therefore two separate publications with two distinct authorships and stable, distinct identities.

- **The same confirmed proposal always reaches the same identities.** A retry after a crash or a lost reply replays what committed (RC-16, by the store's own identity check) and finishes what did not, **resuming only the exact original durable request**; it never writes a second, altered or reordered demand, operation, claim or Reserve entry.
- **Any different content under the same demand, request or operation identity meets the committed key and is refused**; committed facts are never replaced. **An independently changed second act offered while the demand waits for its start is refused** (`DEMAND_CONFLICT`), never substituted; an operation another writer started under the waiting demand's request is a conflict, neither adopted nor replaced.
- **No retained state is added.** There is no new pin, receipt or ledger format: the committed record in the package is the only memory of what committed (the session still opens the existing owner-only retained-intent directory, unchanged).
- **Once pre-play ends, setup is closed**, replay included.

## Recovery

The package's own file lock and durable-write order are used unchanged. A kill leaves the lock; it is refused until the operator explicitly passes `--reclaim-stale-lock`, which the engine honours only for a provably dead holder. Tests interrupt before the first commit, between the Economy demand and the Production start, after the operation commit and before the reply (a lost acknowledgement), by a known refusal of each act, by a failed reopen after the close, by a real `SIGKILL` of the shipped binary at the console, after the demand and after the start, and by a failure before **and** after every mutating filesystem operation of the whole command; each converges on the uninterrupted campaign (equal head, state and journal hashes), with an operation never present without its demand and no second demand, operation, claim or Reserve entry.

## The disposable witness (tests only)

`tests/integration/initial-local-demand-foundation.test.ts` then registers the committed operation's Temporal object — a **disposable scenario step performed by the Temporal owner's own `registerObject`, not by this command and not a shipped producer** — and independently advances an authorized exact canonical time boundary through the **existing Temporal coordinator** with the genuine Production completion, World-State acceptance and Economy realization providers:

- before the declared boundary nothing is consumed, accepted or realized (a premature horizon engages nothing);
- at it, **Production** consumes the declared input exactly once and completes one durable; the **World-State custodian** accepts the SAME conserved reference as one durable entity of the demanded class and quantity at the demanded locus; and **Economy** alone writes realized access, once, at the operation's own declared boundary — all read back after save/reopen, with the originating demand and request byte-identical;
- the test asserts independently computed expectations, never the outcome as a source: nothing is credited because the scenario author asserted it;
- `tests/integration/initial-local-demand-recovery.test.ts` interrupts that phase too — a failure before and after every mutating filesystem operation of the whole due transaction, completion without acceptance, acceptance without Economy's stage, a duplicate delivery of the request — and each re-presentation lands on the identical campaign with exactly one Reserve debit, one output and one access;
- fabricated realizations, completions, accepted entities, rewritten demands or operations, and a hand-debited Reserve are refused by the owners, and the demand stays open.

**This proves only the existing deterministic owner chain plus the new admission seam; it does not prove live autonomous Population need formation, economic valuation, market exchange, player agency, actor cognition or true-world productivity calibration.** The live NPC interpretation and decision, naturally generated demand and production decisions, actual client / AI-host integration, and PC knowledge and consequential choice remain an **EXTERNAL PREREQUISITE MISSING** and are not claimed. The registration of the operation's Temporal object is likewise not performed by this command: no time-registration path is shipped here, and none is claimed.

## Security

The full proposal is shown only on the operator's own console and held only in the owner-verified package. It is not written to the retained-state directory, and no host-facing surface (referee, player-view, observe-request or advance-request MCP servers, the protocol package) imports or names this command: it is **explicitly unavailable during live in-character play** (a bound player character closes the path, replay included). **No MCP, phone or client demand, production or Economy creation tool is added.** No model, MCP client or command-line flag can attest the human confirmation. The module has no network, child-process, environment or global-state access; its dry run copies the package's committed state to a private scratch directory and removes it.
