# Diplomacy Externalized Claim / Dispute Core Backbone Foundation

Eighteenth bounded slice, built on the same commit, owner-registry, admission, persistence and recovery machinery as the Diplomacy External Recognition foundation (`docs/diplomacy-external-recognition-foundation.md`) and the earlier owner foundations. It adds the Diplomacy owner's second persistent fact: one externally communicated claim / dispute record. **Initial authored establishment only.**

Governing source (exact pins live in `spec/f027/spec-lock.json` and the owner registry): **WS-008 Diplomacy / Inter-Faction Relations v1.1** (frozen F-027 pin `2026-09-24T07:01:45.312Z`) §§2–3, §7 (Claim / Dispute), §§19–24, §29.3 (R-3 dependency registration and invalidation), §29.4 (`effect_on`) and §29.7, with **F-016 Phase 2C** (pin `2026-09-21T23:21:44.154Z`) and **F-017** (pin `2026-09-25T23:42:27.802Z`): lawful Actor / ACS / GIP authority precedes the externally communicated act, which precedes the Diplomacy record.

A Claim / Dispute record is one authored statement: _one or more diplomatic parties externally asserted, denied, protested, reserved, recognized or disputed a position concerning an underlying subject_. Diplomacy owns only the fact that the position was externally communicated. The underlying substantive claim stays with its authoritative owner. The record does **not** establish what any party privately believes or will later do, and no objective truth is inferred from an assertion, denial, protest, reservation, recognition or dispute.

**Not implemented (out of scope, unchanged):** Relation Edge, including derived reference arrays and any Recognition → Relation matching; dynamic party decision, motive or strategy; Actor / ACS autonomous response; GIP authority or domestic-incorporation procedure; Channel and message transport; Negotiation workflow; Diplomatic Instrument, Clause and Binding Entry formation; callable rights, guarantees, enforcement or security mechanisms; compliance or performance resolution; Framework formation or collective decision; any Epistemic receipt / access event (none is created, inferred or backfilled, and `BROADCAST_EXPOSURE` is never treated as individual receipt); dynamic `effect_on` receipt adjudication; any post-establishment mutation (status change, new or changed communicated position, remedy change, interpretation or adjudication update, effect resolution, dependency-driven re-resolution, conversion, merger, settlement, retirement or deletion); any timer, tick, scheduler, watcher or polling loop; and any RNG, seed, probability, chooser, prior or workaround for GitHub Issue #11 (untouched).

## Identity, keys, lifecycle and idempotence

- **Identity is `dispute_id` alone.** The key is `diplomacy/dispute/<dispute_id>`. The parties, the underlying subject, the status, the optional references and the position entries are **not** identity dimensions. The record is stored once: no copy per party, observer, population member, locus, clause or relation, and no all-pairs or all-disputes scan.
- **One slot per dispute.** A retry, a duplicate construction or a raw-store write reaches the same occupied slot, so no sibling record exists. Identical content under a different `dispute_id` is a distinct record; nothing is merged or deduplicated. The recognition and dispute key spaces are disjoint.
- **ADVANCING, initial establishment only.** WS-008 permits claim / dispute state to remain live, change, resolve and eventually compact or retire, so the kind is `ADVANCING`; this slice implements the first creation only. Diplomacy admission refuses every other change (`AMENDMENT_NOT_SUPPORTED`), and a second creation of an occupied key is refused by the store (`VERSION_CONFLICT`).
- **Retry converges, conflict fails closed.** Re-presenting the same intent is reconciled by identity (RC-16) to the original receipt. A different intent at an occupied `dispute_id` — equal or different content — and the same intent with changed content are refused; the committed dispute is never rewritten.
- **No scan, clock or RNG.** Establishing a baseline dispute reads nothing and writes only its own key; reading one is a direct keyed read; only the diagnostic load-time verifier lists facts, once per open.

## Interpretations recorded for review

1. **Array fields carry no source-undefined rule.** WS-008 defines no minimum cardinality, uniqueness or deduplication rule for `party_refs[]`, `communicated_position_entries[]` or `dependency_refs[]`. Each is a plain array carried exactly as authored: empty, repeated and unsorted arrays are accepted and no element is reordered or removed. Only the distinct `dependency_refs[]` keys are pinned (once each) at admission; the authored array is untouched.
2. **`communicated_position_entries[]` has no entry schema.** WS-008 defines none, so each entry is the repository's weakest canonical value representation (any canonical JSON value, `JsonValueSchema`), carried exactly as authored; no subfield is invented and no entry is parsed, normalised or interpreted.
3. **`status` and `requested_remedy_or_demand` are singular authored values with no source-undefined subtype.** WS-008 fixes `status` as required and singular, defines no closed literal set, and fixes the remedy as optional and singular; neither has a value subtype. Both use the weakest canonical representation that keeps them singular: any canonical JSON scalar (string, finite number, boolean, null) or canonical JSON object, carried exactly as authored. An array is multiplicity and is refused; no enum, no text-only type and no alias normalisation is imposed, and no lifecycle literal set is imposed on `status`.
4. **References are opaque, with the weakest identifier rule.** `party_refs[]` elements, `underlying_subject_ref`, `interpretation_issue_ref`, `instrument_or_clause_ref`, `adjudication_basis_ref` and `provenance_ref` use the repository's opaque `Id`. No party class is fixed (no Population category, Cohort, culture or crowd is converted into a diplomatic party), nothing is dereferenced, and no underlying claim, Diplomatic Instrument, Clause, adjudication or interpretation object is created or required merely to satisfy a reference. `provenance_ref` is distinct from the engine's own rule / spec provenance metadata.
5. **`effect_on` is conditional, exactly three literals, never defaulted.** WS-008 §29.4 fixes `issuance`, `addressee_receipt` and `instrument_or_setting_specified`. Omission stays omission. The contract adds no cross-field rule (for example, it does not require an instrument reference, an effect rule or a dependency alongside `effect_on`, and it does not infer `effect_on` from any other field). `addressee_receipt` is only a stored literal: no Epistemic receipt event is created, inferred or backfilled, and a future dynamic operation using it must consume the lawful F-014D receipt event and discriminate access mode.
6. **`dependency_refs[]` element shape.** WS-008 §29.3 requires the array only where the conclusion is derived from another owner's mutable state and fixes no element shape. Each element is the exact fact key of that committed state, so the dependency is registered through the existing commit-group read and dependency pins (RC-07), exactly as for the recognition path. A purely authored baseline record invents none — not even when an opaque reference names another owner — and its group reads and depends on nothing. Naming a fact that is not committed is refused as a missing prerequisite.
7. **Invalidation is reported, never re-resolved.** The keyed read compares each pinned dependency version with the committed one and reports `dependencies.invalidated`; it re-resolves nothing, rewrites nothing and adds no watcher. Load verification treats an advanced dependency as the legitimate upstream write it is, not as corruption.
8. **The existing owner, a new facet and a new governing-rule citation; the others are untouched.** The Diplomacy owner is the existing IM-06 `diplomacy` owner; the new facet is a technical encoding of the exclusive Externalized Claim / Dispute facet and creates no second substantive owner. Its citation records the WS-008 artifact and exact pin with the F-016 Phase 2C and F-017 lineage. No other kind's citation is changed or reused.

These are recorded interpretations of the brief, not new rules; none adds a source-undefined executable restriction, and each is a candidate for the later Diplomacy work it belongs to.
