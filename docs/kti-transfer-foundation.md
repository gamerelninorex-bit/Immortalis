# KTI Managed Transfer Package / Result-Close Backbone Foundation

Eleventh bounded slice, built on the Campaign Continuity Foundation (`docs/campaign-package.md`), the Canonical World Identity & Owner Foundation (`docs/canonical-world-foundation.md`), the Turnless Temporal & Resolution Transaction Foundation (`docs/temporal-foundation.md`, including its durable pre-stage transaction authority), the Named-Actor Character Capability & Capability-Close Backbone Foundation (`docs/actor-capability-foundation.md`) and the Epistemic Access / Sealed Accessible Content Packet Backbone Foundation (`docs/epistemic-access-foundation.md`). **One already-committed KTI development object** and **one already-sealed F-014D `BOUNDED_SHARED_ACCESS` Accessible Content Packet** for a bounded, named non-PC recipient can now become **one KTI-owned, active, managed Transfer Package** for that source × recipient × development-object programme, **published at one declared KTI result close** through the lawful KTI owner (`kti` / `kti_development`, IM-09), under the existing IM-02 stage/dependency machinery. It is a foundation for later KTI competence, reproduction, adoption and Diplomacy staging; it is not their implementation. **It must not — and does not — turn receipt into comprehension, competence, mastery, reproduction, adoption, belief, institutional uptake, diffusion or behaviour.**

Governing lock: `spec/f027/spec-lock.json` (F-027 v1.0). Source: WS-002 KTI — the frozen post-ratification KTI v0.3 source conformance overlay (lock pin `2026-09-26T02:44:38.319Z`), conforming the Sovereign-ratified KTI v2.2 Candidate v0.3 and KTI Scaling Profile v1 Candidate v0.3 (both pin `2026-09-26T02:10:16.626Z`; Candidate v0.2 §4.2 producer-side temporal cut and §4.3, Profile Class A and Class E), KTI Concept 2 §2 (development-object classes) and §9 (Intentional transfer package) and the KTI final scoped closure; F-014D §§2.1, 17, 18 (KTI Transfer Adapter; the KTI ↔ F-014D temporal cut); F-017 v0.3 §3 (CLOSE), as already implemented by IM-02. **CAL-01 (APPROXIMATE-PARTITION) remains UNCALIBRATED and is not used: every proof is exact. No score, number, threshold, grade, roll, prior, seed or default exists anywhere.** Every other F-027 open gate is unchanged.

This is a **foundation proof**, not a knowledge/technology simulation. All fixture data is synthetic (`packages/testkit/src/kti-fixtures.ts`): the existing Epistemic fixtures (a test access source, and a packet consumer that forms the packet an earlier consequence needed) are reused, and a test **KTI result consumer** is the dependent consequence that materially requires a Transfer Package and records exactly the package it read. It is registered through the existing extension seam (which cannot write a canonical, kernel, Population, Production, Economy, World-State, Logistics, Named-Actor, Epistemic or KTI key space) and owns nothing KTI. The KTI owner is real and lives in `@immortalis/engine`.

## One canon: how it reuses IM-02 / IM-03 / IM-11 / IM-12 / IM-17

Nothing new is persisted outside the existing campaign package. All three KTI kinds are ordinary `OwnerFact`s written through `store.commit`, so the existing validation, expected-version checks, RC-16 receipts, idempotent replay, unknown-outcome reconciliation, hash-chained journal and package/load integrity are the ones in force. **The package format is unchanged (still format version 1); there is no second journal, scheduler, roster, sidecar save path, polling loop or per-recipient/per-object refresh.** The temporal coordinator and the Epistemic and Named-Actor modules were not changed (conformance tests assert none names the KTI owner). The only edits to predecessor engine code are additive wiring: the registry gains the three kinds, `identityMismatch` handles them, `canonicalAdmission` dispatches the KTI owner, object registration also asks the KTI rule, and `CanonicalCampaign.open`/`verify` also run the KTI verifier.

## The lifecycle: object + sealed packet → basis → result close → consumption

1. **Packet (already sealed, F-014D → KTI).** The Epistemic owner formed the packet in an earlier consequence's object (tenth slice). KTI does not form, recreate or improve it.
2. **Object (authored).** `establishDevelopmentObject` commits KTI's own Class-A identity. It reads and depends on nothing foreign and creates no institution, actor, Population or world fact.
3. **Basis (authored, after the packet — the establishment of the programme).** `establishTransferBasis` commits the programme declaration. **A formed or received packet never creates a basis or package**: the packet is evidence a programme consumes, and only this explicit KTI-owner publication (with the cross-resolution management gate) establishes the Class-E record. Admission requires exactly three committed facts, pinned at their current versions and depended on (RC-07): the development object, the sealed packet and the packet's sealed provenance. So **KTI can consume the packet only AFTER packet formation** (a basis before it is `PREREQUISITE_MISSING`). It checks, from the committed evidence: the packet is the **named recipient's own** sealed packet (a stale, foreign, event, provenance or other-recipient reference is refused); the packet was formed from a **`BOUNDED_SHARED_ACCESS` event** whose one named participant is the recipient (the mode-consumer invariant — an unlowered `BROADCAST_EXPOSURE` is never receipt and is refused); the **packet supports the object** (its payload `referent` is the canonical `object_id`, below); the **identity** is derived from exactly (`source_id`, recipient, object); and the recipient is a lawful non-PC subject. The programme `source_id` is **not** compared with, and never copied from, the F-014D true source.
4. **Material trigger = the consequence's object.** A dependent consequence registers its temporal object with the KTI stage declared ahead of its own stage. Registration is refused unless the basis is **already committed** — a consequence cannot create the transfer it needs. There is no standalone engagement, tick or sweep: with no consequence engaged, no package is ever published, however many bases exist.
5. **Result close (IM-02 stage).** The coordinator resolves the declared stage first: it reads exactly the basis, the sealed packet (**AS-OF-NOW, after packet formation**) and the object, and commits the package under its StageKey-derived group/intent identity and the transaction's durable authority, declaring the **KTI result close**. The StageKey is `(kti-transfer/<package>, kti / kti-publish-transfer-result-close, <package key>)`: no horizon, source or packet version, retry, consumer or slice is an identity dimension.
6. **Consumption.** The consequence's stage reads the package **AS-OF-DECLARED-CLOSE**, naming the KTI result close, so it cannot resolve before it and observes the committed close itself. A later consequence of the same programme declares the same stage in its own object and **adopts** the committed result by identity — never duplicated, recomputed or improved. Two consequences due at the same instant share one result: one declares the stage, the other reads the close.

## The temporal cut: no same-resolution feedback

F-014D packet formation → KTI consequence write → KTI result close → any later lawful read (KTI v0.2 §4.2; F-014D §2.1). Structurally: the packet is **sealed before the basis can exist**, so a KTI consequence cannot recreate it; the KTI owner can write no Epistemic key (owner exclusivity, for a raw commit too) and a KTI stage's read of the packet is NOW of an already-committed fact; the Epistemic formation stage is exactly the declaration derived from its event, so it **can read no KTI state at all** — not the package at its close, not NOW (tested); and every other reader of KTI state reads the package only at the declared KTI result close, never NOW, never the basis or the development object. The sealed packet, provenance, event and source are byte-identical after the result (tested).

## Receipt, transfer workflow and learning are separate

- **Receipt** is the sealed packet: F-014D's route, payload and intelligibility determination. KTI does not re-decide it.
- **A managed transfer being active** is the Transfer Package: workflow state only. It says a transfer from this programme source to this recipient of this object is materially managed across resolution boundaries.
- **Comprehension, competence, reproduction, adoption, adherence, belief, institutional uptake and diffusion** do not exist here. The package has no field for them and no module names them (conformance-tested).

## Judgment calls and open residuals (none resolves an open gate)

- **The programme source is an opaque `source_id` (Blue clarification, Issue #14).** Class E's source dimension is the source party/source faction of the deliberate programme (Concept 2 §9), not the F-014D Sealed Engine Provenance's true source/holder/carrier (a programme may be sponsored by one party while the packet comes from an instructor, document or intermediary). The basis carries `source_id` as an identity dimension parallel to the recipient — an opaque identity, not a copied foreign fact value — and admission does **not** require it to equal the provenance's source; nothing of the true source/holder/carrier is copied into KTI. Whether `source_id` names an existing faction or legal entity, its mandate or any treaty permission or source-side authority belong to their lawful owners (not implemented, not invented, and Diplomacy is not required to establish this workflow record).
- **Packet-to-development-object linkage is the canonical `object_id` (Blue clarification, Issue #14).** F-014D's Content / Referent may be a payload reference, and KTI requires a singular canonical object identity; for this bounded foundation the packet's `payload.referent` must **be** the canonical KTI `object_id` — an opaque canonical-reference equality, not natural-language matching. Prose, a synonym, another reference scheme, a case/whitespace variant or an ambiguous label fails closed; the object carries no free-text label of its own, and no mapping or adjudication mechanism exists (a future lawful one may widen this; none is invented).
- **One active package per programme; no merging, no completion.** A second packet for the same `source_id` × recipient × object finds the programme's slot occupied: its basis is refused and the first package stands (no merge, update or duplicate). The package is create-only and `ACTIVE`; completion, failure, abandonment, retirement and "ordinary recipient development state is sufficient" are **not implemented** (the brief forbids inventing a chooser or threshold), so the slot is never freed in this slice. A "later materially new transfer creates a new package" rule needs that lifecycle and is deferred with it.
- **The Class-A and Class-E gates are authored literals, not adjudicated.** `MATERIALLY_FUTURE_CAUSAL` and `CROSS_RESOLUTION_MANAGED` restate the source's creation gates; the engine does not compute whether an object or transfer _is_ materially future-causal or managed. Faction/recipient relationship facets (encounter, intelligibility, competence/PARTIAL depth, adoption/reach, continuity, evidence limits), transmitted-means, recipient-bottleneck, reproduction/independence-condition and source-constraint fields of Concept 2 §9, and the active-set archival/reactivation lifecycle have no source structure for this slice and are **not implemented** (unmodelled, fail closed).
- **The recipient is a named non-PC identity, not a KTI competence key.** The brief fixes the recipient as the packet's named recipient; the package holds no competence, so the v0.3 rule "Named Actors are excluded as KTI competence keys" is not engaged. Faction-wide, cohort-wide and institution-wide recipients are never inferred.
- **Cross-owner reads of KTI state other than the package are refused.** The development object (Class A) and the basis are KTI-internal; the KTI v0.2 §4.2 list of facts F-014D may read (relationship, encounter, intelligibility, competence, diffusion/reach, background exposure) is not implemented. Nothing implemented here has F-014D (or any owner) read KTI state yet; the registration rule and `ktiResultCloseRead` are the one lawful form such a read must take.
- **Sealed provenance and the event are read by admission and load verification only (engine-side).** No declared stage of KTI reads them (the Epistemic registration rule refuses any declared read of them by any stage); the basis' pinned reads record the causal dependence on the sealed provenance without cloning it.
- **A result close is consumable through IM-02 only where its stage is engaged** (parity with the ninth and tenth slices). A consequence that reads the close without declaring the stage is unresolved (`PREDECESSOR_ABSENT`), never credited.
- **No Named-Actor existence record yet** (as in the ninth and tenth slices): a recipient is an opaque identity that is not a PC, not under player control and not a Population ledger.
- **Implementation Escalation status — none required for this slice.** Nothing in the slice needs a lawful uncertainty mechanism. **GitHub Issue #11 stays open and unimplemented**: no RNG, seed, roll table, chooser, probability or uncertain capability establishment exists in KTI (a conformance test asserts it).
- **Cost.** The advance path reads the engaged basis, packet and object by identity and writes only that programme's package. `verifyKtiIntegrity` (like the other verifiers) lists all facts once per open — a diagnostic path (CAL-06), not the advance path.
