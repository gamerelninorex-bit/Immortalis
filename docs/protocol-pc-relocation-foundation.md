# Trusted Confirmed Active-PC Single-Leg Movement Gateway Foundation

Forty-first bounded slice, built on the Active-PC Voluntary Movement Commitment → Single-Leg Physical Relocation Foundation (`docs/pc-movement-foundation.md`, PR #42), the Active-PC Post-Handover Physical Locus Custody (`docs/pc-locus-custody-foundation.md`, PR #41) and the trusted-context protocol seam of PRs #39–#40 (`docs/protocol-event-signal-foundation.md`, `docs/protocol-causal-event-signal-delivery-foundation.md`). **Trusted server-side code that already holds one player-confirmed destination choice for the active PC can bind it, with an explicitly declared Logistics delivery boundary, into a trusted context; an untrusted host can then invoke one allowlisted operation that names nothing, and the existing PC → Logistics owner paths commit the PC's single leg up to lawful in-transfer custody.** It is neither a generic action framework nor a credential/session implementation.

## The trust boundary and what "confirmed" means here

1. **Confirmation is a precondition of the binder call, not a field.** The trusted service calls the binder only after the player has confirmed this exact destination by the service's own means. The `choice` it passes is the exact existing `PcMovementCommitInput` — `{ pc_id, destination: { world_id, locus_id }, authored_under: { role: "role.player", permission: "permission.player_choice.commit" } }` — validated by the existing strict schema. The gateway never states the authority itself and never defaults it: a choice not stated under exactly that role and permission yields an inert handle. There is no `confirmed` flag, role claim, LLM wording or host assertion that can stand for the confirmation.
2. **Not claimed.** The gateway does not verify a human, a session, an identity or that a confirmation interaction took place; login, credentials, sessions, accounts, tenants and the confirmation UI are not modelled, not implemented and not claimed. Calling the binder is the trusted side's attestation, nothing more. A deployment that cannot truthfully make that attestation must not call it.
3. **Authority is the context, never the request.** The campaign, PC, destination, authored authority, declared delivery boundary and publication material (`cause`, `basis`, `secrecy`, which F-027 defines no vocabulary for and which are therefore authored by the trusted side and never defaulted) come from the context. The host request carries only the operation name.
4. **Trusted context is not canon.** Every invocation re-runs the existing owner admission: the PC must be the active binding's PC at the pinned version, its stationary custody must hold as the one authority, the destination must be an established distinct locus of its world, and one slot per PC/entity applies at every layer. A wrong PC, stale binding or custody, mismatched or unestablished destination, rival locus, existing transfer or second move is refused by the owners, not by gateway logic.
5. **One refusal, one unknown.** Every failure — over-claiming request, forged or incomplete context, any owner refusal — is `RELOCATION_UNAVAILABLE` ("no relocation is available") with no cause, owner, key, identity or detail. An ambiguous infrastructure outcome is the distinct `RELOCATION_OUTCOME_UNKNOWN` (RC-16), not success and not failure.
6. **Minimum receipt.** Success is exactly `{ status: "RELOCATION_COMMITTED" }`: no revision, hash, key, owner, replay flag, locus or arrival. It is identical for a first call and a retry, so it is not a new player-facing consequence channel; results reach the player only through the existing IM-13 → IM-14 path.
7. **Isolation.** A context is bound to one campaign object; the gateway constructs its Logistics adapter from that campaign's own store. Two campaigns with identical PC, world, locus and group identifiers cannot cross. This is bounded campaign-isolation evidence for this operation, **not** an authentication or session isolation claim.

## The sequence

The operation commits, in order, each under its own existing owner and unchanged in meaning:

1. `CanonicalCampaign.commitPcVoluntaryMovement` — the PC-side commitment-of-record (`pc_movement_commitment`).
2. `CanonicalCampaign.establishPcMovementRequest` — the PC-owned Movement Service Request (`pc_movement_request`).
3. `LogisticsAdapter.commitMovement` — the single-leg Logistics commitment at the trusted side's explicitly declared `delivery_at`.
4. `LogisticsAdapter.dispatch` — the transfer; World-State's stationary custody yields atomically with this commit and Logistics is the sole in-transfer locus.

Group and intent identities are `pc-relocation-group:<step>:<pc>` and `pc-relocation-intent:<step>:<pc>`, derived from the canonical PC identity alone (technical encodings; no clock, counter, random value or host-supplied idempotency).

**The gateway does not register the transfer's temporal object, advance time, resolve a boundary or promise arrival.** Registering the object with the coordinator and resolving the declared boundary remain the existing Temporal machinery, driven by the trusted side by its normal means; the existing Logistics delivery → World-State destination commit → Logistics retirement chain is the only arrival path. Until then the PC is `IN_TRANSFER` with Logistics as the one authority.

## Recovery

Presenting the same request again — with the same context or a freshly bound equivalent — is the recovery path. Every committed step replays (`replayed`), the remaining steps commit, and the run converges on the uninterrupted one; after a commit a retry returns the same status and writes nothing, in transfer or after arrival. A lost reply or crash at any of the four commits is `RELOCATION_OUTCOME_UNKNOWN` and reconciles by identity, including across save → close → load. A partial sequence (for example, a declared boundary the Logistics commitment refuses after the two PC-side steps committed) is recoverable only through the existing validated current state: the PC stays stationary at its origin under World-State, nothing is rolled back, and the same PC relocates once the lawful boundary is declared. A changed input (a different boundary after Logistics committed) is a conflict, never a silent reuse.

## Not implemented

Generic action routing, free-form language or a parser for player speech, unauthenticated host mutation, a full login/session/credential service, MCP/HTTP/transport, provider adoption or deployment, result narration, event discovery, a universal command/commit framework, new choice or confirmation canon, an actor mind, a second PC journey, route finding, distance/speed/calibration, obstacles/hazards, carrier or passenger logic, a time-advance policy, temporal-object registration, source-lock edits, live migration, any IA/V row or gate promotion, and PF-6/F-028 activation.

## Residuals

- Whether a confirmation actually occurred is outside this slice; the binder's caller owns that precondition. Real authentication, session binding and a confirmation surface remain future, separately authorised work.
- The transfer is not registered with the Temporal kernel by the gateway; a trusted caller must register and advance by the existing means for arrival.
- Exactly one journey per PC under the current one-slot constraints; a second relocation is refused by the existing owners.
- A declared boundary the Logistics commitment refuses is only discovered after the PC-side steps commit; the committed willingness and request stand (no invented rollback) and the retry converges.
- Local success is not provider or recovery acceptance (IA-07 BLOCKED). No register evidence was added; whole-row status remains separately governed.
