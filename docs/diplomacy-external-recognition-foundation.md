# Diplomacy External Recognition Core Backbone Foundation

Seventeenth bounded slice, built on the same commit, owner-registry, admission, persistence and recovery machinery as the GIP foundations (`docs/gip-governance-instrument-foundation.md` and its predecessors) and the earlier owner foundations. It adds the engine's first Diplomacy-owned persistent fact: formal external recognition. **Initial authored establishment only.**

Governing source (exact pins live in `spec/f027/spec-lock.json` and the owner registry): **WS-008 Diplomacy / Inter-Faction Relations v1.1** (frozen F-027 pin `2026-09-24T07:01:45.312Z`) §2.1, §2.2, §6 (External Recognition), §24 (invariants 7-8), §29.2 (R-2 continuity and succession), §29.3 (R-3 dependency registration and invalidation), §29.7 and §29.8 m-4, with **WS-007** (pin `2026-09-24T01:42:24.952Z`) and the **GIP Concept Amendment v2.1** (pin `2026-09-24T01:42:22.902Z`) — pure external recognition stays in Diplomacy, not GIP — **F-016 Phase 2C** (pin `2026-09-21T23:21:44.154Z`) and **F-017** (pin `2026-09-25T23:42:27.802Z`): GIP authority precedes Diplomacy, and a later incorporation result never rewrites the earlier external act.

An External Recognition is one authored statement: _one recognizer formally holds one scoped external recognition status toward one referent, effective from an authored point, under an authored authority basis and act or instrument_. It is **not** objective existence, control, territorial truth or internal legal status; it is not recipient awareness, receipt, comprehension, belief, acceptance or loyalty; it is not internal law or domestic incorporation; it is not a treaty, negotiation, Diplomatic Instrument, Clause or Binding Entry; it is not an Actor, Faction or ACS choice; and it is never inferred from contact, trade, negotiation, treaty-making or conduct (WS-008 §29.8 m-4).

**Not implemented (out of scope, unchanged):** negotiation; Diplomatic Instrument, Clause, Binding Entry, treaty or framework formation; Actor, Faction or ACS choice; GIP Collective Decision procedure, domestic incorporation, applicability / Administrative Reach and office transition; external performance or compliance; communication delivery, receipt, comprehension or awareness; any Relation Edge, Channel or global relationship index; any symmetric reciprocal recognition record; any universal trust, reputation or influence score; any post-establishment recognition mutation (status change, withdrawal, suspension, supersession, succession application, dependency-driven re-resolution, cold-history retirement); any timer, tick, scheduler, watcher or polling loop; and any RNG, seed, probability, chooser, prior or workaround for GitHub Issue #11 (untouched).

## Identity, keys, lifecycle and idempotence

- **Identity is `recognition_id` alone.** The key is `diplomacy/recognition/<recognition_id>`. The recognizer, the referent, the scope, the status and the dependencies are **not** identity dimensions; recognition is directional, so the opposite direction is a separately authored act with its own identity, never a generated reciprocal copy.
- **One slot per recognition.** A retry, a duplicate construction or a raw-store write reaches the same occupied slot, so no sibling record exists. Distinct recognitions are distinct only by their authored `recognition_id`; nothing is merged or deduplicated.
- **ADVANCING, initial establishment only.** WS-008 permits later withdrawal, suspension, supersession / continuity consequences and cold-history retirement, so the kind is `ADVANCING`; this slice implements the first creation only. Diplomacy admission refuses every other change (`AMENDMENT_NOT_SUPPORTED`), and a second creation of an occupied key is refused by the store (`VERSION_CONFLICT`).
- **Retry converges, conflict fails closed.** Re-presenting the same intent is reconciled by identity (RC-16) to the original receipt. A different intent at an occupied `recognition_id` — equal or different content — and the same intent with changed content are refused; the committed recognition is never rewritten.
- **No scan, clock or RNG.** Establishing a baseline recognition reads nothing and writes only its own key; reading one is a direct keyed read; only the diagnostic load-time verifier lists facts, once per open.

## Interpretations recorded for review

1. **`recognition_status` and `continuity_basis` are open named values.** WS-008 §6 says _Possible_ `recognition_status` values and §29.2 says setting-valid bases _may include_ personal, office, represented_entity "or another explicitly named basis", so neither is a closed enum. Both are carried as non-empty, whitespace-trimmed identifiers (the repository's weakest identifier rule). The listed values and the examples are exported as documentation (`LISTED_RECOGNITION_STATUSES`, `EXAMPLE_CONTINUITY_BASES`) and are never used to accept or reject a value; no alias is normalised into a listed value.
2. **References are opaque, with the weakest identifier rule.** `recognizer_ref`, `recognized_referent_ref`, `authority_basis_ref`, `instrument_or_act_ref`, `provenance_ref` and `successor_rule_ref` use the repository's opaque `Id` (not the key-safe `EntityId`, because none of them is embedded in a key). No recognizer-party or referent class is imposed — in particular `recognizer_ref` is not restricted to a GIP office — and nothing is dereferenced or created from a reference.
3. **`recognition_scope` and `effective_from` types.** The source gives no type for either. `recognition_scope` is one singular authored text value (never an array) and `effective_from` is one authored scalar carried faithfully, a string or a finite number; neither is parsed, compared, scheduled or turned into a Temporal boundary. `withdrawal_or_supersession_condition` is optional authored text, never evaluated.
4. **`dependency_refs[]` element shape.** WS-008 §29.3 requires the array "where the conclusion is derived from another owner's mutable state" but fixes no element shape. Each element is the exact fact key of that committed state, so the dependency is registered through the existing commit-group read and dependency pins (RC-07), the same mechanism every prior owner path uses. No minimum length, uniqueness or deduplication is imposed: the authored array is carried verbatim, and admission pins each distinct named fact once. A record without the field is a purely authored baseline and invents no dependency; the group must then read and depend on nothing. Naming a fact that is not committed is refused as a missing prerequisite.
5. **Invalidation is reported, never re-resolved.** The keyed read compares each pinned dependency version with the committed one and reports `dependencies.invalidated`; it re-resolves nothing, rewrites nothing and adds no watcher. Load verification treats an advanced dependency as the legitimate upstream write it is, not as corruption.
6. **A new owner and a new governing-rule citation; the others are untouched.** Diplomacy is a distinct IM-06 owner with one facet, as WS-008 §2.1 and the Runtime Contract (Economy / GIP / Diplomacy kept separate) require. Its citation records the WS-008 artifact and exact pin with the WS-007 / GIP Amendment, F-016 Phase 2C and F-017 lineage. No other kind's citation is changed or reused.

These are recorded interpretations of the brief, not new rules; none adds a source-undefined executable restriction, and each is a candidate for the later Diplomacy work it belongs to.
