# Trusted Player-Authorized NULL-PC OOC Target-Only Temporal Advance Gateway Foundation

Forty-fifth bounded slice, built on the existing Temporal kernel (`docs/temporal-foundation.md`), the real shipped owner stage providers (Production, World-State, Economy, Logistics, Population, Epistemic, KTI, Named-Actor and PC-Capability) and the protocol package's earlier gateways (`docs/protocol-pc-transfer-advance-foundation.md`). **Trusted server-side code that holds the player's genuine, separate out-of-character (OOC) choice to advance a campaign that currently has no active PC can bind that choice's explicit canonical target and its durable transaction identity and provenance into a trusted context; an untrusted host can then invoke one allowlisted operation that names nothing, and the existing `TemporalCoordinator.advance` resolves any registered work due at or before that target through the real owner stages, or, when none is due, carries stable state to the target exactly and lazily.** It is neither a general wait system, a natural-language or date interpreter, a world-process bypass, an action framework nor a credential/session implementation, and it replaces nothing in the kernel.

## The trust boundary and what "player-authorized" means here

1. **The player's OOC choice is a precondition of the binder call, not a field.** The trusted service calls the binder only after the player has made a genuine, separate choice to advance a campaign that currently has no active PC, by that service's own means. It passes the **explicit target** the player chose (an existing `CanonicalTimeSchema` value: an opaque `unit` and a non-negative integer `value`, exactly as the kernel's own coordinate defines them) and the choice's durable identity and authored provenance — exactly the existing `ResolutionRequestSchema` fields the trusted side alone may state: `transaction_id`, `cause`, `trigger { kind, ref }`, `context { role, permission }` and `publication { basis, secrecy }` — validated by the existing strict schema (`ResolutionRequestSchema.pick`). The gateway never states the role or permission and never defaults any of them: a transaction not stated under exactly `role.player` + `permission.player_choice.commit` yields an inert handle (so does a `role.player_character` context, a target that is not a `CanonicalTimeSchema` value, and any extra field — there is no `requested`, `continues` or condition for the trusted side to state here).
2. **No time is invented.** There is no default calendar, unit, duration, date parser or inferred horizon. The target is the trusted side's value; the host cannot supply, select or override it. It must be valid in the kernel's actual canonical time coordinate (a different unit is refused) and cannot be in the past (the kernel's `TARGET_BEFORE_BASIS`).
3. **Identity is the trusted side's, stable across retries and reopen.** The transaction identity and provenance come from the context and are retained by the caller; the gateway derives nothing from a random value, clock, message counter or revision and never re-identifies a retry.
4. **Not claimed.** The gateway does not verify a human, a session, an identity or that a choice interaction took place; login, credentials, sessions, accounts, tenants and any choice surface are not modelled, not implemented and not claimed. Calling the binder is the trusted side's attestation, nothing more. A deployment that cannot truthfully make that attestation must not call it.
5. **Trusted context is not canon.** Every invocation first re-reads the campaign's operative `role.player_character` binding and then runs the kernel's own admission. A wrong unit, a past target, absent temporal state or a stale basis is refused by the kernel or by this re-read, not by the host's claim.
6. **One refusal, one unknown.** Every failure — over-claiming request, forged or incomplete context, an active PC, a held continuation, a past or wrong-unit target, any kernel refusal — is `NULL_PC_ADVANCE_UNAVAILABLE` ("no advance is available") with no cause, owner, key, identity, target, stop reason or detail. A failure after anything may have committed (an `UNKNOWN_OUTCOME`, a poisoned or closed store, or any change in the store head since the call began) is the distinct `NULL_PC_ADVANCE_OUTCOME_UNKNOWN` (RC-16), never "safely no advancement".
7. **Minimum receipt.** Success is exactly `{ status: "NULL_PC_ADVANCE_COMMITTED" }`: no revision, hash, key, owner, replay flag, time, stop reason, event, recipient or attainment. It is identical for a first call and a retry, and identical whatever stop reason the kernel recorded.
8. **Isolation.** A context is bound to one campaign object, frozen and opaque; the gateway constructs its coordinator from that campaign's own store. Two campaigns with identical identifiers cannot cross. This is bounded campaign-isolation evidence for this operation, **not** an authentication or session isolation claim.

## The NULL-PC rule (inert whenever a PC is active)

The first thing the operation does after the strict request check is read the campaign's operative binding (`CanonicalCampaign.binding()`); if a `role.player_character` binding exists, the call is the one refusal and **nothing else is read or written**. This holds for a context bound before a PC was inserted, and for the replay of an identity that committed while the campaign was NULL: a PC that has since become active makes the context inert. While the interval is NULL, no PC Actionable-Knowledge-Time test exists (F-014B W3-CP3) and none is run; the operation grants no PC Glance, Narrative-Kernel report, observer privilege, event discovery, placement, status knowledge or later PC memory, and it has no special OOC omniscience.

## The literal Temporal request

The operation builds exactly one `ResolutionRequestSchema` value and nothing else:

```
transaction_id, cause, trigger, context, publication   ← from the trusted context (verbatim, never defaulted)
continues: null                                         ← the initial branch only; a held continuation is never silently consumed or cancelled
requested: { target: <the explicitly chosen CanonicalTime>,
             condition: null }                          ← target only; no stop predicate is supplied or inferred
```

It drives it through the **existing** `TemporalCoordinator.advance`, so the kernel alone selects what is due from the active boundary index (every registered due world process at or before the target is resolved by its own owner path and none is skipped), imports each engaged object's declared dependency closure, runs normal interruption and `DEPENDENCY_UNRESOLVED` semantics and commits the recorded transaction, the new canonical time and the stop/continuation in one kernel group. The registry is the real, shipped owner stage providers and nothing else — `productionCompletionProvider`, `worldFallbackAcceptanceProvider`, `economyRealizationProvider`, `worldEntityTransitionProvider`, `logisticsDeliveryProvider`, `logisticsRetirementProvider`, `populationStageProvider` (with the existing `populationBarrierEvaluator`), `epistemicPacketProvider`, `ktiTransferResultCloseProvider`, `namedActorCapabilityCloseProvider` and `pcCapabilityCloseProvider`. No testkit fixture acts as a source of authority, no provider is added or wrapped, and an object whose owner has no registered provider stops the transaction under the kernel (`DEPENDENCY_UNRESOLVED`, `PROVIDER_ABSENT`) instead of being faked.

One pre-check sits in front of the kernel on a fresh (non-replay) request; it only refuses and never writes:

- **A held continuation stays.** If the Temporal state holds any continuation, a new target is refused. Resuming a held remainder is a separately authorized operation outside this slice; the kernel's own `CONTINUATION_HELD` guard remains the final authority.

**Quiet intervals are the kernel's exact lazy carry (F47-R1).** The gateway adds no admission rule about what is due and never reads the boundary index. When the chosen target is valid and no registered material boundary is due by it — an empty active index, or a target strictly before the earliest earned boundary — the same unchanged target-only request goes to the kernel, which carries stable state to the target exactly and lazily (F-014B §6 step 3): the transaction records `TARGET_REACHED`, engages no object, writes no owner fact and invents no process, and any pending boundary and its owner state are untouched for a later choice. Absence of due work is therefore not a refusal ground and is not a host-visible signal: the receipt is byte-identical to the one returned when owner work resolved. The kernel's own validation still applies (a past target, a target in another time unit, absent temporal state, a held continuation and any unresolved stage are refused or stopped truthfully).

## What "committed" means (stop reason is not a side channel)

`NULL_PC_ADVANCE_COMMITTED` means the **temporal transaction** committed. It does not say that the target was attained, that any world process resolved, or that any observer, narrator or PC learned anything, and the host cannot tell. When a refused stage, a missing owner provider or an unresolved dependency stops the transaction before the target, the kernel records an honest `DEPENDENCY_UNRESOLVED` transaction with a held continuation (the time it earned moved; nothing is faked or fast-forwarded and the requested time is **not** reported as reached), and the host receives the same neutral status as for a reached target. Reporting a distinct status for that case would expose the kernel's stop reason and hidden world state; reporting it as unavailable would claim "no advancement" after the transaction committed. Any narration or information requires separate lawful I-001 / F-014D / NPK access; this slice implements none of it.

## Recovery

The same request with the same transaction identity and target — with the same context or a freshly bound equivalent, in the same process or after save → close → load — is the recovery path (RC-16):

- A transaction that already committed is replayed by the kernel against the same literal request: the status is the same, nothing is written, no second clock advance occurs, and committed stages are adopted by identity and never recomputed. The same identity presented with a different target, cause, trigger, context or publication is a conflict and is refused. A committed record that consumed a continuation (not this gateway's initial branch) is refused.
- A partial run (a crash or lost reply after the opening authority, any owner stage or the transaction record) leaves the registered boundary pending until the transaction commits, so the re-presented request finds the same committed state, adopts every committed stage and commits the rest, converging on the uninterrupted run.
- A lost reply or an ambiguous commit is `NULL_PC_ADVANCE_OUTCOME_UNKNOWN`. A failure that committed nothing is the plain refusal.

## Residuals

- Whether the player's OOC choice actually occurred is outside this slice; the binder's caller owns that precondition and must retain its target and transaction identity across retries and reopen. Real authentication, session binding and a choice surface remain future, separately authorised work.
- **Choice left to engineering:** the registry carries every shipped owner stage provider rather than a hand-picked subset, so any registered owner work the engine can really run is run by its own owner and none is skipped; a provider the engine does not ship stops the transaction truthfully. Only the Logistics, World-State, Production and Economy chains are exercised end to end here; the Population, Epistemic, KTI, Named-Actor and PC-Capability providers are registered but not separately exercised by this slice's tests.
- **Choice left to engineering:** the "held continuation stays" pre-check is a conservative refusal that adds no canonical effect (the kernel would refuse the same request with `CONTINUATION_HELD`).
- A PC that becomes active between a commit and a retry makes the retry the plain refusal rather than a replayed receipt (the operation is inert while a PC is active). The committed transaction is unaffected.
- Local success is not provider or recovery acceptance (IA-07 BLOCKED). No register evidence was added; whole-row status remains separately governed.
