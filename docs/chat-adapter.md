# Ordinary-chat host adapter (remote MCP + OAuth 2.1)

A **transport and a front end**: it lets a compatible, ordinary chat host that you link yourself play the existing campaign by conversation — without a technical console — while every rule, every record and every confirmation stays where it already was. It adds no gameplay, no model, no provider key, no owner rule and no engine change. It keeps exactly one bookkeeping file of its own (the pending-operation record, below) and reads the owners back to settle an uncertain outcome; it never invents an owner fact. Source brief: BLUE live-recovery continuation brief v2 (OB-058, native pin `2026-10-17T13:38:11.385Z`, PR #73 comment 6234545963). Not deployed by this change; both PRs stay draft and unmerged.

**Everything below the "Evidence" heading that is labelled MECHANISM is a script, not a chat session.** No real ordinary-chat client, model or player has used this yet.

## Neutral contract (host-independent)

The operations are typed requests over the existing shipped operations; MCP (Streamable HTTP, spec 2025-06-18) is only the first transport. Another qualified host needs only an adapter that can (1) authenticate, (2) call these typed operations, and (3) put a **human-typed** reply to the engine's printed confirmation, from somewhere the model cannot write.

| Scope     | Operation                                                                                                          | What it is                                                                                                              | What the caller supplies (untrusted)       |
| --------- | ------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| `player`  | `read_current_observation_glance`                                                                                  | the existing earned, current Active-PC Glance read (unchanged player-view transport)                                    | nothing                                    |
| `player`  | `observe_surroundings`                                                                                             | the shipped `observe-surroundings`                                                                                      | nothing (character from the scenario file) |
| `player`  | `collect`                                                                                                          | the shipped `collect`                                                                                                   | the **amount** only                        |
| `player`  | `continue_collection`, `finish_collection`, `cease_collection`, `settle_collection_lapse`, `reconcile_last_action` | the shipped `collect-continue`, `collect-finish`, `cease`, `settle-collection-lapse`, `reconcile`                       | nothing                                    |
| `player`  | `await_action`, `cancel_action`                                                                                    | follow the one action in progress (the human's confirmation is collected here); withdraw a pending proposal (a decline) | optional run id / cursor / wait            |
| `referee` | `referee_list_tasks`, `referee_get_task`, `referee_submit_decision`                                                | the existing bounded referee exchange, byte-for-byte the same operations the browser tools use                          | host id, task id, the AI's own reading     |

Never offered: a generic command, shell, file reader, owner query, campaign/path/role/permission/time argument, hidden-state dump, setup or authoring command, **or any tool that can reply to a prompt or carry a confirmation**. An unsupported action fails closed.

## Authentication (OAuth 2.1)

ChatGPT documents OAuth 2.1 (authorization code + PKCE `S256`) as its only supported authenticated mode (no API keys, no machine-to-machine); the adapter implements exactly that and nothing wider.

- Discovery: `/.well-known/oauth-protected-resource`, `/.well-known/oauth-authorization-server`; a `401` carries `WWW-Authenticate: Bearer resource_metadata=…`.
- Registration: dynamic client registration (`/oauth/register`), public clients only, `https` redirect URIs only (loopback `http` only when the whole service is in `insecure-loopback` development mode).
- Consent (`/oauth/authorize`): a page that states in plain words what is asked. **A scope is granted only by typing that lane's own secret** — `player` by the player secret, `referee` by the (different) referee secret — through the same constant-time, rate-limited check the lane sign-in uses. A client, a registration or a model's wording grants nothing. The player secret never grants `referee`, nor the reverse.
- Tokens: stateless, HMAC-signed, audience-bound to `<public origin>/mcp`, access 1 h, refresh 30 d and single-use (rotated); the signing key derives from **both** lane secrets, so rotating either secret revokes every token. Codes are 5 min and single-use. **Single redemption survives a restart (BLUE R1):** redeeming a code or a refresh token first creates, with exclusive-create semantics, one marker file named by its random id under `<operator dir>/oauth-spent/` (mode 0700/0600); the first redemption wins atomically — across concurrent requests and across restarts — and every later one is `invalid_grant`. If a redemption cannot be recorded it is refused (fail closed); one lost to a crash between recording and answering needs a new consent, which is the honest reconnect. Markers of expired grants are swept. Every token also carries the identity of the one **grant** (consent) it belongs to, unchanged through refreshes. Sessions (`Mcp-Session-Id`) are in memory and bound to the client **and the grant** that initialized them; a restart ends them and the client simply re-initializes.
- The endpoint answers only under its own public host name (DNS-rebinding guard) and refuses any foreign browser `Origin`.

## Confirmation: the human's, never the model's

The shipped commands print an exact proposal and a fresh, subject-bound challenge phrase and accept only that phrase typed to their terminal (anything else declines). The adapter keeps that terminal unchanged and offers exactly **two** places for the _human_ to type it:

1. **The client's own elicitation** (MCP `elicitation/create`, when the client declared the capability at `initialize` and negotiated 2025-06-18). `await_action` carries the question on its own response stream; the engine's proposal text and phrase go to the **human's** client UI; the answer returns to the server directly and is typed into the terminal. It is never a tool argument or result, and `accept` with the wrong phrase, `decline`, `cancel`, a closed connection and silence are all the same non-confirmation.
2. **The confirm page** `/confirm` — a clearly labeled **development fallback**, not accepted as fulfilling in-chat play — for a client that cannot elicit: single-purpose, requires the **player secret** (the assistant has no way to present a session cookie or the secret), shows the same proposal and prompt, and takes the typed phrase once.

What the model is given instead: the engine's report with the challenge phrase **removed** ("the phrase is not shown to the assistant"), no `ask`/`reply` transcript lines and no audit `PROGRESS` lines, a state (`RUNNING`, `AWAITING_CONFIRMATION`, `FINISHED`) and an exit code. `cancel_action` can only decline. A phrase from an earlier proposal does not confirm a later one (each run prints its own).

**Client-capability limit (must be verified live):** the elicitation channel is non-model-controlled only if the client renders it to the _human_ and does not hand it to the model to fill. OpenAI's MCP-server guide does mention elicitation, but neither documentation nor a client's declared capability proves that the Sovereign's actual account/mobile client supplies a native, non-model-controlled human surface; that is **unverified**. A question is also bound to the authorization that asked it (BLUE R2): a response under another grant — even of the same registered client, e.g. a referee-only grant answering a player's question — is refused (`404` for the session, `403` for the question), while a refresh of the same grant and a deliberately dual-scoped host keep working. If the live client can supply neither channel acceptably, the correct result is a STOP for that live route, not a weaker flow.

**Operator diagnostic of the initialize negotiation (24 October).** Each _accepted_ `initialize` writes one line to the service's stderr (the operator's log, never a response, tool result or player view):

```
immortalis-phone: mcp initialize accepted: requested=<2025-06-18|2025-03-26|2024-11-05|OTHER> negotiated=<one of those three> elicitation=<ABSENT|OBJECT|OTHER> form=<true|false|n/a> url=<true|false|n/a> eligible=<true|false>
```

`requested` is the protocol the client asked for when it is one the server supports and `OTHER` otherwise (the server then answers with its latest, `2025-06-18`); `elicitation` is `ABSENT` when the client declared no such capability, `OBJECT` when it declared one as an object (with `form` and `url` stating only whether those members are present) and `OTHER` for any other value (a scalar, `null` or an array); `eligible` is true exactly when the session may be carried on the eliciting transport (an elicitation object **and** the negotiated `2025-06-18`), which is the condition `await_action` then uses. The line is built from that closed whitelist alone. It never contains a client name or version, a capability key or value, a header, a token, a session, grant or client identity, a path or any campaign fact; a refused (unauthorized, wrong-host or malformed) initialize writes nothing. It is not de-duplicated (the service's other operator notes are, once per distinct line), so a repeated identical handshake is visible each time; a missing, throwing or rejecting sink changes nothing about the handshake. **What it is not:** a log line is engineering evidence of what a client _declared_. It does not show that any client renders a confirmation control to the human, and a fresh conversation alone is not evidence of a new grant or session. `tests/integration/chat-initialize-diagnostic.test.ts` covers each capability shape, the older and unsupported protocols, repeated handshakes, refused ingress, sentinel secrets planted in every client-supplied field and header, the real `main.ts` stderr, and the agreement between the logged eligibility and what the transport then does.

## Orchestration without deadlock

Every player operation **returns** (it never waits for the engine to finish): `RUNNING` means the engine is working, perhaps waiting for a referee reading. `await_action` waits for news for at most 25 s — **except** that while it is asking the human it holds the call open for up to **5 minutes** (the elicitation timeout; silence leaves the proposal pending and confirms nothing) — and returns on news, so the same assistant can serve the referee side between two of its own calls (`referee_list_tasks` → `referee_get_task` → `referee_submit_decision`) while the engine waits. Only one action runs at a time; a second is refused. **An uncertain outcome is a persisted, owner-checked block (BLUE R3).** Before any command that can write is dispatched — every player command except the read-only `status`, `locality-status` and `character-status`, whether it is started from the chat or from the phone page — the adapter writes a trusted, campaign-bound pending-operation record (`<operator dir>/chat-pending-operation.<campaign id>.json`, one file per campaign, atomic replace, 0600) naming the command, its closed options, the run and — for an observation — the character, the canonical basis it would be made at and the task and event identities of **every attempt** the shipped command may ask at that basis, all captured beforehand. If that record cannot be written, nothing is dispatched. A definite outcome removes it; an exception, an exit 4 or an engine status of `…OUTCOME_UNKNOWN` / `RECONCILIATION_REQUIRED`, or a process that died while it ran (a restart finds the record) leaves it, and then **no other writing command starts, from the chat or the phone page** (the read-only commands, and `reconcile`, still run), the report is `outcome: UNCERTAIN` (never "nothing was confirmed"), and the model is told not to retry or to claim either result. The record is cleared only by **owner-side evidence about that operation**, by class of command:

- **collection operations** (`collect`, `collect-continue`, `collect-finish`, `cease`, `settle-collection-lapse`, `reconcile`): `collection-recovery.ts` captures the operator ledger's immutable identities/digests, active PC, canonical basis/Temporal digest, original collection/act/target, reach task digest/attempt identities and held lineage before dispatch. New choices use the operator's existing trusted `newId` seam, reserving their UID before dispatch while still recording the intent only **after human confirmation**. The shipped operator commands run under their existing session lock; a changed pre-dispatch snapshot refuses execution. Recovery verifies those original identities and owner facts, not a status string or whatever choice is now latest. A missing Temporal registration is not inferred from a prospective extraction object. A partial continuation requires its retained reach decision; a partial ledger operation uses the existing reconciler only when it cannot select an unrelated confirmed choice. A lapse completion remains bound to the captured held lineage. Readback uses a fresh owner-verified reopen after completion. Missing old identities, changed inputs/tasks/lineage, unavailable owners or incomplete records retain uncertainty. An ordinary refusal that follows partial owner writes also retains the barrier; it is not automatically treated as a no-effect outcome. An owner-verified absence can settle an operation without claiming success. Recovery asks neither the human nor the referee again and never invents a confirmation;
- **an observation** (no ledger intent): the recorded PC/basis and all attempt identities locate the retained decision, event, packet and sealed Temporal transaction. A complete observation additionally requires clean Epistemic integrity. No evidence, a retained negative, or complete evidence settles the original operation; none implies arbitrary gameplay success. A partial positive uses the existing `formObservedPacket` owner path directly with the unique original retained decision key. The active PC and canonical basis must still match before completion; recovery never reselects the CLI's current task, asks another choice or rerolls a referee. A later-attempt decision can therefore complete lawfully without changing the operator package. Missing/ambiguous evidence stays blocked;
- **`initialize-time` and `prepare-collection`**: the original document and its SHA-256 pin are retained before dispatch. These two commands derive every publication from that document and campaign alone. Reconciliation reads those exact owner-committed groups: none means no publication of that operation committed; all means complete; a partial preparation remains blocked for the operator to inspect and finish with the identical document. Recovery never asks for another confirmation or repeats the command. Another chronology, setup or campaign cannot settle the original.
- **anything else** (other setup, authoring and binding commands, or a command not known to the record): no supported readback reconstructs their original typed answers, keep secret or dispatch-time versions. They remain blocked for engineering inspection. Legacy setup records without the document identity also remain blocked.

What the assistant is told is neutral: a blocker never carries the content of a half-formed observation. An unreadable record, an unsupported readback or a record that cannot be cleared are _structural_: the assistant is told to stop and that the operator must intervene (it is not sent round another `reconcile`). An engineer who has inspected the owners may correct or remove the record; every `reconcile` re-reads it, even when an earlier record is cached in memory. Malformed, unreadable or foreign replacements remain blocked and are never overwritten by stale cached state. Removal lifts the adapter barrier; it is not a success receipt or proof that the earlier action did nothing. There is no player or assistant clear-record operation. **Shutdown latches before draining work: no command dispatches after closing begins, including a launch awaiting identity capture. It waits (up to 8 s) for captures, recoveries and running player/referee commands to wind down**, because the command releases the campaign's writer lock only when it has; a hard kill can still strand that lock, which the phone never reclaims (recovery then reports the campaign unavailable until the operator reclaims it). Recovery only presents what the player already confirmed or reads canonical state, so it creates no second consequence; nothing in the adapter retries an action of its own accord or advances canonical time from a wall clock.

## Configuration (ready to connect once reviewed)

| Variable                                                                                         | Meaning                                                                                                                                                                                   |
| ------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `IMMORTALIS_PUBLIC_URL`                                                                          | the service's bare `https` origin (e.g. `https://immortalis-r5.up.railway.app`); **unset = the chat adapter is off** and `/mcp`, `/oauth/*`, `/.well-known/*` and `/confirm` do not exist |
| `IMMORTALIS_SCENARIO_FILE`                                                                       | operator-written, owner-only JSON (default `<operator dir>/chat-scenario.json`); engineering plumbing the player never names                                                              |
| `IMMORTALIS_PLAYER_VIEW_HOST_ID`                                                                 | host identity for the earned-Glance read; the trusted server process binds it once (proving the view against canon) on first use. Unset = the Glance tool returns the one opaque refusal  |
| existing `IMMORTALIS_PLAYER_TOKEN`, `IMMORTALIS_REFEREE_TOKEN`, `IMMORTALIS_REFEREE_HOST_IDS`, … | unchanged; the two lane secrets are the consent secrets                                                                                                                                   |

Scenario file (all seven keys, nothing else; an absent or malformed file makes the collection tools refuse with the exact gap, and starts nothing):

```json
{
  "player_character": "pc-namar-1",
  "world": "world-namar",
  "source": "source-namar-salt",
  "reserve": "<reserve id>",
  "quantity_unit": "<unit>",
  "mechanism": "<mechanism id>",
  "basis": "<basis id>"
}
```

Both the service and operator preflight (`docs/phone-bridge.md`, "Operator preflight") demand a regular file owned by the service user and not writable by anyone else. The preflight names each defect and checks every identity against the campaign before a long setup. A refusal to the player or the assistant stays cause-free; the cause goes to the operator's log. **An unset `IMMORTALIS_PLAYER_VIEW_HOST_ID` disables the earned Glance** (every read returns the same opaque refusal a genuine non-receipt would), so the preflight fails it when the route is on.

The engine still validates every identity against canon; preparation (`prepare-collection`, `declare-closed-setting`, `attest-cycle`, clarification) remains an engineering step on the existing console and is **not** a player operation. If the live scenario lacks a substantive prerequisite (scene closure, source access, workforce representation, a prepared and attested mechanism) the commands refuse as they do today; the adapter invents none.

**Connect (one time, after BLUE review and the Sovereign's deployment decision):** in the chat client add a custom MCP server with URL `<IMMORTALIS_PUBLIC_URL>/mcp` and OAuth; on the consent page the Sovereign types the **player secret** (and, only if this same chat is also to be the referee, the separate **referee secret**). Nothing else is entered.

## Evidence and its limits

- `tests/integration/chat-adapter.test.ts` — **MECHANISM**: OAuth (registration, consent, PKCE, redirect/client binding, code and refresh single use, expiry, key rotation); MCP lifecycle, session/client binding, scope-filtered tool lists, origin and host guards; no tool property can carry a reply/confirmation; the challenge phrase never reaches the model; elicitation exact/wrong/decline/cancel/silence; replayed phrase refused; the confirm page; the same assistant serving the referee side between its own calls without deadlock; a crashed command; the shipped `observe-surroundings` with the real referee exchange and the real player-view Glance behind the endpoint, with a declined second proposal changing nothing; static scope checks. Repair tests: spent code and rotated refresh refused after the process is recreated (and the unspent refresh, a never-redeemed code and a new consent still work; eight concurrent redemptions spend once; an unrecordable redemption is refused); a referee-only grant of the same client cannot answer, use or end a player session's question (while the authorized human can, across a refresh).
- `tests/integration/chat-adapter.test.ts`, `chat-recovery-readback.test.ts`, and `chat-collection-recovery.test.ts` — **MECHANISM**, isolated real campaigns plus explicitly labelled transport doubles. Coverage includes restart after a confirmed lost reply, partial observation event/packet/seal, later-attempt decision completion, generic reconcile's inability to settle a partial observation/continuation, original task/act/target matching, missing Temporal registration, partial cessation/lapse, ordinary refusal after partial writes, failed/unknown readback, changed-context refusal and legitimate next choice. Canonical records are compared by actual values and versions, including time/source/Reserve, with repeated recovery proving no additional consequence. The collection finish fault lands the real source debit and Reserve credit before losing the ledger reply; recovery retains the exact transaction and changes neither balance nor version again.
- `tests/integration/chat-tool-registration.test.ts` — an isolated harmless typed handler registered on `createMcpHttp`, using real OAuth grants and the same MCP session/dispatch implementation. Player registration/call works; wrong scope, unauthenticated access, extra owner-like arguments and an unregistered owner operation fail. This is a transport extension proof, not a new game capability.
- **Known recovery limits:** a hard kill may strand the campaign writer lock; the adapter never reclaims it automatically. Pre-upgrade records lacking collection identity stay blocked for engineering inspection. Missing/contradictory owner evidence and an unavailable campaign/ledger cannot produce a settled result. Other page setup/authoring operations have no automatic readback. A partial document-derived setup stays blocked; a restart alone establishes no outcome. A future operation needs its own lawful typed dispatch, confirmation requirements and owner-backed recovery evidence; this is not a universal transaction engine.
- **Not claimed:** any real ordinary-chat session; that the live client elicits to the human; that an AI understood any sentence; unattended play (an active conversation is required, and no always-on worker, paid API or model credential is involved); any change to the engine or to the previously reviewed #72 runtime.

The local operator may run `pnpm phone prepare-chat --scenario <owned-seven-key-json-file>` after setup and cycle attestation. The command requires the explicitly configured campaign and player-view host, validates all seven identities and physical locality against canon, binds only that configured view through the existing operator binder, and installs the scenario exclusively as 0600 in an operator-owned 0700 directory. This is engineering preparation, not an assistant tool or proof of native chat elicitation.
