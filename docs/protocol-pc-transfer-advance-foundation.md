# Trusted Player-Authorized Active-PC Stop-at-Delivery Temporal Advance Gateway Foundation

Forty-third bounded slice, built on the Trusted Confirmed Active-PC Single-Leg Movement Gateway with its Temporal enrollment (`docs/protocol-pc-relocation-foundation.md`, PRs #43–#44), the Active-PC Voluntary Movement Commitment → Single-Leg Physical Relocation Foundation (`docs/pc-movement-foundation.md`), the Active-PC Post-Handover Physical Locus Custody (`docs/pc-locus-custody-foundation.md`) and the existing Temporal kernel (`docs/temporal-foundation.md`). **Trusted server-side code that holds the player's SEPARATE choice to progress an already-started movement can bind that choice's durable transaction identity and provenance into a trusted context; an untrusted host can then invoke one allowlisted operation that names nothing, and the existing `TemporalCoordinator.advance` drives the PC's one in-transfer movement to its lawfully earned delivery boundary through the three real owner steps.** It is neither a generic wait/timer, an action framework nor a credential/session implementation, and it replaces nothing in the kernel.

## The trust boundary and what "separately authorized" means here

1. **The player's progression choice is a precondition of the binder call, not a field.** Starting the movement (the relocation gateway's confirmation) does **not** authorize advancing time. The trusted service calls the advance binder only after the player has made a distinct choice to progress, by that service's own means. The `transaction` it passes is that choice's durable identity and authored provenance — exactly the existing `ResolutionRequestSchema` fields the trusted side alone may state: `transaction_id`, `cause`, `trigger { kind, ref }`, `context { role, permission }` and `publication { basis, secrecy }` — validated by the existing strict schema (`ResolutionRequestSchema.pick`). The gateway never states the role or permission and never defaults any of them: a transaction not stated under exactly `role.player` + `permission.player_choice.commit` yields an inert handle, and so does any extra field (there is no `target`, `requested` or `continues` for the trusted side to state here).
2. **The movement's own identities are not a progression instruction.** A `transaction_id`, `cause` or `trigger.ref` that is the PC's movement request identity, its Logistics object, process or boundary identity, or one of the relocation gateway's derived group/intent identities yields an inert handle. The relocation's earlier confirmation, repeated or not, never reaches this operation: a relocation context is not an advance context (it is a different registered handle), and the operations' request literals differ.
3. **Identity is the trusted side's, stable across retries and reopen.** The transaction identity and provenance come from the context and are retained by the caller; the gateway derives nothing from a random value, clock, message counter or revision and never re-identifies a retry.
4. **Not claimed.** The gateway does not verify a human, a session, an identity or that a choice interaction took place; login, credentials, sessions, accounts, tenants and the confirmation UI are not modelled, not implemented and not claimed. Calling the binder is the trusted side's attestation, nothing more. A deployment that cannot truthfully make that attestation must not call it.
5. **Trusted context is not canon.** Every invocation freshly re-reads the committed state and runs the kernel's own admission: the operative PC binding must name this PC; the PC's physical-locus custody names its world; the PC must not be stationary at its origin; the Logistics commitment must be the PC's own single leg through the PC-owned Movement Service Request; the kernel's registered object for that transfer must be the Logistics-owned one with the commitment's declared delivery boundary, still pending and present in the active boundary index; and while the transfer is in transfer that object must equal exactly the object `logisticsTemporalObject` derives from the committed commitment and transfer. A wrong PC, an unenrolled or foreign object, a resolved boundary, a prior delivery or a stale binding is refused by this re-read or by the kernel, not by the host's claim.
6. **One refusal, one unknown.** Every failure — over-claiming request, forged or incomplete context, absent or stale state, any kernel refusal — is `ADVANCE_UNAVAILABLE` ("no advance is available") with no cause, owner, key, identity, stop reason or detail. A failure after anything may have committed (an `UNKNOWN_OUTCOME`, a poisoned or closed store, or any change in the store head since the call began) is the distinct `ADVANCE_OUTCOME_UNKNOWN` (RC-16), never "safely no advancement".
7. **Minimum receipt.** Success is exactly `{ status: "ADVANCE_COMMITTED" }`: no revision, hash, key, owner, replay flag, locus, time, stop reason, boundary or arrival. It is identical for a first call and a retry, and identical whatever stop reason the kernel recorded.
8. **Isolation.** A context is bound to one campaign object; the gateway constructs its Logistics adapter and coordinator from that campaign's own store. Two campaigns with identical PC, world, locus, object and transaction identifiers cannot cross. This is bounded campaign-isolation evidence for this operation, **not** an authentication or session isolation claim.

## The literal Temporal request

The operation builds exactly one `ResolutionRequestSchema` value and nothing else:

```
transaction_id, cause, trigger, context, publication   ← from the trusted context (verbatim, never defaulted)
continues: null                                         ← an initial request; a held continuation is never silently consumed or cancelled
requested: { target: null,                              ← condition only; no time is supplied or inferred
             condition: { kind: "STOP_AFTER_BOUNDARY",  ← the existing StopConditionSchema form
                          object_id, boundary_id } }    ← read from the PC's committed Logistics-owned kernel object and its one registered boundary
```

The kernel alone then selects what is due from the active boundary index, so **every earlier or independent due world process is resolved by its own owner path and none is skipped**; it imports the engaged object's declared dependency closure, runs normal interruption and `DEPENDENCY_UNRESOLVED` semantics, and resolves in its own order **Logistics delivery → World-State destination custody (`world_pc_locus_custody` / ECT-01) → Logistics retirement**, committing the recorded transaction, the new canonical time and the stop/continuation in one kernel group. The stage providers are the real ones the engine already ships (`logisticsDeliveryProvider`, `worldEntityTransitionProvider`, `logisticsRetirementProvider`); no testkit fixture acts as a source of authority. Exactly one authority answers "where is the PC?" at origin, in transfer, after each partial stage and at the destination; the Role Registry binding, handover and coupling are unchanged.

## What "committed" means (stop reason is not a side channel)

`ADVANCE_COMMITTED` means the **temporal transaction** committed. It does not say that the transfer was delivered, that the PC arrived, recognized a place, learned of an event or holds any knowledge, and the host cannot tell. When another lawful dependency, a missing owner provider or a refused stage stops the transaction before the delivery boundary, the kernel records an honest `DEPENDENCY_UNRESOLVED` transaction with a held continuation (the time it earned moved; the PC stays `IN_TRANSFER` with Logistics as the one authority; nothing is faked or fast-forwarded), and the host receives the same neutral status as for an arrival. Reporting a distinct status or error for that case would expose the kernel's stop reason and hidden world state, which the source forbids; reporting it as unavailable would claim "no advancement" after the transaction committed. Any narration, arrival information or current-location knowledge requires separate lawful I-001 / F-014D access and NPK access; this slice implements none of it. A later new-identity request cannot abandon a held continuation (`CONTINUATION_HELD` is the one refusal), and continuing a held remainder is not implemented here.

## Recovery

The same confirmed request with the same transaction identity — with the same context or a freshly bound equivalent, in the same process or after save → close → load — is the recovery path (RC-16):

- A transaction that already committed is replayed by the kernel against the same literal request: the status is the same, nothing is written, no second clock advance, arrival or draw occurs, and committed stages are adopted by identity and never recomputed. The same identity presented with different provenance is a conflict and is refused.
- A partial run (a crash or lost reply after the opening authority, the Logistics delivery, the destination custody, the retirement or the transaction record) leaves the registered boundary pending until the transaction commits, so the re-presented request finds the same committed state, adopts every committed stage and commits the rest. At every cut exactly one authority answers the PC's location (in transfer; in transfer with delivery established; destination committed with retirement pending; destination committed), and the run converges on the uninterrupted one.
- A lost reply or an ambiguous commit is `ADVANCE_OUTCOME_UNKNOWN`. A failure that committed nothing is the plain refusal.

## Not implemented

A generic player wait/timer UI or free-form language parser, a new authentication, session, credential or hosted provider, NPC autonomous cognition, a broad action framework, route finding, travel speed or capacity, a multiphase or second journey, cancellation or rerouting, PC perception, maps or guides, recognition or knowledge, narrative presentation, a new source of location truth, a new Temporal scheduler, alternate clock or artificial game turn, continuation of a held remainder, any IA/V row or gate promotion, any source-lock edit, migration, provider adoption or release change, and PF-6/F-028 activation.

## Residuals

- Whether the player's progression choice actually occurred is outside this slice; the binder's caller owns that precondition and must retain its transaction identity across retries and reopen. Real authentication, session binding and a choice surface remain future, separately authorised work.
- A foreign-intent or differently registered Temporal object left by an earlier path (PR #44's residual) is not repaired: the operation re-reads, finds a state that is not the one correct registered object, and refuses. A partial run begun under a different transaction identity is adopted by the kernel's stage identities, under that earlier identity's authority, exactly as the existing kernel behaves.
- A transaction that stops before delivery on a lawful dependency leaves the PC in transfer with a held continuation; progressing it needs separately authorised continuation work, not built here.
- Local success is not provider or recovery acceptance (IA-07 BLOCKED). No register evidence was added; whole-row status remains separately governed.
