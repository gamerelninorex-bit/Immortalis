# Host-requested observation — one real configured host exercise (retained, not acceptance proof)

Reported **separately** from the scripted tests, as the BLUE v5.2-A1 bounded brief (native pin `2026-10-15T12:57:55.189Z`) requires. It is a single exercise per scenario, run once, by one host, and it is not acceptance, not a semantic validation and not a claim about any model's understanding.

## What was run

- **Host:** the Claude Code CLI (2.1.300) in non-interactive print mode, started once per step with `--mcp-config` (one stdio server, `--strict-mcp-config`) and told to call the single tool once with no arguments and reply with the returned text. The host used the credentials already present in the session that ran it; this slice adds, holds and reads no provider credential, API key or paid service. The host held **two separate bindings** under one host identity (`claude-code-host`): a _request_ binding (`immortalis-observe-request`) and, separately, the existing _read_ binding (`immortalis-player-view`). Each call was a separate host process that could see only the one server it was configured with.
- **Campaigns:** built only by the shipped commands (`establish-locality` → `author-character` → `establish-character-locus` → Temporal establishment), exactly as the integration tests build theirs: a **positive** world whose path from the character's bench to a red patch is open, and an **independent negative** that differs only by an opaque screen across the path.
- **Sequence per campaign (each a separate process):** (1) the host reads — the existing opaque refusal; (2) the host calls the request tool — a request is left; (3) the **operator answers on its own console** (`answerObservationRequest`, the shipped answer, which runs the existing `observeSurroundings`): the console printed the requesting host, said the request is not the player's choice, drew a fresh challenge, and the challenge was then typed back; (4) the host reads again.

## What it shows

Curated from the stream-json output of the six host sessions: [`host-observation-request-real-host/host-calls.json`](host-observation-request-real-host/host-calls.json).

1. **The request is real, bounded and inert.** The host reported the request server `connected`, exposing exactly one tool of this server (`request_active_pc_observation`), called it with `{}`, and relayed the result: `OBSERVATION_REQUESTED` with the fixed words _"Nothing has been observed and nothing has been decided: the player must separately choose and confirm on their own console, and may decline. This request is not that choice."_ In both campaigns the existing read, called before the request and not changed by it, was the existing opaque `PROJECTION_UNAVAILABLE` refusal.
2. **Positive.** After the operator's separate confirmation (`OBSERVATION_RECEIVED`, basis `100 fixture-time-unit (unchanged)`), the host's existing read returned the existing presentation, unchanged — contact `PERCEPTION`, referent "a patch on the wall facing the character", content "a broad patch of bright red on pale plaster", viewpoint `role.player_character` — and relayed it verbatim; the integration suite asserts the same bytes equal the direct gateway's.
3. **Independently falsifying negative.** With the opaque screen, the same host request and the same operator confirmation ended in `OBSERVATION_NOT_ESTABLISHED`; the host's read after was exactly `{"ok":false,"error":{"code":"PROJECTION_UNAVAILABLE","message":"no projection is available"}}`, byte for byte what it was before — nothing in it, or in the request's acknowledgement, says why.

## What it does not show

- **That any AI perceived or understood anything.** The referee host that answered the F-014D question in both campaigns was the **scripted, plumbing-only** policy the tests use (it reads the delivered words by rule and certifies nothing about any AI); the semantic support for what the producer establishes remains the retained exercise in [`b52-direct-observation-live-host.md`](b52-direct-observation-live-host.md), neither repeated nor extended here.
- **That a human confirmed.** The "player's" confirmation in this exercise was typed by a script on the operator's console after the console printed the fresh challenge; it demonstrates the separate channel and the single-use challenge, not that a person typed. No claim is made that OS-owner verification identifies a person.
- **That the host model understood, interpreted or correctly relayed the scene** beyond echoing the returned text; **that any natural play loop exists** (no free-text look intent, action, duration, actor or movement exists); **ordinary chat-client completion** (the host was driven by a fixed instruction, not a play conversation); or that any other MCP client behaves the same. It demonstrates only that a real, locally configured MCP client can start the request server, list and call its one tool, and — separately — read afterwards through the existing read-only server.
