# Live host exercise — BLUE v5.2 active-PC direct physical observation (what was and was not observed)

> **This is a finite, single-model, single-session exercise, not an acceptance proof.** It is retained so a person can read exactly what a real AI host was shown and what it answered, and judge the readings for themselves. **No semantic acceptance is claimed from it, and none is claimed anywhere in this slice.** Whether the brief's positive and independent-negative acceptance may be called PASS is a decision for the independent BLUE review; this document supplies evidence, not that verdict.

> **Repair 1 (BLUE hold on `9617a98577ffd9f52f45a729a6a60ce71b861184`, finding H-2).** The first version of this exercise (retained only in git history at that commit) let the positive's open path rest on silence: the host's path reading said "no obstruction is stated", and the scene quoted daylight, three paces and clear air but nothing that excluded a solid opaque barrier. This version adds one affirmative physical setting statement to the shared scene (`locus.constraint.5`: _"Nothing solid stands between the bench and the north wall: the floor between them is bare, and no screen, curtain, partition or other object crosses the line from the bench to the wall."_ — a statement about objects and the line, not about sight or receipt). The independent negative `n1` now **replaces only that one path statement** (same `path` aspect, same position in the scene) with the opaque screen; target, character, faculty statement, placement, illumination, geometry, clear air and canonical time are identical to the positive. All six scenarios were rerun blind, in full, and the files below are that rerun. **H-1 (the Temporal boundary at the excluded `T0`) is not addressed by this repair**; see the foundation document.

## Whether a genuine AI-host semantic exercise occurred

**Yes, with the limits below.** The host was a **real headless Claude Code client** (`claude -p`, model `claude-sonnet-5-5` per the client's own init record in every trace) registered to the **real `immortalis-referee` stdio MCP server** (`--mcp-config`), which it discovered and called unaided: for each question it called `referee_list_tasks`, `referee_get_task` and `referee_submit_decision`. The service side was the shipped `immortalis-operator` binary run as real processes (establish-locality → referee-bind-host → author-character → establish-character-locus → observe-surroundings), exactly the committed code at the PR's head commit (`3429b4b`). The only in-process step is the Temporal owner's establishment of canonical time (value 100), done through the engine's own coordinator exactly as the test support does it, because no operator command for it exists yet.

No test policy, scripted answer or verdict is supplied by the driver. The driver (`run-exercise.mts.txt`) (a) types the **player's** lines, (b) types back the confirmation phrase the service printed, and (c) launches the host client whenever a question is pending. The host's prompt (`host-prompt.txt`) is one generic instruction, identical for all scenarios; it names no scenario, expected result or colour.

24 client runs (four questions per scenario, each answered by exactly one client run), 73 tool calls (24 `referee_list_tasks`, 24 `referee_get_task`, 25 `referee_submit_decision`), **24 decisions accepted; 23 at the first submission and 1 refused once by the engine and then corrected by the host** (`n4-eyes-closed`, run 04: `DECISION_INCOHERENT: the path rests only on committed world facts`, which is the engine refusing an internally inconsistent answer; the retained trace shows both submissions). No other tool error.

### Honest limits

1. **One model family, one session, one run per scenario.** The same session that wrote the engine also wrote the scene, the six player statements and the expectation of each outcome. A different model, an interactive chat client, a second run of the same model or a hostile world could read the same words differently; model variance is real and was not sampled here.
2. **No person has reviewed these readings.** The engine checked that each answer was well-formed, complete and quoted the delivered words verbatim, and **derived each verdict itself**; it did not and cannot check that a reading was _right_.
3. **Earlier runs are not retained in the tree.** The first full set of six (against the same code, before the H-2 repair above) is in git history at `9617a98`. Before even that set, earlier runs of the driver against earlier code exposed one ambiguity in the task text (what to answer for a world fact that "contradicts" versus one that blocks the path), which was repaired in the task document text; those earlier files were not kept. The files here are the complete set of the rerun, one per scenario, against the committed code, with no selection.
4. **The negatives are mostly the shape "nothing was established", not proof of obstruction.** Only `n1` and `n5` reach `BLOCKED` on the path; `n2`, `n3` and `n4` end `UNRESOLVED` because a fact the law requires was not stated. The engine treats those as non-establishment, never as proof that something is or is not there, and the player is shown only that nothing was received.
5. **The scene is small and written in the same idiom as the question.** It is one alcove, one wall, daylight, clear air. It does not test subtle optics, partial obstruction, distance, scale, dimness, hidden or illusory sources, or several viewers.
6. **No adversarial prompt-injection witness was run** against a live host. Injection, role spoofing, source leakage and the other mechanism cases are covered by the engine's own tests with scripted answers, not by this exercise.
7. The host supplied no `claimed_model` label (optional, self-reported); the model above is the client's own init record.

**What the positive produced.** After the player's separate, confirmed choice to look, the Epistemic owner committed one `BOUNDED_SHARED_ACCESS`, one-recipient (`pc-maren`), `PERCEPTION` event and its sealed packet, and the existing trusted Event-Signal path delivered it. The player was shown raw appearance only:

> referent: _The north wall in front of the seated viewer, with its red patch_
> content: _A pale white, evenly lit flat wall three paces ahead, bearing one broad patch of bright red about an arm-span wide, level with the viewer's eyes._

The retained positive decision now records `path: OPEN` on three quoted world facts, daylight (`locus.constraint.3`), clear air (`locus.constraint.4`) and the affirmative open-path statement (`locus.constraint.5`), rather than on an absence; its grounds read "nothing obstructs the line from bench to wall at three paces".

A fresh owner-verified open read back the retained `OBSERVATION_ESTABLISHED` decision, the `access/*` facts, the packet and the temporal state (canonical time `100`, unchanged; one observation transaction), with **0 integrity violations** (all six scenarios report 0 on their ordinary open; the negatives read back no `access/*` facts and no transaction). The engine requires each payload basis item to quote the committed setting verbatim; it cannot check that the host's prose content is a faithful rendering of that basis, which is a reading for the reviewer.

**What the independent negative produced.** `n1` is the positive's scene, player, character and canonical time with the single open-path statement replaced. The host read faculty and position as `ESTABLISHED` and the path as `BLOCKED` ("Despite clear air and daylight, an opaque screen with no gap stands across the full width and height between the bench and the north wall, so nothing on the north wall reaches the viewer's eyes"; its one path premise quotes the screen statement), the engine derived `OBSERVATION_OBSTRUCTED`, no event or packet was committed and the player was told only that nothing was received, without the reason. In `n1`'s console, the observe step itself (from the confirmation prompt to the result) names no screen, wall or patch; the setting appears only in the earlier setting confirmation the person authored and in the sealed decision.

**Not-shown reasons.** In every negative the player-facing console reports `OBSERVATION_NOT_ESTABLISHED` and "nothing was received at this basis"; the verdict name, grounds and setting appear only in the retained, sealed decision and in the "ordinary open" audit section of the transcript.

## What this does and does not show

- **Shows:** the end-to-end mechanism works with a real tool-calling host over the real stdio MCP server and real processes for the fourth operation; that an LLM host given the closed vocabularies produced answers that satisfied the engine's coverage and quotation rules in all 24 runs (23 at the first submission, one after a single engine refusal); and that for this one pair of scenes the same host, character and player produced `ESTABLISHED` for an open path affirmed by a committed setting statement and `OBSTRUCTED` when only that statement was replaced by a continuous opaque screen, with the packet content of the positive grounded in the quoted setting.
- **Does not show:** reliability across models, runs, languages, adversarial players or subtler worlds; absence of prompt-injection weaknesses; that a person would accept these readings; an ordinary user-facing game host (still absent); or that the engine's closed premise vocabulary is sufficient for scenes beyond this one.
- **Open for a reviewer:** whether a single positive/negative pair on one model satisfies the brief's "established by a real interpreter" bar or whether more witnesses are required; whether `n2`/`n3`/`n4` ending `UNRESOLVED` rather than `OBSTRUCTED` is the intended law (the engine's design is that missing circumstances are non-establishment, never proof of obstruction); and the narrow Epistemic-only current-basis amendment to the Temporal kernel described in `docs/active-pc-direct-observation-foundation.md` (flagged there for BLUE review).
