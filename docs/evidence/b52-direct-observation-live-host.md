# Live host exercise — BLUE v5.2 active-PC direct physical observation (what was and was not observed)

> **This is a finite, single-model, single-session exercise, not an acceptance proof.** It is retained so a person can read exactly what a real AI host was shown and what it answered, and judge the readings for themselves. **No semantic acceptance is claimed from it, and none is claimed anywhere in this slice.** Whether the brief's positive and independent-negative acceptance may be called PASS is a decision for the independent BLUE review; this document supplies evidence, not that verdict.

> **Final-head set.** Every file in this evidence directory comes from one full rerun of all six scenarios against **the final implementation** (code commit `50951b1`, which contains the H-1 event-triggered packet formation of `e453352`; the PR head adds only this evidence and its documents). Two earlier sets are superseded and retained only in git history: the first at `9617a98`, and the H-2 repair set at `d07c53d`, which ran before the H-1 packet orchestration existed. The H-2 correction they carry is kept here: the shared scene states affirmatively that nothing solid stands between the bench and the wall (`locus.constraint.5`: _"Nothing solid stands between the bench and the north wall: the floor between them is bare, and no screen, curtain, partition or other object crosses the line from the bench to the wall."_ — about objects and the line, not about sight or receipt), and the independent negative `n1` replaces **only that one statement** (same `path` aspect, same position) with a continuous opaque screen. Target, character, faculty statement, placement, illumination, geometry, clear air and canonical time are identical in the positive and in `n1`.

## Whether a genuine AI-host semantic exercise occurred

**Yes, with the limits below.** The host was a **real headless Claude Code client** (`claude -p`, model `claude-sonnet-5-5` per the client's own init record in every trace) registered to the **real `immortalis-referee` stdio MCP server** (`--mcp-config`), which it discovered and called unaided: for each question it called `referee_list_tasks`, `referee_get_task` and `referee_submit_decision`. The service side was the shipped `immortalis-operator` binary run as real processes (establish-locality → referee-bind-host → author-character → establish-character-locus → observe-surroundings), exactly the committed code of `50951b1`. The only in-process step is the Temporal owner's establishment of canonical time (value 100), done through the engine's own coordinator exactly as the test support does it, because no operator command for it exists yet.

No test policy, scripted answer or verdict is supplied by the driver. The driver (`run-exercise.mts.txt`) (a) types the **player's** lines, (b) types back the confirmation phrase the service printed, (c) launches the host client whenever a question is pending, and (d) after the run performs a read-only audit of the saved campaign (below; the only write it attempts is a replay of the formation, which must write nothing). No model is invoked by the audit. The host's prompt (`host-prompt.txt`) is one generic instruction, identical for all scenarios; it names no scenario, expected result or colour.

24 client runs (four questions per scenario, each answered by exactly one client run), 73 tool calls (24 `referee_list_tasks`, 24 `referee_get_task`, 25 `referee_submit_decision`), **24 decisions accepted; 23 at the first submission and 1 refused once and then corrected by the host** (`n3-no-stated-sight`, run 04: the answer did not satisfy the closed response shape, a rule identifier outside the permitted list; the retained trace shows both submissions). No other tool error.

### Honest limits

1. **One model family, one session, one run per scenario.** The same session that wrote the engine also wrote the scene, the six player statements and the expectation of each outcome. A different model, an interactive chat client, a second run of the same model or a hostile world could read the same words differently; model variance is real and was not sampled here.
2. **No person has reviewed these readings.** The engine checked that each answer was well-formed, complete and quoted the delivered words verbatim, and **derived each verdict itself**; it did not and cannot check that a reading was _right_.
3. **Earlier runs are not retained in the tree.** The two earlier full sets of six are in git history (`9617a98`, `d07c53d`). Before even those, earlier runs of the driver against earlier code exposed one ambiguity in the task text (what to answer for a world fact that "contradicts" versus one that blocks the path), which was repaired in the task document text; those earlier files were not kept. The files here are the complete set of the final-head run, one per scenario, with no selection.
4. **The negatives are mostly the shape "nothing was established", not proof of obstruction.** Only `n1` and `n5` reach `BLOCKED` on the path; `n2`, `n3` and `n4` end `UNRESOLVED` because a fact the law requires was not stated. The engine treats those as non-establishment, never as proof that something is or is not there, and the player is shown only that nothing was received.
5. **The scene is small and written in the same idiom as the question.** It is one alcove, one wall, daylight, clear air. It does not test subtle optics, partial obstruction, distance, scale, dimness, hidden or illusory sources, or several viewers.
6. **No adversarial prompt-injection witness was run** against a live host. Injection, role spoofing, source leakage and the other mechanism cases are covered by the engine's own tests with scripted answers, not by this exercise.
7. The host supplied no `claimed_model` label (optional, self-reported); the model above is the client's own init record.

**What the positive produced.** After the player's separate, confirmed choice to look, the Epistemic owner committed one `BOUNDED_SHARED_ACCESS`, one-recipient (`pc-maren`), `PERCEPTION` event, the event triggered its own packet formation under one durable transaction authority, and the sealed packet and Sealed Engine Provenance followed. The existing trusted Event-Signal path then delivered the raw appearance only:

> referent: _The north wall in front of the seated character, with a red patch on it_
> content: _A plain whitewashed wall, evenly lit, three paces ahead. On it is one broad patch of bright red, about an arm-span wide, at the height of the character's own eyes, standing out against the pale surface._

The retained positive decision records `path: OPEN` on three quoted world facts, daylight (`locus.constraint.3`), clear air (`locus.constraint.4`) and the affirmative open-path statement (`locus.constraint.5`) — not on an absence of a stated obstruction. The engine requires each payload basis item to quote the committed setting verbatim; it cannot check that the host's prose content is a faithful rendering of that basis, which is a reading for the reviewer.

**What the independent negative produced.** `n1` is the positive's scene, player, character and canonical time with the single open-path statement replaced. The host read faculty and position as `ESTABLISHED` and the path as `BLOCKED` ("Despite clear air and daylight, an opaque screen with no gap stands across the full width and height between the bench and the north wall, so nothing on the north wall reaches the viewer's eyes"; its one path premise quotes the screen statement), the engine derived `OBSERVATION_OBSTRUCTED`, no event or packet was committed and the player was told only that nothing was received, without the reason. In `n1`'s console, the observe step itself (from the confirmation prompt to the result) names no screen, wall or patch; the setting appears only in the earlier setting confirmation the person authored and in the sealed decision.

**Not-shown reasons.** In every negative the player-facing console reports `OBSERVATION_NOT_ESTABLISHED` and "nothing was received at this basis"; the verdict name, grounds and setting appear only in the retained, sealed decision and in the "ordinary open" audit section of the transcript.

## What this does and does not show

- **Shows:** the end-to-end mechanism — the final, event-triggered packet-formation path included — works with a real tool-calling host over the real stdio MCP server and real processes; that an LLM host given the closed vocabularies produced answers that satisfied the engine's coverage and quotation rules in all 24 runs (23 at the first submission, one after a single refusal); that, for this one pair of scenes, the same host, character and player produced `ESTABLISHED` for an open path affirmed by a committed setting statement and `OBSTRUCTED` when only that statement was replaced by a continuous opaque screen; that the positive was delivered and the negatives were not; and that the saved campaigns verify, replay without writing, and show no Temporal object, no indexed boundary, no crossed boundary and unchanged canonical time.
- **Does not show:** reliability across models, runs, languages, adversarial players or subtler worlds; absence of prompt-injection weaknesses; that a person would accept these readings; an ordinary user-facing game host (still absent); or that the engine's closed premise vocabulary is sufficient for scenes beyond this one.
- **Open for the independent reviewer:** whether a single positive/negative pair on one model satisfies the brief's "established by a real interpreter" bar or whether more witnesses are required; whether `n2`/`n3`/`n4` ending `UNRESOLVED` rather than `OBSTRUCTED` is the intended law (the engine's design is that missing circumstances are non-establishment, never proof of obstruction); and the one design interpretation the H-1 recovery rests on, recorded in `docs/active-pc-direct-observation-foundation.md` (an event-triggered resolution transaction under F-017 §4 with no Temporal object or indexed boundary).
