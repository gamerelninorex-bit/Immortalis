# Host-requested active-PC target-only OOC time advance — one real configured host exercise (retained, not acceptance proof)

Reported **separately** from the scripted tests, as the BLUE v5.2-A1 bounded brief (native pin `2026-10-15T15:46:04.940Z`) requires ("exercise actual configured host/tool invocation, with precise version and session trace"). It is a single exercise per scenario, run once, by one host, and it is not acceptance, not a semantic validation and not a claim about any model's understanding.

## What was run

- **Host:** the Claude Code CLI (**2.1.300**) in non-interactive print mode, started once per step with `--mcp-config` (one stdio server, `--strict-mcp-config`) and told to call the single tool once with no arguments and reply with the returned text. The host used the credentials already present in the session that ran it; this slice adds, holds and reads no provider credential, API key or paid service. The host held **two separate bindings** under one host identity (`claude-code-host`): a _request_ binding (`immortalis-advance-request`) and, separately, the existing _read_ binding (`immortalis-player-view`). Each call was a separate host process that could see only the one server it was configured with. The model identity of the host session is intentionally not recorded in this repository.
- **Campaigns:** built only by the shipped owner paths, exactly as the integration tests build theirs (`establish-locality` → `author-character` → `establish-character-locus`, each referee-qualified by a **scripted** host; then GIP's own adapter commits an institution, an office, a Scope Binding and one `active` Instrument whose own declared term is a sunset at `150` with its Temporal registration, and the Temporal owner establishes canonical time `100`). Nothing in either campaign says `expired` before the operator's choice is executed.
- **Sequence per campaign (each a separate process):** (1) the host asks through the request tool; (2) the **operator answers on its own console** (`immortalis-advance-request-answer`, the shipped answer): it printed the requesting host, said the request names no target and is not the player's choice, ran the existing `pc-target-advance` command with **the target the operator gave on its own command line**, drew a fresh challenge, and the challenge was then typed back **by a script**; (3) the host reads through the existing separate read-only server. The owner state (canonical time and the Instrument's lifecycle and version) was read by the test harness through the ordinary campaign re-open before the request, after it, and after the operator's choice.

## What it shows

Curated from the stream-json output of the four host sessions: [`host-advance-request-real-host/host-calls.json`](host-advance-request-real-host/host-calls.json).

1. **The request is real, bounded and inert.** The host reported the request server `connected`, exposing exactly one tool of this server (`request_active_pc_target_advance`), called it with `{}`, and relayed the result: `TARGET_ADVANCE_REQUESTED` with the fixed words _"No time has advanced and nothing has been decided: the player must separately name an exact target and confirm it on their own console, and may decline. This request names no target …"_. In both campaigns the canonical time (`100`), the Instrument (`active`, version `1`) and the store's own state hash were **unchanged by the request alone**.
2. **Positive.** The operator named the target `300` (beyond the sunset), confirmed the fresh challenge, and the shipped command returned `PC_TARGET_ADVANCE_COMMITTED`. The owner state then read: canonical time `300`, Instrument `expired`, version `2` — written by GIP's own sunset provider when the Temporal kernel resolved the boundary it had registered, not by the request, the operator's input or any fixture.
3. **Independently falsifying negative.** In a second campaign built from the same antecedents, the operator named the target `120` (short of the sunset) and confirmed. The shipped command again returned `PC_TARGET_ADVANCE_COMMITTED` (it is a transaction status, not target attainment or expiry), the canonical time read `120`, and the Instrument stayed `active`, version `1`.
4. **No player knowledge came of the time change.** In both campaigns the host's read through the existing read-only server, after the advance, was the existing opaque `PROJECTION_UNAVAILABLE` refusal: a time change earns no observation, packet or perception, and the host's relayed text carried nothing of the expiry.

## What it does not show

- **That any AI understood or decided anything.** The host called one tool because it was told to. It chose no target, no timing and no reason; the target and the confirmation were the operator's.
- **That a human confirmed.** The confirmation in this exercise was typed by a script on the operator's console after the console printed the fresh challenge; it demonstrates the separate channel and the single-use challenge, not that a person typed. No claim is made that OS-owner verification identifies a person.
- **That any natural play loop exists** (no in-world wait, free-text intent, action, duration, actor or movement exists), **ordinary chat-client completion** (the host was driven by a fixed instruction, not a play conversation), or that any other MCP client behaves the same. It demonstrates only that a real, locally configured MCP client can start the request server, list and call its one tool, and — separately — read afterwards through the existing read-only server.
- **Acceptance of any kind.** No F-027 register row, status or gate moved; local success is not provider/recovery acceptance (IA-07 BLOCKED).
