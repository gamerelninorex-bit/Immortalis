# B2-T12 — falsifiability: remove each guard, see which tests notice

Method: `run-mutants.py` applies ONE (or, where stated, several) exact-once text edit(s) to a production file, runs the **behavioural** B2 test set (the
integration, contract and security files below; 158 tests), records which tests fail, and restores every touched file **by SHA-256** (the harness
asserts the restore). `mutate.py` is the single-mutant driver; `mutation-results.jsonl` is its raw output at this head. The catalogue and scope conformance
tests are excluded from the set on purpose: they are byte-sensitive and fail under ANY edit, which would prove nothing.

`b2-custody-negatives`, `b2-stage-claims`, `b2-gm-wait-contracts`, `b2-static-boundary`. The unmutated set passes (158 tests) at this head.

## The survivors

- **M13b: survives by redundancy, not by a missing test.** The seal's "repeats exactly what its own opening opened" law is written twice on purpose: in the
  custody check of the seal (M13, killed by seven single-field departures) and in the Temporal kernel's own transaction admission, which a GM seal also passes through
  (the same law a player-origin seal is judged by). The custody check speaks first for every departing seal, so the kernel's copy cannot be reached by a seal the custody
  check let through; removing only the kernel's copy changes no verdict. It is kept because it is the law the legacy seal already lived under.
- **M17: an equivalent mutant.** The file package's post-replay "protected store needs the W2 admission" check cannot fire on any input: that loader replays the WHOLE
  journal, and the per-entry refusal (M16, killed) fires first for every journal that holds custody, so the state-based check is unreachable there. Its twin in the
  checkpoint package IS reachable (a warm open whose custody entries lie before the checkpoint) and is killed (M17b, by an attack test: the manifest re-stamped
  under the identity of an admission that lacks the verifier).

## Repair 1 (BLUE F-1 / F-2): the six added mutants

M21 to M26 are the guards of `repair-1.md`. **M25 restores the original defect** (the stage branch reopened on cause and dependency, the claim check removed) and is
killed by `b2-stage-claims`, `b2-fence-layers`, `b2-custody-lifecycle` and `b2-crash-recovery`. M21 (claim check removed) and M22 (claim judged live only, so replay
trusts a hash-consistent journal) are killed by the live and the forged-historical twins. M23 and M24 remove one HALF of the claim (a dependency alone, a cause alone) and each
is killed, so neither half is carried by the other. M26 widens the strict seal contract to admit credited stages again and is killed by the contract negatives.
M01 (the commit core's own fence) is now also killed by `b2-stage-claims`.

## What the layering shows (and how it was made visible)

The first run left M02, M03, M06, M07, M08 alive: the commit core alone refuses every live and replayed write during an ACTIVE wait (M01), so the base-admission and
extension-binding copies of the same predicate changed nothing a commit through the store could show. They are defence in depth, and a defence nobody exercises is
not one, so `b2-fence-layers.test.ts` calls each layer DIRECTLY on a state that holds an ACTIVE wait and requires that layer's own refusal. Likewise M13, M14, M16 and
M17b are killed by `b2-custody-negatives.test.ts`, which was added for exactly the guards the first run showed unwatched.

## What this does not show

It shows that each guard is watched by at least one test that fails when it is removed. It does not show the tests are complete (no mutation set can), and it says
nothing about a guard that was never turned into a mutant. The mutants were chosen as the load-bearing decisions of the mechanism, not by coverage tooling.
