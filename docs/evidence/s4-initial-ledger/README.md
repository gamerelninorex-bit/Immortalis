## Whole-operation cost (matched, fresh process, median of 3)

`tools/s4-ledger-benchmark.ts` holds the causal action fixed — one world, one locus, one released PC, one first-ACTIVATION binding — while the amount of **unrelated** dormant history varies (0 / 100 / 500 / 2000 committed worlds nothing refers to). The same script runs on the pre-S-4 base and on this slice; the only difference between the two runs is that the S-4 tree also commits the PC's ledger before the binding (`initializePcStandingInstructionLedger` exists only there). Each sample is a **new Node process** on a private copy of one seeded package, so nothing is warm.

Reproduce: `S4_BENCH_SHA=<label> node --experimental-strip-types tools/s4-ledger-benchmark.ts matrix <outDir>` (`S4_BENCH_SIZES`, `S4_BENCH_REPS`); run it from a checkout of the base and from this tree. Raw samples: `benchmark/raw/{before,after}-<dormant>-<n>.json`; summary: `benchmark/summary.json`.

## A defect this measurement found, and its repair (stated plainly)

The first "after" run showed `verify()` and cold reopen reading about twice as much as the base at 500 and 2000 unrelated worlds (full `verify()`: 27,485 → 54,938 file reads and 776 → 1,515 ms at 2000; cold reopen 873 → 1,141 ms). Cause: the ledger's cold-open meaning check re-judges an engine-origin ledger against "the facts as they stood before its group", and the walkable view of that cut **dated every committed fact** (one durable receipt lookup per fact) before the setup-placement scan discarded all but the few placements. The repair passes the scan's key test into the walk, so a fact is dated only if its key could be a placement; the scan's result is unchanged. The superseded first-run samples are kept in `benchmark/raw-superseded-per-fact-date-walk/`; the figures above are the repaired tree. Regression test: `tests/integration/pc-standing-ledger-scaling.test.ts` ("the per-unrelated-fact cost of verification is identical with and without a ledger"), which fails on the pre-repair code (slope 2 versus 1 receipt lookups per unrelated fact; mutation M10 below).

## BLUE exact-HEAD review H-1 on `12fe016`, and its repair

**Finding (BLUE, PR #107 comment `6949868657`):** an `ENGINE_ORIGIN_LEDGER_CLOSURE` with an explicit `setup_closure: null` was not rejected at ledger admission when the intended world already had a committed closure; the mismatch surfaced only when a binding later arrived. **Reproduced exactly as BLUE specified** (`tests/integration/pc-standing-ledger-closure-origin.test.ts`, first test): a real PC, world, locus, B1 setup placement and `world_setup_closure`; an otherwise valid raw ledger group with the closure substituted by `null`, the SHA-256, version head and derived group / intent / cause identity recomputed, and the reads and dependencies made consistent with the false null. **On `12fe016` the direct `store.commit` succeeded** (revision 7, both ledger facts committed): `h1/red-on-12fe016.txt`. **On the repair it is refused with `REFERENCE_INVALID` and neither ledger fact is committed:** `h1/green-on-repair.txt`.

**The narrow schema delta (identified, not silent).** The version value did not say which world its closure-or-null was about, so no admission could check it. The `ENGINE_ORIGIN_LEDGER_CLOSURE` origin gains **one required field, `target_world`**: an exact `{ fact_key, version, commit }` reference to the committed world profile the creation route was qualified against (the same reference encoding as `pc_creation`). Nothing else in the value, the head, the keys or the binding changes; `START_OF_LEDGER` is untouched; `target_world` also enters the derived operation identity. No owner permission, `SETUP_ELIGIBLE_KIND_IDS`, player question or Class 2 / waiting behaviour changes.

**The rule, applied at the PC-owner commit.** For an engine-origin ledger, against the cut strictly before the group: the target world's profile must be committed exactly as cited, and read and depended on; if that world has a committed `world_setup_closure` the origin must cite exactly it (an explicit null, or any other world's closure, is refused); if it has none the origin must be an explicit null **and the group must read that world's closure key at version 0** (a real absence pin, so a closure that lands beneath a planned ledger makes it a stale read and the store refuses it). One pure function (`ledgerOriginViolation`) serves normal admission, a raw `store.commit`, historical replay (the incremental pre-state) and cold-open verification, which also checks the group really pinned the absence. The binding must couple the target world and still re-checks closure applicability from the committed facts.

**Tests (all red or absent before, green now):** 21 + 12 new (table above); expectations that the repair intentionally changed: the two cross-world binding refusals in `pc-standing-ledger-foundation.test.ts` now report that the ledger was qualified against another world, and one forged origin in `pc-standing-ledger-legacy.test.ts` carries a `target_world`. Eight mutants (N1–N8) are all killed. Preserved and re-run green: the PC-owned atomic head/version → strictly older head → separate binding chain for both ACTIVATION and EXISTING_ACTOR_HANDOVER, authentic old bindings, L-2, deterministic retries and the 21 durable-cut recovery cases, concurrency, and zero extra player questions (the transcript test still finds the same 16 asks and 96 lines).

**Cost after the repair.** The ledger group now also reads and depends on the target world's profile: the action's file reads at 500 / 2000 unrelated worlds went from 90 / 114 to 102 / 129 and the package grew by about 200 bytes per ledger; elapsed times are inside the sample spread of the first submission. The first-submission samples are kept in `benchmark/raw-superseded-12fe016/` (summary `benchmark/summary-12fe016.json`); the tables above are the repaired tree.

## Plainly stated limitation (inherited; not a PASS of scaling, not a ledger-specific cost)

Elapsed time of a cold open and of `verify()` is **not independent of unrelated dormant history**: about 1 s at 2000 unrelated worlds, before and after this slice alike. That growth is the existing strict re-open of the whole campaign (journal replay and canonical integrity visit each committed fact), which every lane already performs. S-4 adds no history-proportional work of its own beyond the repaired constant above and one extra commit per newly created PC. Owning route: the existing persistence / open-cost line (H-07 retained-storage evidence), not this slice. Reconsider before any T2/T3 claim on a campaign with more than a few hundred unrelated committed facts.
