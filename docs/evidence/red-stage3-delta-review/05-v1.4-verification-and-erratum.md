## 4. Erratum to RED's v1.3 record

RED's v1.3 §3.2 said: "The store's read API is exactly five methods: `head`, `getFact`, `listFacts`, `lookupReceipt`, `committedGroup` (`store.ts` 51–66). They map one-to-one onto the audit snapshot's `head`, `factAt` and `factsAt` at the captured head, `receiptByIntent` and `groupById`."

**That was an overstatement.** `CampaignStore` (`store.ts` 49–80) declares **five required reads plus two optional read-only proof methods**: `committedGroupById?(groupId)` and `ruleCheckedGroupIds?()`. Each is documented as optional "so that a store without it fails every dependent historical proof CLOSED". In addition, `committedGroup` is keyed by **intent** id, so the `groupById` in BLUE's v1.3 snapshot corresponded to the optional group-identity method, not to `committedGroup`, and RED's "one-to-one" mapping glossed that. BLUE's v1.4 mapping (`groupByIntent` for `committedGroup`; `groupById` only if the optional capability is supplied and qualified) is the correct one.

- **What stands:** the five required reads account for the 3,393 test references stated in v1.3 (the histogram counted those five). RF-11 remains confirmed.
- **What this adds.** The optional methods are not marginal. They are referenced 7 + 12 times in production code across the engine's checkpoint and file packages, the commit core and the integrity checkers for actor presence and auditory premises and culture adjudication, and 19 + 5 times in tests. Any gate or current-view interface that withholds the raw store from those integrity consumers must supply the optional proofs or those proofs fail closed and the campaign becomes unavailable. This belongs inside BLUE's W-C-READ "current-admission/integrity consumers" driver; RED notes it as scope, not as a new finding.
- **Reproduce:** `git grep -n committedGroupById` and `git grep -n ruleCheckedGroupIds` at `36d5063`, production and tests separately.
