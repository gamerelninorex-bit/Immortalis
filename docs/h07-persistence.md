# H-07 S1: change-driven file persistence and verified reopen

Authority: [BLUE brief](https://app.notion.com/p/40520af901e081f99c71f1f9ffeaacf3), native pin `2026-10-26T03:39:33.985Z`; starting main `f74a7dd302fee98476baf44dead1e9d0e295c829`. F-027 v1.0 and all source locks, runtime snapshots and acceptance/gate registers remain unchanged. This is IM-11/12/17 implementation work under RC-07/09/16, with IA-01/02/03/06/22/30 mechanism evidence. It does not promote IA-22, IA-07, PF-6 or F-028.

The internal v2 file-store format retains the original v1 genesis identity and the exact journal bytes, canonical full-state SHA-256 and receipt/hash-chain meaning. Normal commits append changed owner writes already present in the journal, then atomically publish the manifest. At each 128-entry boundary, a derived state checkpoint and immutable path-copy index are durably written before publication. The manifest rename remains the single effective commit point. An ordinary reopen verifies its checkpoint publication proof and no more than 127 tail transitions, then the existing `CanonicalCampaign.open` owner validators run. Cold group and receipt lookups verify hash-anchored index paths and exact original journal byte ranges synchronously, preserving the existing store method shapes.

A checkpoint carries historical-verifier identity and per-entry evidence earned by admission or strict historical verification. An untrusted or changed policy requires strict replay and a separately constructed index generation before a new trusted anchor can be published. The index integrity hashes are derived lookup evidence, never a new committed state root or receipt field. No owner or receipt root is replaced. The relevant MineWorld source pattern (periodic checkpoints plus journal replay) was inspected at `b355727619ffb38dd2dbf0b09cb1b3661756146e`; its database/provider and gameplay/scheduler semantics are not adopted.

Existing v1 saves are strictly verified, retained as inert `legacy-manifest.v1.backup`, `legacy-state.v1.backup` and `legacy-journal.v1.backup` bytes, independently replayed and compared in successor form, and activated by one manifest publication. Interruption leaves the old v1 manifest or a verified successor authoritative. Old binaries are not claimed to read v2. The optional legacy writer exists for compatibility and independent v1 regression fixtures; ordinary canonical creation uses v2. No real campaigns are migrated by this PR.

BLUE [R-01](https://github.com/gamerelninorex-bit/Immortalis/pull/89#issuecomment-6419594290) repairs checkpoint crash residue that otherwise blocks the existing player-view proof. An extra correctly named state snapshot earns automatic removal only after independent journal replay reproduces its complete canonical state digest and the verified authoritative head, with the canonical caller's existing owner checks. A superseded snapshot must match committed history. An aborted next checkpoint must match the single complete uncommitted transition at the next checkpoint boundary; only an isolated proof replays it. The live core, manifest, receipts and uncommitted journal bytes remain unchanged. The existing original-intent retry still decides whether to replay the original receipt or publish the missing group, with no duplicate effects. Cleanup requires held writer authority, an unchanged on-disk authoritative manifest and unchanged candidate bytes immediately before removal. Pre-activation migration/policy verification cannot clean files under a hypothetical successor.

This residue recovery is exceptional O(state + history replay work), including historical receipt hashing and owner verification; it runs only when an extra checkpoint-state candidate exists. A clean ordinary reopen retains bounded replay and does not read historical registry data. Unknown, foreign, malformed or state-inconsistent extras retain their refusal-producing residue status; arbitrary files and partial temporary writes are not cleared by filename. Cleanup failure refuses that open and is retryable on a fresh open. The player-view residue check, projection, host binding and consent rules are unchanged. New regressions cross checkpoint publication in both directions and fail post-publication cleanup, then exercise the real player-view/Glance reconnect, immutable-intent retry, strict audit, corrupt/unknown refusal, cleanup interruption and lost-writer authority. Scripted observation setup is mechanism evidence only, not a named-client or human playtest.

`openFileCampaign(dir, { audit: true, ...bindings })` performs strict full-history verification. Use strict verification for first trust or unknown save provenance; ordinary reopen reuses anchors earned by this store or a prior strict verification. Ordinary reopen deliberately does not read untouched dormant historical bytes. Corruption there is detected when accessed or strictly audited. This is a provisional detection limitation, not immediate all-byte verification or authentication against an adversary who rewrites every hash. Full canonical hashing remains O(current state), as do current-state owner checks; first migration and explicit full audit replay the entire history and recompute each historical full-state receipt. Reconsider through the existing H-07/IA-22/Master Roadmap/OB-030 route when full hashing dominates, cold-history assurance fails, actual restart scale reveals growth, or before release qualification.

Engineering Acceptance: the same accepted goal saves and reopens the same world, without new player schema, identifiers, confirmations or technical chores. One existing store path supplies durable journal publication, derived checkpoints and exact indexed evidence. Measurements include open/replay, owner validation, map copying, sorting/full hashing, serialization, bytes and durable writes, indexed lookups and checkpoint overhead. The synthetic fixed Temporal action asserts identical outcome digest, 27 keyed reads over ten keys, zero coordinator listings, four groups, idempotent replay and close/reopen continuation. Genuine AI interpretation, named-client/human latency, sustained gameplay, hosted recovery and full Tenet 1/H-07 acceptance remain unclaimed.

## H-07 S2: policy-transition first open (OB-030 mitigation)

Authority: [BLUE brief](https://app.notion.com/p/40f20af901e081709d56ccbe40371fbb), native pin `2026-11-05T08:54:33.078Z`; exact base `main` `a1f26c70862dd0de26c0836b1708ca3b9d9aa667`. F-027 v1.0, all source locks, the Runtime Contract snapshot and both registers are unchanged (`pnpm run check:spec` passes). No owner, receipt root, manifest/checkpoint/index shape, format version, provider or gameplay behaviour is added or changed, and no real campaign is opened or migrated: every fixture is synthetic and disposable.

**The measured problem.** A compatible v2 package whose `verification_policy` differs from this build's (an older `historyVerificationId`, for example every package written before the v0.9 identity change, opened under the declared legacy admission) must earn a new trusted anchor by strict replay. PR #95's matched run measured that first open at a median 631.4 s and about 859 MB peak RSS at 2,003 entries, with 8,012 historical group verifications (4 per journal entry). Attribution on the exact base showed four complete passes over the same committed journal:

1. the strict pass that earns per-entry evidence under the current verifier (required);
2. a second full replay inside the "independent" check of the hypothetical successor (`loadCheckpoint(fresh, audit)`), over the very bytes pass 1 had just judged;
3. a third, because the published successor was then reopened with the options pass 1 had forced to `audit: true`, so the ordinary bounded reopen was silently a full replay too (and the store it returned held the whole history in memory);
4. a fourth, by the R-01 reconciliation of the checkpoint snapshot that the transition itself had just superseded, which replays the full history to prove a file this same open had already digest-verified.

**What changed.** `loadCheckpoint` (`packages/engine/src/persistence/checkpoint-package.ts`) now performs pass 1 only, and replaces passes 2-4 with work that is bounded by the journal's bytes rather than by owner replay:

- **One strict pass**, unchanged: every real group is judged by the current `verifyHistorical` against its actual incremental pre-state, chain and receipt (including the full-state SHA-256) are re-derived, owner validation (`beforeMigrationCheck`) runs once on the hypothetical successor, and the old index is compared entry by entry. Nothing inherits an old policy's `checked` flag.
- **Successor proof from durable files** (`proveSuccessor`), before the single manifest publication: the committed journal bytes re-read from disk must be byte-identical (SHA-256) to the bytes the strict pass judged; for **every** historical intent and group (`i:` and `g:` keys, 2 per journal entry) the successor index's hash-directed `lookup(root, key)` must reach exactly the `Location` the replay derived (so a misrouted branch, a missing identity or a duplicate standing in for one is refused, not merely counted); the tree must hold nothing else (each enumerated leaf is a distinct expected key, and the leaf count equals the expected key count); every node is hash-verified as it is read (the verifying reader memoizes verified nodes, so each is read once); the successor then loads as any open does (state-file digest, index root, publication proof of the last entry). A second replay of identical bytes with the same pure verifier cannot reach a different verdict, so it was the only thing dropped; the proof additionally refuses a successor that does not describe the replay that earned it, which the second replay did not compare. A lock check precedes the publication. _(BLUE hold S2-I1 on `14220f6` found that the first version of this proof enumerated leaves without checking keyed reachability; two hash-valid counterexamples, a misrouted branch and a duplicate leaf replacing an identity, are now tests and fail on that version.)_
- **Superseded snapshot** removed after publication only under the R-01 cleanup conditions (writer authority held, the published successor still the authoritative manifest, the candidate bytes still the bytes this load verified). Any doubt or failure removes nothing, and the next open runs the unchanged, fully proved R-01 reconciliation.
- **Reopen** uses the caller's own options. An ordinary caller gets the bounded, lazily verified store every later open returns; a caller that itself passed `audit: true` still gets its strict audit.

**Preserved, with falsifying tests** (`tests/integration/policy-transition-replay.test.ts`): journal bytes, receipts, `state_sha256`, head and facts are byte-identical to the unchanged package; manifest and checkpoint shapes, cardinality and meaning; owner validation before and after; a corrupted cold prefix, broken chain, rejected historical group, owner violation, state or digest mismatch, damaged, foreign, dropped or swapped index entry, a journal changed between replay and publication, a damaged successor snapshot, and a lost writer lock are each refused with no publication; an untrusted policy never publishes a trusted anchor; a crash before, after or inside every durable step converges byte-for-byte to the same verified successor; fresh processes perform and read back the transition; the original intent reconciles by immutable identity. Each of those 30 tests passes on this head; 13 of them (the count, proof and cleanup assertions: one strict pass, one verification per group, a journal changed between replay and publication) fail on the exact base loader (4 per group), and the other 17 assert preserved behaviour and pass on both (the hash-valid misrouted-branch and duplicate-leaf falsifiers pass on the base because its independent second replay caught them; they fail on the enumeration-only proof of `14220f6`). Historical lookups after the transition are checked for every identity, in this process and in fresh ones, not a sample. Fixtures are seeded through a non-fsyncing copy of the file seam (same bytes, closed cleanly) so the suite does not load a shared CI disk; every operation under test uses the production seam.

**Measured** ([evidence](evidence/h07-s2-policy-transition-cost.md), exact base `a1f26c7` against the S2-I1-repaired code `40d41e7`, same fixtures, fresh process per sample, 5 measured repetitions, 316 retained samples): the canonical 2,003-entry old-policy first open falls from a median 426.2 s (416.9-432.2) to 110.8 s (109.8-113.9), 3.85×; strict passes 4 → 1; historical group verifications 8,012 → 2,003; full-state hashing 26.5 GB → 6.66 GB; peak RSS 1,008 MB → 640 MB; writes and fsyncs identical; every sampled canonical outcome (head, facts, receipts, journal bytes) identical between base and head; ordinary open/commit unchanged within spread. The keyed-lookup proof adds 2 × entries SHA-256 key digests and about 43 ms at 503 entries (the first, enumeration-only run measured 108.0 s at 2,003, so the repair costs about 2.6% there). The one-fact series (state does not grow) improves about 2× at the same 4× fewer passes.

**What this does not do, stated plainly.** The remaining cost of a first open is the one required strict pass, which is still O(entries × state): replay recomputes the canonical full-state SHA-256 of every historical receipt, and the profile in [the matched evidence](evidence/h07-s2-policy-transition-cost.md) attributes most of the pass to that exact hashing and canonical serialization. It is a once-per-campaign-per-policy cost, not a per-session one, but it is not constant, and this change neither makes it cheap at long history nor introduces an incremental, staged or background re-verification. A caller that asks for `audit: true` on a package whose policy also differs pays the policy-forced pass plus the audit it requested; a crash after publication and before cleanup costs one further proved replay on the next open. The OB-030 pre-live-open HOLD persists until BLUE independently reviews the actual performance evidence and expressly resolves it; a green suite does not lift it. T2/T3 (genuine host, named client), retained storage, sustained play and H-07 acceptance remain UNRUN.

**Reconsideration trigger (OB-030 / H-07 / IA-22 route):** if, at the history length a real campaign reaches before it is opened live, the single strict pass is still prohibitive, the next separately authorized slice should address the pass itself (a byte-identical incremental canonical state digest, or staged verification with its own interruption evidence), not this loader.

Reproduce: `H07S2_EXACT_SHA=<commit> bash tools/h07-s2-benchmark.sh` (fixtures are rebuilt by the script; `tools/h07-s2-benchmark.ts` drives one fresh-process sample, `tools/h07-s2-compare.ts` reduces the raw JSON).

## H-07 S3: strict historical replay re-derives each receipt digest incrementally (OB-030 mitigation)

Authority: [BLUE brief](https://app.notion.com/p/40f20af901e08115be38c9eca083f717), native pin `2026-11-05T17:11:20.132Z`; exact base `main` `0b203a5ca502dd79ed847aedd235c97b660ad9ea`. F-027 v1.0, all source locks, the Runtime Contract snapshot and both registers are unchanged (`pnpm run check:spec` passes). No owner, receipt root or field, journal byte, manifest/checkpoint/index shape, format version, provider, credential or gameplay behaviour is added or changed, and no real campaign is opened or migrated: every fixture is synthetic and disposable. IM-11/12/17 under RC-06/07/09/16, mechanism only.

**The measured problem.** After S2 the first open of an old-policy package is one strict pass, but the pass still recomputed the canonical full-state SHA-256 of every historical receipt by sorting every fact, re-serialising every fact with `canonicalJson` and hashing the whole text, at every revision: O(entries × state). The matched profile in the S2 evidence attributed about 69% of the remaining first open (503 entries) to that, and on the exact S3 base the 2,003-entry canonical first open still took a median 103.5 s with about 6.66 GB hashed and 6.6 G characters serialised.

**What changed, and what did not.**

- The digest is, and stays, the SHA-256 of exactly `{"campaign_id":…,"facts":[…],"revision":N}`, the facts in ascending UTF-16 key order and each the `canonicalJson` of that fact. No other digest, checkpoint, approximation, skipped check or later-checkpoint substitute is introduced. Every historical receipt is still recomputed over those exact bytes and compared with the recorded receipt, together with the entry hash, group/intent identity, chain, expected versions, reads, dependencies, the CURRENT `verifyHistorical` against the actual incremental pre-state, and the unchanged owner validation.
- `packages/engine/src/commit/state-digest.ts` (new) is an ephemeral, process-local evaluator of that same message for a strict replay that advances one committed group at a time: a fact's canonical bytes are produced once (by the same `canonicalJson`) and kept while the fact is unchanged; the sorted order is kept by merging the written facts into the previous order instead of re-sorting; and SHA-256 prefix states (`Hash#copy` every 32 facts) are reused for exactly the prefix before the first fact a group changed, and nothing after it. Where keys fall is never assumed: an early rewrite hashes (nearly) the whole message again, a late one almost none of it. It persists nothing, publishes no root, and falls back to the unchanged from-scratch computation for any state it cannot handle (a Map key different from the fact's key, a `written` list that does not describe the step, another campaign's identity); a failure inside it clears its alignment and surfaces exactly as `canonicalJson` does.
- `CampaignCore.#compute`, the receipt construction, is **byte-identical** (it is pinned by `tests/conformance/h07-source-boundaries.test.ts`, which is unchanged and passes). `replay` makes the one `stateSha256` call of that construction answer through a single-use, synchronous hook that it sets and clears around `#compute` (cleared on every exit, including a throw); everywhere else `stateSha256` is the unchanged from-scratch reference. `prepare` (every live commit), admission, the loaders' independent state checks and the head checks therefore all still use the reference, and the final `stateSha256(core.state) === head.state_sha256` check of the strict pass remains an independent from-scratch cross-check of the evaluator's last answer. The evaluator lives in the `CampaignCore` only while a replay runs: a live `accept` and `CampaignCore.endReplay()` (called once by `loadCheckpoint` when its replay loop ends) release it.
- The ordinary bounded tail replay (at most 127 entries) uses the same evaluator, so ordinary opens of larger states also improve. Its one-time construction from the checkpoint state is the same `canonicalJson` work as one reference digest plus a copy of each fact's bytes, so a one-entry tail does not pay for more than it did; the matched ordinary-path cells in the evidence show the ordinary open improving and the live commit unchanged.
- Not changed, deliberately: `file-package.ts` (its bytes are pinned by several older suites; the legacy v1 loader's core is discarded after migration), the live commit path, owner validation, the derived index, the publication boundary, the lock arbiter and the manifest-rename commit point. The persistence and commit directory pins in `tests/conformance/auditory-premises-conformance.test.ts` are refreshed with comments, as for H-07 R-01 and S2; `check:spec` and the historical-pin census pass.

**Preserved, with falsifying tests.** `tests/unit/state-digest.test.ts` (43 tests): the evaluator equals the reference at every revision for appending late, inserting early, inserting anywhere, overwriting the first, a middle and the last key, several writes per group, awkward UTF-16 vs code-point key orders, and sizes straddling every prefix boundary (1-130 facts), over many seeds; it rebuilds only once per replay; it falls back or rebuilds, never guesses, on a misaligned, renamed or inconsistent step; a live commit never touches it; an admission asking `stateSha256` during replay gets the reference; ending a replay, interleaving a live commit and replaying again change no result; a receipt state hash altered at an early/middle/late revision, a receipt computed over a different byte order, a changed first/middle/last EXISTING fact after the prefix states were built (the case a wrong invalidation would accept), a duplicated/skipped/reordered entry and a group writing one key twice are each refused and the genuine entry then applies. `tools/h07-s3-mutation-check.sh` breaks the evaluator ten ways and the suite fails on every one. `tests/integration/strict-replay-digest.test.ts` (30 tests) takes packages written by the ordinary path under an older policy: growing state and history at 3/103/503/2,003 entries, a 3,003-entry one-fact history, fixed-size states whose history rewrites an existing first/middle/last/rotating fact, and real canonical owners under the declared pre-v0.9 Runtime Contract at 103 and 503 entries. For each: one strict pass judges each group once; the evaluator produced a digest for every revision, equal to the one the unchanged writer recorded (spied) and, at sampled revisions, to an independent definition that shares no code with the core; head, facts, receipts, groups and journal bytes are identical; a real new intent is accepted, idempotent on repeat and refused when altered; a cold reopen, a lookup of every historical identity and a strict audit all remain lawful; and a fresh process performs and reads back the transition. Refusals, each leaving every byte of the package unchanged: an altered receipt hash, a changed fact value (hash re-sealed) at early/middle/late revisions, a content mismatch, a reordered line, a claimed foreign owner, a damaged or duplicate-fact checkpoint snapshot, a corrupted cold entry (accepted by an ordinary cached open, found by the transition), an untrusted policy, an incompatible contract, a lost writer lock. A crash before/after every durable step on growing, late-rewrite and early-rewrite packages leaves the old or the one verified new manifest and converges byte-for-byte; two concurrent recoveries yield one winner, one refused open and one verified successor. The S2 suite (`policy-transition-replay.test.ts`, `legacy-package-compat.test.ts`, `checkpoint-*.test.ts`) passes unchanged.

**Measured** ([evidence](evidence/h07-s3-strict-replay-hashing-cost.md), exact base `0b203a5` against product code `eb997bc`, same fixtures, fresh process per sample, 5 measured repetitions, 480 retained records): the canonical 2,003-entry old-policy first open falls from a median 103.5 s (98.6-104.3) to 10.1 s (9.9-10.7), 10.2×; CPU 113.9 → 11.3 s; peak RSS 628 → 501 MB; characters serialised 6.6 G → 0.25 G; full-state sorts 1,998 → 58; SHA-256 bytes processed 6.66 → 3.41 GB (51% of what each digest covers is an unchanged prefix at this fixture's key order); strict passes, groups verified, bytes read and written, fsyncs and digests identical. 503 entries: 7.09 → 1.79 s (3.96×); 103: 0.57 → 0.35 s (1.64×); 3: no change. Fixed-size states rewriting one existing fact (2,000 entries): 3.17× (first key, 87% of the message re-hashed), 3.28× (middle), 3.56× (last key, 5% re-hashed), 3.43× (rotating). A one-fact history, whose state is tiny, shows no gain and no material change (−9% to +2%, overlapping ranges; about +15-25 µs per replayed entry in the focused timing). Ordinary open of the canonical 2,003-entry package: 10.2 → 2.6 s; the live commit is unchanged within spread. Every sampled canonical outcome (head, every fact, probe receipts and groups, journal bytes, the accepted commit's receipt, owner violations) is identical between base and head in all 39 cell groups (458 samples).

**What this does not do, stated plainly.** The first open of a 2,003-entry canonical package is still about 10 s and still grows faster than linearly. The SHA-256 requirement is exact, so the bytes at and after the first changed fact are hashed again at every revision: 3.4 GB at this fixture, and nearly the whole state every time when the writes land early in the key order of a large state (the first-key shape above). What remains is dominated by work this slice does not touch: the unchanged owner validation (about 2.2 s at 2,003 entries), the derived-index extension and lookups (about 2.8 s), the loader's own independent single-state digests (about 0.65 s) and the immutable-state `Map` copy per replayed entry (about 0.2 s). It is a once-per-campaign-per-policy cost, not a per-session one. No SLA or game limit is derived, and **the OB-030 pre-live-open HOLD persists** until BLUE independently reviews the actual evidence and expressly resolves it; a green suite does not lift it. T2/T3 (genuine host, named client), retained storage, sustained play and H-07 acceptance remain UNRUN.

**Reconsideration trigger (OB-030 / H-07 / IA-22 route):** if, at the history length and state size a real campaign reaches before it is opened live, the first open is still prohibitive, the next separately authorized slice addresses what S3 leaves: owner validation and index construction cost, or staged verification with its own interruption evidence, not a weaker digest.

Reproduce: `H07S3_EXACT_SHA=<commit> bash tools/h07-s3-benchmark.sh` (fixtures are rebuilt by the script; `tools/h07-s3-benchmark.ts` drives one fresh-process sample, `tools/h07-s3-compare.ts` reduces the raw JSON, `tools/h07-s3-replay-micro.ts` times the replay alone, `tools/h07-s3-mutation-check.sh` runs the falsifiability check).
