# H-07 S1: change-driven file persistence and verified reopen

Authority: [BLUE brief](https://app.notion.com/p/40520af901e081f99c71f1f9ffeaacf3), native pin `2026-10-26T03:39:33.985Z`; starting main `f74a7dd302fee98476baf44dead1e9d0e295c829`. F-027 v1.0 and all source locks, runtime snapshots and acceptance/gate registers remain unchanged. This is IM-11/12/17 implementation work under RC-07/09/16, with IA-01/02/03/06/22/30 mechanism evidence. It does not promote IA-22, IA-07, PF-6 or F-028.

The internal v2 file-store format retains the original v1 genesis identity and the exact journal bytes, canonical full-state SHA-256 and receipt/hash-chain meaning. Normal commits append changed owner writes already present in the journal, then atomically publish the manifest. At each 128-entry boundary, a derived state checkpoint and immutable path-copy index are durably written before publication. The manifest rename remains the single effective commit point. An ordinary reopen verifies its checkpoint publication proof and no more than 127 tail transitions, then the existing `CanonicalCampaign.open` owner validators run. Cold group and receipt lookups verify hash-anchored index paths and exact original journal byte ranges synchronously, preserving the existing store method shapes.

A checkpoint carries historical-verifier identity and per-entry evidence earned by admission or strict historical verification. An untrusted or changed policy requires strict replay and a separately constructed index generation before a new trusted anchor can be published. The index integrity hashes are derived lookup evidence, never a new committed state root or receipt field. No owner or receipt root is replaced. The relevant MineWorld source pattern (periodic checkpoints plus journal replay) was inspected at `b355727619ffb38dd2dbf0b09cb1b3661756146e`; its database/provider and gameplay/scheduler semantics are not adopted.

Existing v1 saves are strictly verified, retained as inert `legacy-manifest.v1.backup`, `legacy-state.v1.backup` and `legacy-journal.v1.backup` bytes, independently replayed and compared in successor form, and activated by one manifest publication. Interruption leaves the old v1 manifest or a verified successor authoritative. Old binaries are not claimed to read v2. The optional legacy writer exists for compatibility and independent v1 regression fixtures; ordinary canonical creation uses v2. No real campaigns are migrated by this PR.

BLUE [R-01](https://github.com/gamerelninorex-bit/Immortalis/pull/89#issuecomment-6419594290) repairs checkpoint crash residue that otherwise blocks the existing player-view proof. An extra correctly named state snapshot earns automatic removal only after independent journal replay reproduces its complete canonical state digest and the verified authoritative head, with the canonical caller's existing owner checks. A superseded snapshot must match committed history. An aborted next checkpoint must match the single complete uncommitted transition at the next checkpoint boundary; only an isolated proof replays it. The live core, manifest, receipts and uncommitted journal bytes remain unchanged. The existing original-intent retry still decides whether to replay the original receipt or publish the missing group, with no duplicate effects. Cleanup requires held writer authority, an unchanged on-disk authoritative manifest and unchanged candidate bytes immediately before removal. Pre-activation migration/policy verification cannot clean files under a hypothetical successor.

This residue recovery is exceptional O(state + history replay work), including historical receipt hashing and owner verification; it runs only when an extra checkpoint-state candidate exists. A clean ordinary reopen retains bounded replay and does not read historical registry data. Unknown, foreign, malformed or state-inconsistent extras retain their refusal-producing residue status; arbitrary files and partial temporary writes are not cleared by filename. Cleanup failure refuses that open and is retryable on a fresh open. The player-view residue check, projection, host binding and consent rules are unchanged. New regressions cross checkpoint publication in both directions and fail post-publication cleanup, then exercise the real player-view/Glance reconnect, immutable-intent retry, strict audit, corrupt/unknown refusal, cleanup interruption and lost-writer authority. Scripted observation setup is mechanism evidence only, not a named-client or human playtest.

`openFileCampaign(dir, { audit: true, ...bindings })` performs strict full-history verification. Use strict verification for first trust or unknown save provenance; ordinary reopen reuses anchors earned by this store or a prior strict verification. Ordinary reopen deliberately does not read untouched dormant historical bytes. Corruption there is detected when accessed or strictly audited. This is a provisional detection limitation, not immediate all-byte verification or authentication against an adversary who rewrites every hash. Full canonical hashing remains O(current state), as do current-state owner checks; first migration and explicit full audit replay the entire history and recompute each historical full-state receipt. Reconsider through the existing H-07/IA-22/Master Roadmap/OB-030 route when full hashing dominates, cold-history assurance fails, actual restart scale reveals growth, or before release qualification.

One existing store path supplies durable journal publication, derived checkpoints and exact indexed evidence. Measurements include open/replay, owner validation, map copying, sorting/full hashing, serialization, bytes and durable writes, indexed lookups and checkpoint overhead. ## H-07 S2: policy-transition first open (OB-030 mitigation)

Authority: [BLUE brief](https://app.notion.com/p/40f20af901e081709d56ccbe40371fbb), native pin `2026-11-05T08:54:33.078Z`; exact base `main` `a1f26c70862dd0de26c0836b1708ca3b9d9aa667`. F-027 v1.0, all source locks, the Runtime Contract snapshot and both registers are unchanged (`pnpm run check:spec` passes). No owner, receipt root, manifest/checkpoint/index shape, format version, provider or gameplay behaviour is added or changed, and no real campaign is opened or migrated: every fixture is synthetic and disposable.

**The measured problem.** A compatible v2 package whose `verification_policy` differs from this build's (an older `historyVerificationId`, for example every package written before the v0.9 identity change, opened under the declared legacy admission) must earn a new trusted anchor by strict replay. PR #95's matched run measured that first open at a median 631.4 s and about 859 MB peak RSS at 2,003 entries, with 8,012 historical group verifications (4 per journal entry). Attribution on the exact base showed four complete passes over the same committed journal:

1. the strict pass that earns per-entry evidence under the current verifier (required);
2. a second full replay inside the "independent" check of the hypothetical successor (`loadCheckpoint(fresh, audit)`), over the very bytes pass 1 had just judged;
3. a third, because the published successor was then reopened with the options pass 1 had forced to `audit: true`, so the ordinary bounded reopen was silently a full replay too (and the store it returned held the whole history in memory);
4. a fourth, by the R-01 reconciliation of the checkpoint snapshot that the transition itself had just superseded, which replays the full history to prove a file this same open had already digest-verified.

**What changed.** `loadCheckpoint` (`packages/engine/src/persistence/checkpoint-package.ts`) now performs pass 1 only, and replaces passes 2-4 with work that is bounded by the journal's bytes rather than by owner replay:

- **One strict pass**, unchanged: every real group is judged by the current `verifyHistorical` against its actual incremental pre-state, chain and receipt (including the full-state SHA-256) are re-derived, owner validation (`beforeMigrationCheck`) runs once on the hypothetical successor, and the old index is compared entry by entry. Nothing inherits an old policy's `checked` flag.
- **Successor proof from durable files** (`proveSuccessor`), before the single manifest publication: the committed journal bytes re-read from disk must be byte-identical (SHA-256) to the bytes the strict pass judged; every node of the freshly written index generation is read back hash-verified, and the generation must hold, for every historical intent and group, exactly the location the replay derived, and no other key; the successor then loads as any open does (state-file digest, index root, publication proof of the last entry). A second replay of identical bytes with the same pure verifier cannot reach a different verdict, so it was the only thing dropped; the new proof additionally refuses a successor that does not describe the replay that earned it, which the second replay did not compare. A lock check precedes the publication.
- **Superseded snapshot** removed after publication only under the R-01 cleanup conditions (writer authority held, the published successor still the authoritative manifest, the candidate bytes still the bytes this load verified). Any doubt or failure removes nothing, and the next open runs the unchanged, fully proved R-01 reconciliation.
- **Reopen** uses the caller's own options. An ordinary caller gets the bounded, lazily verified store every later open returns; a caller that itself passed `audit: true` still gets its strict audit.

**Preserved, with falsifying tests** (`tests/integration/policy-transition-replay.test.ts`): journal bytes, receipts, `state_sha256`, head and facts are byte-identical to the unchanged package; manifest and checkpoint shapes, cardinality and meaning; owner validation before and after; a corrupted cold prefix, broken chain, rejected historical group, owner violation, state or digest mismatch, damaged, foreign, dropped or swapped index entry, a journal changed between replay and publication, a damaged successor snapshot, and a lost writer lock are each refused with no publication; an untrusted policy never publishes a trusted anchor; a crash before, after or inside every durable step converges byte-for-byte to the same verified successor; fresh processes perform and read back the transition; the original intent reconciles by immutable identity. Each of those 27 tests passes on this head; 13 of them (the count, proof and cleanup assertions: one strict pass, one verification per group, a journal changed between replay and publication) fail on the exact base loader (4 per group), and the other 14 assert preserved behaviour and pass on both. Fixtures are seeded through a non-fsyncing copy of the file seam (same bytes, closed cleanly) so the suite does not load a shared CI disk; every operation under test uses the production seam.

**Measured** ([evidence](evidence/h07-s2-policy-transition-cost.md), exact base `a1f26c7` against this code, same fixtures, fresh process per sample, 5 repetitions): the canonical 2,003-entry old-policy first open falls from a median 418.4 s (400.2-433.5) to 108.0 s (104.6-114.0), 3.87×; strict passes 4 → 1; historical group verifications 8,012 → 2,003; full-state hashing 26.5 GB → 6.66 GB; peak RSS 1,002 MB → 634 MB; writes and fsyncs identical; every sampled canonical outcome (head, facts, receipts, journal bytes) identical between base and head; ordinary open/commit unchanged within spread. The one-fact series (state does not grow) improves about 2× at the same 4× fewer passes.

**What this does not do, stated plainly.** The remaining cost of a first open is the one required strict pass, which is still O(entries × state): replay recomputes the canonical full-state SHA-256 of every historical receipt, and the profile in [the matched evidence](evidence/h07-s2-policy-transition-cost.md) attributes most of the pass to that exact hashing and canonical serialization. It is a once-per-campaign-per-policy cost, not a per-session one, but it is not constant, and this change neither makes it cheap at long history nor introduces an incremental, staged or background re-verification. A caller that asks for `audit: true` on a package whose policy also differs pays the policy-forced pass plus the audit it requested; a crash after publication and before cleanup costs one further proved replay on the next open. The OB-030 pre-live-open HOLD persists until BLUE independently reviews the actual performance evidence and expressly resolves it; a green suite does not lift it. T2/T3 (genuine host, named client), retained storage, sustained play and H-07 acceptance remain UNRUN.

**Reconsideration trigger (OB-030 / H-07 / IA-22 route):** if, at the history length a real campaign reaches before it is opened live, the single strict pass is still prohibitive, the next separately authorized slice should address the pass itself (a byte-identical incremental canonical state digest, or staged verification with its own interruption evidence), not this loader.
