The internal v2 file-store format retains the original v1 genesis identity and the exact journal bytes, canonical full-state SHA-256 and receipt/hash-chain meaning. Normal commits append changed owner writes already present in the journal, then atomically publish the manifest. At each 128-entry boundary, a derived state checkpoint and immutable path-copy index are durably written before publication. The manifest rename remains the single effective commit point. An ordinary reopen verifies its checkpoint publication proof and no more than 127 tail transitions, then the existing `CanonicalCampaign.open` owner validators run. Cold group and receipt lookups verify hash-anchored index paths and exact original journal byte ranges synchronously, preserving the existing store method shapes.

A checkpoint carries historical-verifier identity and per-entry evidence earned by admission or strict historical verification. An untrusted or changed policy requires strict replay and a separately constructed index generation before a new trusted anchor can be published. The index integrity hashes are derived lookup evidence, never a new committed state root or receipt field. No owner or receipt root is replaced. The relevant MineWorld source pattern (periodic checkpoints plus journal replay) was inspected at `b355727619ffb38dd2dbf0b09cb1b3661756146e`; its database/provider and gameplay/scheduler semantics are not adopted.

Existing v1 saves are strictly verified, retained as inert `legacy-manifest.v1.backup`, `legacy-state.v1.backup` and `legacy-journal.v1.backup` bytes, independently replayed and compared in successor form, and activated by one manifest publication. Interruption leaves the old v1 manifest or a verified successor authoritative. Old binaries are not claimed to read v2. The optional legacy writer exists for compatibility and independent v1 regression fixtures; ordinary canonical creation uses v2. No real campaigns are migrated by this PR.

`openFileCampaign(dir, { audit: true, ...bindings })` performs strict full-history verification. Use strict verification for first trust or unknown save provenance; ordinary reopen reuses anchors earned by this store or a prior strict verification. Ordinary reopen deliberately does not read untouched dormant historical bytes. Corruption there is detected when accessed or strictly audited. This is a provisional detection limitation, not immediate all-byte verification or authentication against an adversary who rewrites every hash. Full canonical hashing remains O(current state), as do current-state owner checks; first migration and explicit full audit replay the entire history and recompute each historical full-state receipt.
